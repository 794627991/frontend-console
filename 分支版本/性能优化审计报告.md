## 确认问题列表（按严重度排序）

### P1-1｜`appendRaw` rAF 合并：后台整窗时 `_writeQueue` 无界堆积 + 恢复时单次巨量 `term.write` 卡死
- 位置：`index.html:1292-1304`
- 触发：设备持续输出（如日志/抓包），用户把 pywebview 窗口最小化或系统进入 occlusion，`requestAnimationFrame` 不再每帧回调。`loadingHistory` 为 false 时，`appendRaw` 每次都把 SSE chunk 追加进 `_writeQueue`，但 flush 依赖 rAF，永远不触发 → 队列无限增长（可到几十~几百 MB）。恢复前台后 rAF 补一次回调，**一次性 `term.write(几百MB)`**，xterm 同步解析会冻结数秒甚至假死。
- 与旧代码对比：旧代码每个 SSE chunk 立即 `term.write`（事件源只要被 consume 就写，无 rAF 门控）。回归点是 rAF 门控是**新增的**。
- 备注：同页面多个连接 tab 用 `display:none` 隐藏时 rAF 仍会触发（rAF 是 document 级，与元素可见性无关，`switchTab` index.html:1265 只是 CSS 隐藏），所以**只在整窗后台化时才出问题**，连接 tab 切换不触发。
- 修复建议（任选）：
  1. 在 rAF 回调里对 `_writeQueue` 长度设置上限（如 >1MB 时先写掉再继续攒）；
  2. flush 时若队列异常大，按行拆成多个 write 分批，避免单次超长 write；
  3. 监听 `visibilitychange`，hidden 时改用 `setTimeout(0)`（后台定时器仍会迟到执行）代替纯 rAF 兜底，避免无界堆积。

### P1-2｜`termSendRaw` 微批：关闭连接后积压的按键被静默丢弃（最后一条命令丢失）
- 位置：`index.html:1335-1352`，配合 `closeConnection` `index.html:1600-1612`
- 触发：用户在输入框打了半条命令，在 8ms 定时器尚未触发时点了「断开」（鼠标通常"打完即点"），或粘贴大文本过程中关闭。关闭时 `_sendQ` 里积压的字节随 `delete connections[portId]` 一起被丢弃；`closeConnection` **没有清除 `b._sendTimer`**，定时器后置触发时 `connections[portId] !== b` → return，剩余队列不发送。
- 旧代码：每键立即 fetch，关不关闭都已发出。回归点：微批把"已按键但未发出"的窗口从 ~0 拉长到 ≤8ms。
- 影响：8ms 窗口内的最后按键丢失。极低频、后果轻（一条命令不全），但确实改变了行为。
- 修复建议：`closeConnection` 里在判 `!b` 前先清 `clearTimeout(b._sendTimer)` 并 flush `b._sendQ`（若连接还没被后端 pop，仍可发）；或至少 documentation 说明该限制。

### P2-1｜rAF flush 丢弃"入队时未暂停、flush 时已暂停"的一帧数据
- 位置：`index.html:1292-1303`
- 触发：`appendRaw` 在非暂停态把数据入 `_writeQueue` 并排 rAF；随后用户在下一帧前点了「暂停滚屏」（`index.html:1814`），rAF 回调里 `!conn.paused` 为 false → 清空 `_writeQueue`、不 write、不 highlight。这一帧实时输出被静默丢弃。
- 旧代码：`conn.term.write(text)` 与 ingest 同步执行，无此窗口。回归点：rAF 将 write 从 ingest 同帧推迟到下一帧，引入了这个竞态。
- 影响：暂停那一瞬间的 ≤1 帧数据丢失。低严重度，但行为与旧版不一致。
- 修复建议：flush 时若 paused，把数据写回 `pendingRaw`（复用历史缓冲语义）而不是丢弃；或保留在 `_writeQueue` 等恢复暂停后再 flush（需另加标志避免 1 失效）。

### P2-2｜`refreshMcpInfo` 最近调用脏检查：同一秒两次 MCP 调用 + 列表封顶后不刷新
- 位置：`index.html:2341-2348`
- 触发：`_mcpCallsKey = calls[len-1].ts + '|' + calls.length`。`c.ts` 是**秒**精度（`new Date(c.ts*1000)`，index.html:2341）。当后端最近调用列表已是固定上限（如 slice(20)），`calls.length` 恒定 = N；若两个不同调用落在同一秒内作为最新，`ts` 不变、`len` 不变 → key 不变 → 面板 30s 轮询不渲染新的最近调用，展示陈旧列表。
- 影响：极低。仅同秒多次调用且列表已满时，面板最大延迟到下一秒 key 变化才更新。SPCEC 但可防：建议把 key 改成最新条目对象序列化（含 name/args 摘要），或加一个自增计数器由后端返回。

### P2-3｜`highlightNewKw` decoration 上限 5000→1500：错误密集长日志的常驻高亮大幅缩水
- 位置：`index.html:1442-1445`
- 触发：一条配置/内核刷屏日志里 `error/panic/fail` 关键字行超过 1500 时，只保留最新的 1500 个 decoration，旧关键字行高亮永久消失（`kwDecorLastRow` 已越过那些行，不再重扫）。
- 影响：连招是 UX 层面的"已看到的高亮消失"，非功能错误，但属于明确的用户可见回归。可接受，但建议在造成困惑时把旧 decoration 清除策略与 `kwDecorLastRow` 联动说明清楚。

### P3-1｜串口空闲时的 CPU/唤醒频次约 10 倍于旧实现（忙轮询竞态窗口）
- 位置：`server.py:745-758`（`_io_read_chunk`）＋ `_reader_loop` `server.py:607` sleep(0.02)
- 说明：旧代码空闲时 `s.read(1)` 阻塞在 `timeout=0.2` 内，循环实际周期 ≈200ms（约 5 次/秒唤醒）；新代码 `in_waiting==0` 直接返回 b""，靠外层 `sleep(0.02)`，循环周期 20ms（约 50 次/秒激活 + 每次 `in_waiting` 系统调用）。**空闲时唤醒频次 x10**，属于常态 CPU 成本上升。
- 反向收益：数据到达延迟从最坏 ~200ms 降到 ~20ms（旧阻塞读的等待窗）。这是有意的延迟/吞吐优化，但注释只写了吞吐，没提空闲 CPU 上升。
- 建议：可考虑保留旧"或 1/阻塞"策略仅用于空闲判空（`select` 或 `read(1)` 短超时），或用 `serial.Serial.in_waiting` + 仅在有数据时才走高频；避免 50Hz 常态轮询。

### P3-2｜`SerialPort._io_reconnect` 仍是 `timeout=0.2`（与新的 0.02 不一致）
- 位置：`server.py:777`
- 触发：串口掉线自动重连成功后，若重连期间设备持续输出，offline 到重连这段读路径仍走旧的 0.2s 阻塞，与主路径 0.02 不一致。功能不坏，只是配置漂移，可能造成重连后短暂延迟感知。
- 建议：统一改成 0.02（或抽成常量）。

### P4-1｜注释与实际行为不符：`timeout=0.02` 在判空路径已基本失效
- 位置：`server.py:752-757` 注释"低吞吐时 timeout 0.02s 后返回 b''"
- 实际：`if not n: return b""` 在调用 `s.read()` 之前就返回了，`timeout=0.02` 只在 `in_waiting` 非 0 但字节未落缓冲的窄竞态下才偶发触发。文档性 bug，无功能影响。

## 疑似但不确定（SPECULATIVE）

### S-1｜`appendRaw` 与 `loadingHistory`/`pendingRaw` 的排序竞态（评估为真实但窗口极窄）
- 位置：`index.html:1289(PendingRaw) + 1292-1304(writeQueue) + loadBuffer 1473-1478`
- 场景：数据入 `_writeQueue`（未 loading）→ rAF 未触发前用户触发 loadBuffer（`loadingHistory=true`）→ loadBuffer 的 `term.write(历史)` 先落 xterm → 之后 rAF 把 `_writeQueue` 里的"更新的实时数据"write 到历史上面（旧行在实时行之下）。
- `pendingRaw` 机制本想避免"实时插到历史前"，但只防了 history 加载期间的 ingest，没防"加载前一帧已入 writeQueue"的路径，排序被部分重引入。窗口 = 1 帧（~16ms），仅在"滚动触发 history 加载且同时设备在高速输出"时命中。
- 我的判断：真实存在但难以稳定复现；建议 loadBuffer 入口先把 `_writeQueue` 排空的实时数据合并进 history 之后再渲染（或在 `loadingHistory=true` 时把 `_writeQueue` 剩余清到 pendingRaw）。

### S-2｜`refreshSidebar` 脏检查 key 不含 label/baud/host
- 位置：`index.html:1646` key = `ids.join('|') + '#' + activePortId`
- 本版本无运行时改名/改波特率路径（label 在建连接时固定，index.html:1571/1589/2763），所以当前不漏。但任何未来"重连改波特率"或"SSH 改 host"若复用同一 port_id 覆盖 meta，侧边栏将因 key 不变而漏更新，直到 id 集合或 active 变化。属**结构性脆弱**，非当前 bug。建议 key 里补一个连接元数据摘要。

### S-3｜`_tftp` 传输计数竞态（GIL 保护字段，非崩溃级）
- 位置：`server.py` `_send_file`/`_recv_file` 直接改 `t.bytes_done/t.status`，`status()` 不加锁读。int/str 在 CPython GIL 下读写原子，仅进度可能晚一拍。属良性竞态，不按 bug 计。

## 误报澄清（已核查确认没问题）

1. **termSendRaw 不用于 MCP/AI 路径**：`termSendRaw` 唯一调用点 = xterm `onData`(1174)、全屏退出(1199)、Ctrl+C/D 按钮(1828/1829)、粘贴(2119)。MCP/AI 走 `POST /api/ai/send_raw`（mcp_server.py:249→server.py:1508），**不经 termSendRaw 的 8ms 批**，即时发送，C 正确性不受影响。

2. **Ctrl-C 中断 top 的 8ms 延迟可接受**：`termSendRaw(portId,[3])` 追加进当前 `_sendQ`，与该批既有字节一起发，字节序保持，≤8ms 后到设备。对 top/vim 无感知。批不跨命令重组，不会把 Ctrl-C 提前或打乱。

3. **portId 复用时 rAF/定时器数据不会写到错误连接**：两处都判 `connections[portId] === conn/b`。重连复用同一 portId 时旧队列被丢弃（不写错终端）。旧代码等价（写已 dispose 的 term 同样无效）。

4. **rAF 在连接 tab 间切换不会堆积**：rAF 是 document/root 级，隐藏 tab（display:none, index.html:1265）仍会回调。堆积仅存在于整窗后台化（见 P1-1）。

5. **`conn.paused` 时 ingest 即丢弃是旧行为，非本次引入**：`if (!conn || conn.paused) return;`（index.html:1287）与旧版一致（HEAD 版同样首行判 paused）。本次只引入 flush 时的一帧丢弃窗口（P2-1）。

6. **SSH 读路径无回归**：`_io_read_chunk`(server.py:831) 用 `select`(0.2s) + `recv(4096)`，判空走 reader 的 20ms sleep，空闲唤醒频次不变，无忙轮询。

7. **`_io_read_chunk` 不丢数据**：`s.read(n)` 在 in_waiting 非 0 时返回 ≤n 字节，余量下次循环读走；`return chunk or b""` 兜底。无字节丢失。

8. **新建连接后侧边栏即刻刷新**：connectPort(1574)/connectSSH(1592) 都显式调 `refreshSidebar()`+`refreshGlobalStatus()`；closeConnection(1624/1625) 也调。轮询降载后不会出现新连接迟迟不出现。

9. **`_mcpCallsKey` 的 ts|len 组合在大多数场景够用**：只要是新增调用，`len` 会 +1 → key 变化 → 面板更新（除非触到 S-2/封顶+同秒的窄角）。

10. **TFTP `_tftpListKey` 含每个 transfer 的 status/bytes → 传输进度能实时重建**；进行中的传输另有 1s 轮询刷新，不脏时零重排。

11. **`refreshSidebar` `else` 分支的 `CSS.escape(pid)` 防注入**：pid 为后端生成（COMx / ssh:host:22），`CSS.escape` 已包，`data-close` attribute selector 安全。

12. **历史加载期间 rAF flush 数据不会重复**：`_writeQueue` 数据在 flush 时读后即清空，不残留，无重复渲染。

## 结论
- **必须修**：P1-1（后台无界堆积/巨量 write 卡顿）、P1-2（关闭时队列丢命令）——这两项是本次性能改动引入的真实行为回归。
- **建议修**：P2-1（暂停瞬间丢一帧）、P2-2（同秒调用面板陈旧）、P2-3（高亮上限缩水说明）。
- **性能权衡**：P3-1 空闲 CPU x10 是绕不开的代价，换取 200ms→20ms 延迟，需按"常连空闲监控"多数派场景权衡，建议改判空路径降频。
- 其余为文档/一致性/结构性脆弱，非当前功能破坏。
