## N1【P1】扫描粒度：终版方案与 W-答复互相矛盾

三份文档给出三种说法：

| 文档 | 位置 | 说法 |
|---|---|---|
| 终版设计方案 | §一 决策表第 12 行 | 「顶层 **+ 一级子目录**；用性能换准确（用户定调）」 |
| 终版设计方案 | §11.1 | 「**顶层 + 一级子目录**（用户定调：用性能换准确）」 |
| 终版设计方案 | §13 改动清单 | 「`recommend_scope`（全量磁盘扫描 **+ 一级子目录**）」 |
| **内网答复 W1** | §1.2 / §1.4 | 「**完整扫描**顶层 N 个目录的**子树**」「不能复用 `shallow_probe`，必须**全量遍历**」 |

**问**：推荐器到底扫到哪一层？

| 方案 | 含义 | 数据准确性 | 耗时 |
|---|---|---|---|
| A. 顶层 + 一级子目录 | 只数顶层目录和它的一级子目录各自的三元组 | 顶层数据是**自己不含子目录**的？还是**含全部后代**的？ | 快 |
| B. 完整子树 | 对每个顶层目录完整递归 | 准确 | 六平台 18~48 秒 |

**这是两种完全不同的实现**。若按 A，`kernel` 目录的三元组只统计 `kernel/` 下一层文件，
不含 `kernel/kernel_sdk/` 的数万文件——**L3 判据会用错误的数据**。

**我倾向 B（完整子树）**，理由：

1. 六平台数据（`census_new.txt` 等）就是**完整遍历**得来的，规则验证基于它
2. 若用 A，规则在真实数据上无法复现
3. 18~48 秒的代价内网已确认可接受

**请确认采用 B，并明确「一级子目录」是否只在 UI 上展示（作为树节点），
而不参与推荐判据。**

## N3【P1】点开头目录的剪枝规则，与新需求冲突

终版方案 §三：

```
目录名以 "." 开头                        → 剪枝
```

但**现有代码明确不剪**（`nav_index.py` 的 `_keep_dir`）：

```python
def _keep_dir(name):
    # a398（审计#23）：不跳通用点目录——.libs/.pio 里的 .o/.cmd 是合法
    # 产物（旧版就没跳）；点目录的 ctags 语义在 files.txt 写出端过滤
    return name.lower() not in _skip
```

**a398 审计 #23 已经踩过一次坑**：`.libs` / `.pio` 里有合法 `.o`/`.cmd`，
剪掉会导致产物推导失效。

**问**：v2 的「点目录剪枝」如何与「`.libs`/`.pio` 是合法产物源」共存？

内网 v2 评审时曾提出过（§4.3）：

> 点目录**在 `whitelist` 状态下**作为产物输入保留（读 `.cmd/.o`，文件不进 tags）

**但终版方案 §三 把这条例外删掉了**，变成「一律剪枝」。

**我建议恢复例外**：

```python
def _keep_dir(name, rel):
    if name.lower() in _skip:
        return False
    if name.lower() in _TMP_NAMES:          # 新增：tmp/temp/tmpdir/tempdir
        return False
    if name.startswith("."):
        # 点目录：whitelist 状态下保留（产物输入），其余剪
        st = state_of(rel) if state_of else None
        return st == "whitelist" or _in_artifacts(rel)
    if state_of and state_of(rel) == "off" and not _in_artifacts(rel):
        return False
    return True
```

**请确认是否接受这个调和方案。**

## N4【P1】`artifact_roots` 只取 `linux`/`uboot` 包 —— 与「不落东西」定调冲突

内网 W4 §4.4：

> 用户定调（本轮）：只设成 `sbuilder/output/build/linux` 和 `uboot`
> （有用户源码的那两个）。

**但你的定调原文是「白名单要对编译物递归全面，不要落东西」。**

数据支持内网的判断：62 个包里只有 `linux`（3246 `.cmd` → kernel）和
`uboot`（475 → uboot）指向外部源码，其余包（busybox 407、optee 911 等）
都是**包内副本**，即使扫了也不会映射回用户源码。

**但反过来看**：`optee-head` 有 911 个 `.cmd`，若用户确实想跳转 optee 源码呢？
目前 `sbuilder/output/build/optee-head` 被 `off` 剪枝，用户就完全看不到这些符号。

**三个选项**：

| 方案 | artifact_roots | 代价 | 完整性 |
|---|---|---|---|
| A. 只 linux+uboot（内网建议） | 2 个包 | 2 秒 | 漏 optee/busybox 等 |
| B. 全部 62 包 | `output/build` | +20 秒 | 完全 |
| C. 全部包，但 `.cmd` 无法映射到收录集的自动丢弃 | `output/build` | +20 秒 | 完全，且不污染 |

**我倾向 C**：`_parse_cmd_file` 的 `source_roots` 映射本来就会过滤掉无法映射的 `.cmd`
（内网 W4 §4.4 备选方案里也提到了）。多 20 秒换「不落东西」，符合你的定调。

**但 20 秒 × 每次建库是真实成本。** 请定夺。

## N5【P2】`cmd_ratio` 可以超过 100%？

内网 W2 数据里：

|---|---|---|---|---|
| H11 | modules | 457 | 607 | **132.82%** |

**问**：这是数据错误还是正常现象？

可能原因：`.cmd` 文件数 > 源文件数，说明有源文件被多次编译（多配置/多目标）

**建议**：UI 上 `cmd_ratio` 的显示封顶为 `100%+`，或标注「（含外部源引用）」。

# 三、关于内网 W-答复里的两处，我需要补充说明

## 3.1 W1 §1.5「L0/L1 短路优化」——赞同，但有一个前提

内网建议：先判 L0/L1（3 次 stat / 0 次 I/O），只对需要 L3 的目录全扫。

**建议**：L0/L1 命中的目录，UI 上显示「按规则推荐（未扫描）」+ 一个「查看详情」
按钮，点击后才扫描。这样默认路径快，需要时也能看数据。

**请确认是否接受。**

## 3.2 W4 §4.2「推荐器不扫 artifact_roots 的 `.cmd`」——确认

内网明确指出：若把 `sbuilder/output/build/linux` 的 3246 个 `.cmd` 算进 `sbuilder`，

**这是对的**。推荐器只统计**真实源码目录**，`artifact_roots` 的 `.cmd`

**但要补一条**：`sbuilder` 的 `src` 应该算多少？
内网 W4 §4.2 写 `src = 783（sbuilder 自己的源码）`——这个 783 是从哪来的？
`sbuilder` 目录本身（不含 `output/`）的源码数吗？

若 `sbuilder` 判 `off`，`src` 多少都不影响判定（L0 已命中）。
但 UI 上要显示「783 源」，需要有统计口径。

**请确认**：`off` 目录的三元组是否也要统计（用于 UI 展示）？
若要，`sbuilder` 的统计范围是「`sbuilder/` 下全部」还是「`sbuilder/` 但排除 `output/`」？
