# 一、W1【P0 阻塞】推荐器统计口径与「2~3 秒」承诺冲突

## 1.1 矛盾

| 来源 | 说法 |
|---|---|
| 合并稿 v3 §5.1 | 「只 listdir **2~3 层**，不读文件内容、不遍历全树。目标 SMB **2~3 秒**」 |
| 内网 Q1 的 L2/L3 规则 | 需要每个目录的**精确** `src` / `o` / `cmd` / `code` 计数 |
| 内网《实测数据汇总》§十 | G10 kernel 3.2 万源文件 **9.4 秒**；G10 sbuilder 全树 **22.0 秒**；E13 sbuilder **27.9 秒** |

**精确计数 `src` 必须遍历该目录整棵子树**（`os.walk` 或等价），无法在 2~3 层内得到。
六平台数据本身就是内网「磁盘完整遍历（含 tmp 剪枝）」的结果——**不是** 2~3 层浅扫。

所以：**v3 §5.1 的「2~3 秒」与内网 L2/L3 规则不能同时成立。**

## 1.2 请内网确认采用哪种

| 方案 | 推荐器耗时 | 规则 | 代价 |
|---|---|---|---|
| **A. 完整扫描顶层 N 个目录的子树** | G10 约 32 秒（kernel 9.4 + sbuilder 22） | L2/L3 精确 | 用户点「手动配置」后要**等半分钟** |
| **B. 浅扫 + 标记「需精确统计」** | 2~3 秒 | 先出粗略推荐，用户点「精算」再扫 | 多一次交互 |
| **C. 浅扫 + 结果缓存** | 首次 2~3 秒（L1/L2 粗判），后台慢慢精算 | 先出树，逐目录回填 | 实现复杂，但体验最好 |

**我倾向 A**，理由是：用户点「手动配置」这个动作本身就是「我要认真配」，
等 30 秒可接受；且六平台数据就是全扫得来的，规则验证也基于全扫。

**但六平台里 G10 sbuilder 单目录 22 秒**——若用户有多个这样的顶层目录，
总耗时会到分钟级。**请确认内网实测的「六平台全顶层扫描总耗时」是多少**
（不只是单个目录的耗时）。

## 1.3 如果采用 A，需要进度反馈

现有 `shallow_probe` 是「能下结论就返回」（`hits >= 60` 早退），
精确统计不能用它。需要：

```
推荐器扫描：正在统计 <目录名>…  (3/8，已用 12s)
```

否则用户会以为卡死。

# 三、W3【P1】`code` 与 `src` 的判定口径

内网 Q1.2 定义：

```
src  = 源文件数，后缀 ∈ .c .cpp .cc .cxx .s，不含头文件
code = 代码文件数，含 .h .hpp .hh
```

**问题**：

1. `src` 的清单**没有 `.S`（大写）**，但现有代码 `CODE_EXTS` 含 `.S`（a398 P0-4
   明确记录：不含 Asm 时 850 个 `.S` 零 tag，entry.S/head.S 全丢）。
   六平台数据里 `kernel` 的 `src` 是否含 `.S`？
   - 若含 → Q1.2 的清单漏了 `.S`
   - 若不含 → kernel 的 `src` 会被低估（内核有大量 `.S`），`cmd_ratio` 会被高估

2. `code` 是否也包含 `.S` / `.s`？是否包含 `.py` / `.js` / `.ts` 等非 C 语言？
   - 现有 `CODE_EXTS` 含 `.py .js .mjs .cjs .ts .java .go .rs`
   - 若 `code` 只算 C 系，那么「顶层同时有 `src/` 与 `inc/` 的 MCU 工程」
     若还有 Python 脚本目录，会被 L2.1 判成 `code == 0 → off`

3. **`.h` 在 `src` 里不算**，但 `cmd` 的分子是 `.cmd` 文件数——G10 的
   `sbuilder/output/build/linux` 有 3246 个 `.cmd`，对应的 `src` 如果用
   「包内相对路径」算，是 2300 个（另 945 解析失败）。**`src` 是磁盘上的实际
   `.c` 文件数，还是 `.cmd` 里解析出的源文件数？**

这三点会直接影响 L3 的比值结果，请明确。

# 四、W4【P1】`artifact_roots` 目录的 `.cmd` 归属与 `src` 计数

Q10.3 说：

> `artifact_roots` 扫到的 `.cmd` **必须进 `compiled`**——这是「仅产物源」的价值所在

**问题**：那这些 `.cmd` 对应的源文件，**算进哪个目录的 `src`？**

以 G10 为例：

- `kernel/` 有 32,594 个源、3,246 个 `.cmd`
- `sbuilder/output/build/linux` 也有 3,246 个 `.cmd`，指向**同一个** `kernel/kernel_sdk/*.c`

**推荐器统计时**：

| 口径 | `kernel` 的 `src` | `kernel` 的 `cmd` | `cmd_ratio` | 判定 |
|---|---|---|---|---|
| 口径 1：各算各的（重复计数） | 32,594 | 3,246 | 9.96% | whitelist |
| 口径 2：只算真实目录 | 32,594 | 3,246 | 9.96% | whitelist |
| 口径 3：`sbuilder` 的 `.cmd` 归到 `kernel` | 32,594 | 6,492 | 19.92% | whitelist |

三种都判 whitelist，**但 `sbuilder` 自己呢**？

- 若 `sbuilder` 的 `.cmd` 被算进自己的统计：`sbuilder` 的 `src` ≈ 0（源码在 kernel），
  `cmd` = 3246 → `cmd_ratio` 无穷大 → L3 走 `o_cmd_ratio` → 可能误判
- 若 `sbuilder` 的统计**不含** `artifact_roots` 里的 `.cmd`：`sbuilder` 的
  `src` 和 `cmd` 都只算 `sbuilder` 自己的 → 可能 L2.3（无产物 → full）

**请内网明确推荐器统计的三条口径**：

1. `artifact_roots` 目录里的 `.cmd`，归给**产物源目录**还是**源文件所在目录**？
2. 是否存在**跨目录重复计数**（同一 `.cmd` 被算两次）？
3. `sbuilder` 这类「自身无源码、只有产物」的目录，推荐器应该给出什么状态？
   （我理解应该是 L0 规则直接命中 → `off` + `artifact_roots`，但请确认
   L0 的判据 `Config.in` + `package/` + `output/` 在 G10 上是否真的命中）
