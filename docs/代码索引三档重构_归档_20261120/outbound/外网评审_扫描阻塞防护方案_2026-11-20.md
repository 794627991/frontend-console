回复方：外网（实施方）

对应：`扫描阻塞防护方案_20261120.md`

## 零、总体结论

方向完全正确，用户的四条硬约束（180s 硬超时 / 超时放弃 / 补 worker / 上界 16）
必须实现。

**但第 ③ 层的核心判据存在致命逻辑缺陷**——内网自己诊断出的是「慢」而不是「卡」，
却设计了一个只能识别「卡」的方案。**按现方案实现，G10 那个 26 分钟的问题不会被修复。**

下面 §一 讲清楚，§二 给修正方案，§三~§五 是其余评审意见。

# 一、【P0】第 ③ 层判据无效：目录级推进识别不了「慢」

## 1.1 缺陷

内网 §3.2.1 的设计：

```python
for r, ds, fs in os.walk(sub, onerror=_on_err):
    _cur_d[worker_name] = (r, time.time())    # 每进入一个目录就刷新
```

判据是「**180 秒没有进入新目录** → 判超时」。

内网自己在 §1.5 实测的数据：

```
hikudev-head: 已扫 2000 个文件 = 85.4 秒
§9.2: 60 秒内只处理了 893 个目录
```

**893 个目录 / 60 秒 = 每分钟 893 次时间戳刷新。**
`_cur_d` 的时间戳**永远不会超过 0.07 秒**，更别说 180 秒。

**这个缺陷会让第 ③ 层完全失效**：`hikudev-head` 会被完整扫完（估计 26 分钟），
看门狗一次都不会触发，与现状一模一样。

## 1.2 根因：内网诊断对了，方案设计错了方向

内网 §1.6 的排查表已经准确指出：

> **真实原因**：`hikudev-head` 里的 sysfs 自链，环防护能拦但**很慢**

§二 的表格也写了：

> 现有第 ③ 层的缺陷：`hikudev-head` 的问题不是「无产出」，而是「**产出极慢**」

**但 §3.2.1 的方案仍是「无推进就超时」**——这恰恰是内网自己证明无效的判据。
只是把粒度和阈值从「文件级 120s」换成「目录级 180s」，问题性质没变。

## 1.3 用户定调的准确理解

用户原话：

> 如果 180s 还卡在一个目录，直接不管这个目录

措辞是「**卡在一个目录**」，字面可以读成「长时间停留」。但结合 G10 的实际现象
（26 分钟处理 13/62 个包），用户要解决的问题是「**一个包扫太久拖垮整体**」，
不是「某一行代码挂死」。

**建议理解为**：以**任务单元**（不是目录）为单位计时。

# 二、【P0】修正方案：任务单元级超时（软放弃）

## 2.1 核心思想

`_walk_files` 的任务单元是 `work_q` 里的一个 item（一个种子子树）。
现有代码 `sub = work_q.get_nowait()` —— **一个 item 就是一个可独立放弃的单元**。

改为：

```python
# 每个 worker 处理一个 item 时记录开始时间
_sub_start = {}   # worker_name -> (item_sub, 绝对路径, 起始时间)
```

看门狗判据：**「该 worker 处理同一 item 超过 180 秒」**，而不是「没进新目录」。

```python
for name, (sub, t0) in list(_sub_start.items()):
    if now - t0 < _STALL_LIMIT:
        continue
    # 超时：放弃该 item（该子树）
    ...
```

**效果**：
- `hikudev-head` 作为一个 item，180 秒后**整棵子树被放弃**（含已扫了一半的部分）
- 其他包（0.3~2 秒）完全不受影响
- 这与用户说的「直接不管这个目录，其他继续」语义一致

## 2.2 粒度选择：为什么用 item 而不是「目录」

| 粒度 | 单元 | hikudev-head 的表现 | 问题 |
|---|---|---|---|
| 文件级（现状） | 每个文件 | 一直有产出 → 永不触发 | 已证明无效 |
| 目录级（内网方案） | 每个目录 | 每分钟 893 次刷新 → 永不触发 | **仍然无效** |
| **item 级（本方案）** | 一个种子子树 | 180 秒时被放弃 ✅ | 子树可能较大，误伤范围稍大 |

**item 粒度的代价**：若一个种子子树里有 5000 个正常目录 + 1 个异常目录，
整棵子树会被放弃（而不是只放弃异常目录）。但这个代价是**可接受且可见的**：
`stats["timeout_dirs"]` 记录的是被放弃的 item 路径，用户能看到「跳过的是
`sbuilder/output/build/hikudev-head`，不是整个 sbuilder」。

**关键**：现有代码的 seeds 已经是「L1 子目录（不足 8 个 worker 时拆到 L2）」，
所以 item 粒度天然是「一级或二级子目录」，不会粗到整个顶层。

## 2.3 更细的改进（可选，P2）

若担心误伤，可增强为「item 级超时 + 子树细分重试」：

1. 第 1 次超时：放弃该 item，记录 `timeout_dirs`
2. 建库结束后，用户点「重试这些目录」→ 把该 item 的子目录重新入队（粒度降一级）
3. 仍超时则再降一级，直到单目录

但这会让实现复杂。**建议先做 §2.1 的简单版**，用户看到「跳过了 hikudev-head」
就够了——他要的正是「别卡死」，不是「一定要扫到 hikudev-head」。

## 2.4 已被做完一半的子树如何处理

`hikudev-head` 在 180 秒时已经产出了 2000+ 文件进 `out_q`。这些文件已经进了
`all_rels`。**放弃时不回滚**——已扫的部分保留，只是不再继续扫。

理由：回滚需要在消费侧维护「本 item 已产出文件列表」，成本高且收益小。
部分收录的结果是「该目录下的代码不全」，与「完全跳过」相比差异不大。

**但要记录清楚**：`stats["timeout_dirs"]` 存 `{rel, scanned_files, elapsed}`，
用户能看到「跳过了 hikudev-head，已收录 2000 个文件中的部分」。

# 三、【P1】`_loop_prune` 阈值 >3 → >2：我不建议改

内网 §3.1 提议把阈值从 >3 收紧到 >2。**我建议先不做**，理由：

## 3.1 风险：误剪正常深层目录

阈值 >2 意味着「同一段名重复 3 次即剪」。正常工程的合法路径可能命中：

- `kernel/drivers/<a>/drivers/<b>/`（drivers 出现 2 次，安全）
- 但 `arch/arm/plat-xxx/arch/arm/...` 这类跨层复用段名的情况会到 3 次
- 企业工程里 `src/.../src/.../src/` 也有可能（三层嵌套模块）

内网 §二 表格说「阈值 >3 有效但慢」，**没有给出 >2 的误剪实测数据**。
在 G10/H8/H11 六个平台上验证「>2 不误剪」之前，改动风险大于收益。

## 3.2 收益有限

即使改成 >2，`usb3\driver\usb3\driver\usb3\driver\...` 仍要扫到第 3 层才剪。
内网实测「前 3 层白扫」——改成 >2 只省 1 层，**无法解决 26 分钟问题**。

真正解决靠 §二 的 item 级超时。**环防护留给第 ① 层，不要在两处同时改。**

## 3.3 如果内网坚持，请先提供

- 六个平台在 >2 阈值下的收录文件数对比（是否有下降）
- 至少一个「正常工程路径段名重复 3 次」的检查结果

# 四、【P1】`_is_sysfs_like` 的判据有误剪风险

内网 §3.3：

```python
_SYSFS_PATH_SEGS = {"sys", "proc", "dev"}
def _is_sysfs_like(rel_l):
    segs = rel_l.split("/")
    for i, s in enumerate(segs):
        if s not in _SYSFS_PATH_SEGS:
            continue
        if i == 0 or (i > 0 and segs[i - 1] in ("test", "tests")):
            return True
    return False
```

## 4.1 问题 1：首段是 `dev` 的工程会被整枝剪掉

很多嵌入式工程根目录就叫 `dev`（development 缩写），或者是
`dev/` 存放开发中代码。**首段命中就剪**会误伤。

**建议**：首段规则收紧为「首段是 `sys` 且存在 `test/` 兄弟目录」，
或者干脆**只保留「前一段是 test/tests」这一条**。

## 4.2 问题 2：`test/sys` 的判据不够

G10 的实际路径是 `test\sys\devices\PAFOHD~7\...`。

按内网的规则：`segs[0] = 'test'`，`segs[1] = 'sys'`，`i=1`，
`segs[0] == 'test'` → 命中 ✅。

**但如果是 `sbuilder/board/xxx/test/sys/...` 呢？**
`segs[-2] = 'test'`，`segs[-1] = 'sys'` → 命中 ✅。规则没问题。

**真正的问题**：`test/sys` 在**任何工程**里都可能是合法测试代码目录
（比如某模块的 `test/sys` 是测试 sysfs 读写功能的测试代码，有真实 `.c` 文件）。

**建议改为结构判据**：只有当 `test/sys` 下**没有 `.c`/`.h` 文件**、
且**存在大量短名目录（8.3 格式如 `PAFOHD~7`）**时才判 sysfs。
但这需要扫描，成本高。

**我倾向**：把 `_is_sysfs_like` 做成**可选开关**（默认关），
并在建库汇总里报告「疑似 sysfs 目录（已按普通目录扫描）」，
让用户自己决定是否加入 `exclude_paths`。

理由：`sys`/`proc`/`dev` 是合法目录名，硬剪的风险大于收益；
而 §二 的 item 级超时已经能兜住真正的问题。

# 五、【P1】`_cur_d` 结构变更的连带影响

内网 §3.2.4 说 `_cur_d` 从 `thread_name -> path` 改成 `thread_name -> (path, ts)`。

**但按 §二 的修正，`_cur_d` 的结构不用改**——item 级超时只需要
`_sub_start[worker] = (sub, t0)`，`_cur_d` 保持原样（用于停滞告警显示当前目录）。

这样连带改动从「改 3 处读取 + 1 处写入」降到「新增 1 个 dict」，
风险小很多。

# 六、【P1】补充三处遗漏

## 6.1 worker 被摘除后的 `_active` 计数

内网 §3.2.3 的 `finally` 里：

```python
with _dl:
    dead = me in _dead_workers
...
if not dead:
    _active[0] -= 1
```

**问题**：看门狗摘除 worker 时（§3.2.2 第 ② 步）已经 `_active[0] -= 1`，
worker 自己在 `finally` 里再判 `dead` 跳过减 1 —— 逻辑正确。

**但有一个窗口**：worker 恰好在看门狗判定「超时」与「加入 `_dead_workers`」
之间完成了该 item 并进入下一个 item —— 此时它被「宣告死亡」但实际还活着。

**后果**：`_active` 少减一次（看门狗减了，worker 又减）→ 提前触发 DONE。

**修复**：改用「死亡标记 + 世代号」双重检查：

```python
_sub_start[me] = (sub, time.time(), gen)   # gen 是每次取 item 自增
# 看门狗判定超时时记录 gen
_dead_workers[me] = gen
# worker 退出时对比 gen，不一致说明它已经换 item 了，不算死亡
```

## 6.2 `out_q` 满时 worker 卡在投递循环

现有代码：

```python
while True:
    if _abandoned[0]:
        return
    try:
        out_q.put((r, fs), timeout=1.0)
        break
    except _q.Full:
        continue
```

**这个循环里没有检查 `should_cancel`**。若消费侧停止消费（用户取消），
worker 会卡在这里直到 `_abandoned` 被设置。这是一个**现已存在的**问题，
本次改造应顺手补上：

```python
while True:
    if _abandoned[0]:
        return
    if should_cancel and should_cancel():   # ← 新增
        return
    ...
```

## 6.3 看门狗自身的清理

内网 §3.2.2 的 `_watchdog()` 用 `_stop_wd.wait(_WD_TICK)`，但没有看到
谁调用 `_stop_wd.set()`。

**必须补**：`_walk_files` 的 `try/finally` 里加 `_stop_wd.set()`，
否则每次建库都泄漏一个看门狗线程（daemon 线程会随进程退出，但
同一进程内多次建库会累积）。

# 七、【P2】关于「推荐器复用同一套机制」

内网 §5.3 说推荐器扫描也用同一套。**但推荐器的任务单元不同**：

- 建库：`work_q` 里是种子子树（L1/L2）
- 推荐器：需要对**顶层每个目录**做完整三元组统计（`src`/`o`/`cmd`）

**若推荐器也按 item 级超时，问题会更大**：若 `sbuilder` 是一个 item，
180 秒超时会把整个 `sbuilder` 的统计放弃 → 推荐结果缺数据。

**建议**：推荐器的超时单元应该是**顶层目录内部的一级子目录**（即拆细），
或者干脆给推荐器一个**独立的、更大的超时**（如 300 秒/顶层目录）。

这与我在上一份回复里 W1 提的「推荐器全扫要 32 秒起，可能到分钟级」直接相关。
