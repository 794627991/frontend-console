## 零、用户定调（硬性要求）

> 我们程序对任意目录如果存在阻塞，必须增加硬超时，绝对不允许出现卡死在一个目录出不来的情况。
>
> 如果 180s 还卡在一个目录，直接不管这个目录，其他继续，不能阻塞整体建库推进。
>
> 每次卡死补 1 个 worker，总线程数上界设个保护（如最多补到 16 个），防无限增长。

**四条硬约束**：
1. 任意目录阻塞必须有硬超时（180 秒）
2. 超时目录直接放弃，其余继续
3. 卡死补 worker，保持吞吐
4. worker 总数上界 16，防溢出

### 1.4 深入定位：sysfs 自链环

对 `hikudev-head` 单独诊断（逐目录打印耗时），发现路径：

```
test\sys\devices\PAFOHD~7\0F0C1Z~W.0\usb3\driver\usb3\driver\usb3\driver\
usb3\driver\usb3\driver\usb3\driver\usb3\driver\usb3\driver\usb3\driver\
usb3\driver\usb3\driver\usb3\driver\usb3\driver\usb3\driver\usb3\driver\
usb3\3XXZ5N~K.0\bus\drivers\usb\3-1\power
```

**`usb3\driver\usb3\driver\...` 无限递归。**

这正是 `nav_index.py` 注释里记录过的问题（a398 P0-1）：

> SMB 把 sysfs 自链符号链接展成无 reparse 标记的实体目录（内网报告 §2.1
> 实测单链 56 层多分叉组合爆炸，深度截断只砍最深分支、同层宽度照爆）

`test/sys/` 是 Linux sysfs 的导出快照，符号链接形成的环在 SMB 上变成了实体目录。

### 1.5 现有环防护的有效性验证

现有 `_walk_files` 的 `_loop_prune`（a398 a415R2）：

```python
def _loop_prune(r, sub):
    if r == sub:
        return False
    if len(r) > 480:              # 绝对路径长度上限
        return True
    tail = r[len(sub) + 1:] ...
    segs = tail.split(os.sep)
    if len(segs) <= 3:
        return False
    _c = {}
    for seg in segs:
        _c[seg.lower()] = _c.get(seg.lower(), 0) + 1
    return max(_c.values()) > 3   # 同一段名重复 >3 次即剪枝
```

**实测结果**（用现有 `_walk_files` 扫 `hikudev-head`）：

```
已扫 2000 个文件 = 85.4 秒
```

**结论**：
- ✅ 环防护**生效**（不会无限递归）
- ❌ 但**速度仍然极慢**（2000 文件 85 秒）

**为什么慢**：环防护的阈值 `>3` 只在同一段名重复 4 次时才剪。
`usb3\driver\usb3\driver\usb3\driver\...` 前 3 次都要扫，而每个 `driver` 目录
下又有多个分叉（`usb3`、`bus\drivers`、`3-1`、`3XXZ5N~K.0`），
组合爆炸。

**a398 注释已经预见过这个问题**：

> 同名目录在一条路径上重复 >6 次即判环剪枝（报告 §8.1 原方：depth>6 才启用
> 计数，正常嵌套名不重复不误伤）

但当前实现是 `>3`，仍不够。

### 1.6 为什么这次排查花了这么久

| 原因 | 说明 |
|---|---|
| 假象 1 | 我的普查脚本没实现环防护，自己测试时无限递归 |
| 假象 2 | 同时跑多个 Python 进程争抢 SMB，互相拖慢 |
| 假象 3 | 我的脚本用 `seen` 元组累加，导致 O(n²) |

**教训：排查时必须隔离变量。** 后续诊断改用「子进程 + 硬超时」，一次定位。

## 二、现有防护的三层结构（评估）

| 层 | 机制 | 是否有效 | 缺口 |
|---|---|---|---|
| ① 环防护 | `_loop_prune` 阈值 >3 | 有效但慢 | 阈值宽松，前 3 层白扫 |
| ② 点目录/`_SKIP_DIRS` | 名字匹配 | 有效 | 不含 `sys` |
| ③ 停滞检测 | 120s 告警 / 300s 失败 | **弱** | 只告警不中断；有产出就不算停滞 |

**现有第 ③ 层的缺陷**（关键）：

```python
# 现有逻辑大意
if 距上次产出 > 120s: 告警
if 距上次产出 > 300s: 判定失败
```

`hikudev-head` 的问题不是「无产出」，而是「产出极慢」（2000 文件/85 秒）。
**只要一直在产出，就永远不触发停滞检测。**

这就是为什么它看起来像卡死，但 300 秒阈值也没救。

## 三、方案设计

### 3.1 总览：三层防护（新增第 3 层替换现有第 ③）

| 层 | 机制 | 作用 | 改动 |
|---|---|---|---|
| ① 环防护 | `_loop_prune` 阈值收紧 >3 → **>2** | 更早剪掉自链 | 改 1 行 |
| ② 已知问题路径剪枝 | `test/sys/`、`sys/` 类路径模式直接剪 | 已知问题不进扫描 | 新增 |
| ③ **单目录硬超时 + worker 补偿** | 180 秒无「目录级推进」即摘除该 worker，补新 worker | **兜底任何未知阻塞** | 新增 |

### 3.2 第 ③ 层的核心设计

#### 3.2.1 判定「阻塞」的指标：**目录级推进**，不是文件级

现有逻辑是「无产出（文件数）」→ 但 `hikudev-head` 持续有文件产出。
新逻辑改为「**每扫完一个目录就刷新时间戳**」：

```python
for r, ds, fs in os.walk(sub, onerror=_on_err):
    _cur_d[worker_name] = (r, time.time())    # 每进入一个目录就刷新
```

**为什么用目录级而不是文件级**：
- 文件级：`hikudev-head` 每秒产 20 个文件，永不触发
- 目录级：`os.walk` 进入新目录才刷新。若在某个深路径下 `scandir` 挂住，时间戳停止刷新

**但仍有盲区**：`os.walk` 在一个目录内 `scandir` 返回大量 entry 时，
时间戳不刷新，但目录本身没卡。这类情况会被误判。

**缓解**：
- 180 秒阈值足够宽松（正常目录哪怕有 10 万个 entry，`scandir` 也就几秒）
- 误判的代价是「跳过该目录」，记录到 `timeout_dirs`，用户可见可重试
- **宁可误判，不可卡死**（用户定调）

#### 3.2.2 看门狗实现

```python
_STALL_LIMIT = 180.0        # 单目录无推进上限（用户定调）
_WD_TICK = 5.0              # 看门狗检查间隔
_MAX_WORKERS = 16           # worker 总数上界（用户定调）

_dead_workers = set()       # 已摘除的 worker 名
_dl = threading.Lock()
_stop_wd = threading.Event()

def _watchdog():
    """监控 worker 停滞，摘除卡死的并补新 worker。"""
    while not _stop_wd.wait(_WD_TICK):
        if _abandoned[0]:
            return
        now = time.time()
        # 快照，避免遍历时被 worker 修改
        for name, (d, t) in list(_cur_d.items()):
            if now - t < _STALL_LIMIT:
                continue
            with _dl:
                if name in _dead_workers:
                    continue
                _dead_workers.add(name)
            rel = os.path.relpath(d, root).replace(os.sep, "/")
            # ① 记录超时目录（用户可见）
            with _alock:
                stats.setdefault("timeout_dirs", []).append(rel)
                stats["timeout_pruned"] = stats.get("timeout_pruned", 0) + 1
            # ② 从活跃表摘除
            _cur_d.pop(name, None)
            with _alock:
                _active[0] -= 1
                _last = _active[0] == 0
            say("  ⚠ 目录扫描超时 %ds，已跳过：%s" % (int(_STALL_LIMIT), rel))
            # ③ 如果还有任务且未达上界，补 worker
            with _alock:
                total = len(_live_workers)
            if total < _MAX_WORKERS and not work_q.empty() and not _abandoned[0]:
                _spawn_worker()
            if _last and not _dead_workers_alive():
                try:
                    out_q.put((_DONE, None), timeout=5.0)
                except Exception:
                    pass
```

#### 3.2.3 worker 侧配合

**关键**：卡死的 worker 无法被 kill（`os.scandir` 阻塞），只能「宣告死亡」。

```python
_worker_seq = [0]           # 全局自增，给新 worker 编号
_live_workers = set()       # 当前存活的 worker 名

def _spawn_worker():
    with _alock:
        _worker_seq[0] += 1
        name = "nav_walk_%d" % _worker_seq[0]
        _live_workers.add(name)
    t = threading.Thread(target=_worker, name=name, daemon=True)
    t.start()

def _worker():
    me = _th.current_thread().name
    try:
        while True:
            try:
                sub = work_q.get_nowait()
            except _q.Empty:
                break
            try:
                for r, ds, fs in os.walk(sub, onerror=_on_err):
                    # 每进入一个目录刷新时间戳
                    _cur_d[me] = (r, time.time())
                    ...
                    # 循环内也检查取消
                    if should_cancel and should_cancel():
                        return
                    ...
            except Exception as e:
                _err[0] = e
    finally:
        with _dl:
            dead = me in _dead_workers
        try:
            _cur_d.pop(me, None)
        except Exception:
            pass
        with _alock:
            _live_workers.discard(me)
            if not dead:
                # 正常退出：自己减 _active
                _active[0] -= 1
                _last = _active[0] == 0
            else:
                # 看门狗已代减，这里不再动 _active
                _last = _active[0] == 0
        if _last:
            _send_done_with_retry()
```

#### 3.2.4 `_cur_d` 结构变更

**现状**：`_cur_d[thread_name] = r`（只有路径字符串）

**改为**：`_cur_d[thread_name] = (r, timestamp)`

需要同步修改的现有代码：
- 停滞告警段（读 `_cur_d` 打印「卡在哪个目录」）
- worker 退出时 `_cur_d.pop`

### 3.2.5 补 worker 的循环安全

**风险**：看门狗补的 worker 立刻又卡死 → 无限补。

**保护**：
1. `_MAX_WORKERS = 16` 硬上界
2. 补之前检查 `work_q.empty()`（没任务就不补）
3. 补之前检查 `_abandoned[0]`（消费侧放弃就不补）

**极端场景**：6 个 worker 卡死，看门狗补了 6 个，新补的又卡死 → 达到 16 上界，停止补。
此时剩余活跃 worker 继续处理队列，只是吞吐降低。**不会无限增长。**

### 3.3 第 ② 层：已知问题路径剪枝

```python
# 新增常量：sysfs/procfs 类路径模式（相对路径任一层命中）
_SYSFS_PATH_SEGS = {"sys", "proc", "dev"}

def _is_sysfs_like(rel_l):
    """判断是否是 sysfs/procfs 类导出目录。
    只在 test/ 或顶层直接出现时才剪，避免误伤业务模块同名目录。"""
    segs = rel_l.split("/")
    for i, s in enumerate(segs):
        if s not in _SYSFS_PATH_SEGS:
            continue
        # 前一段是 test，或它是第一个段（相对 root）→ 判 sysfs
        if i == 0 or (i > 0 and segs[i - 1] in ("test", "tests")):
            return True
    return False
```

## 四、被否决的方案（记录理由）

| 方案 | 机制 | 否决理由 |
|---|---|---|
| A. `signal.alarm` | Unix 信号中断 | **Windows 不支持** |
| B. 线程 `timeout` 强制 kill | — | Python 无法 kill 线程 |
| C. 全量单目录子进程 | 每目录一个 `Process` | 48 万目录 × 100ms = 13 小时 |
| D. 顶层目录级子进程隔离 | 每个顶层目录一个子进程 | 粒度粗（`sbuilder` 卡 = 整个 sbuilder 放弃） |
| E. `ProcessPoolExecutor` | 标准库 | 无法 kill 运行中的任务 |
| F. 完整动态线程池 | 复杂调度 | 超出需求，20 行补偿机制够用 |

**采用**：线程级「宣告死亡 + 摘除 + 补 worker」，配合环防护与路径剪枝。

**为什么可行**：卡住的线程作为 daemon 僵尸残留，**不消耗 CPU**（阻塞在 I/O）。
进程退出时自动清理。真正的资源泄漏只是几十个线程栈（每个约 8MB 虚拟内存，
但未访问的栈页不占物理内存）。
