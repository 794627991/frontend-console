## 一、需求来源

现状的收录范围模型是「单层 include 列表 + 一堆兜底路径表」，经几次修修补补后出现三类问题：

1. **白名单档被硬编码路径绑架**。`detect_scope()` 里写死了 `libs/hal_bsp`（fallback_full 整目录全收）、`libs/hal_bsp/hal_inc`（always_include）、`kernel/include`、`uboot/*/arch/*/include` 等。换一个工程形态就全部失效，只能再加一条。
2. **档位判据与用户意图冲突**。a409 的策略是「收录集内扫到任何 `.o` 就强制白名单」，实现上直接覆盖 `sc["tier"]`，连用户在 UI 上显式选的「全量」也被吃掉（a563 已修，但根因是模型没有区分「显式选择」与「自动推算」）。
3. **无法表达「这个子树全量、那个子树白名单」**。真实工程是混合的：`kernel/` 该走白名单，`tools/` 该全量，`sbuilder/output/` 该完全不进。现在只能整工程一个档，再用 `exclude_paths` / `fallback_full` 手填补丁。

用户提出的新模型（原文）：

> 1. 首先还是分为3档：白名单(严格按照白名单执行，删除一切写死路径，只允许白名单)、手动配置(允许工具推荐，工具自识别存在例如halbsp、uboot、seeboot、kernel、rootfs[errot/buildroot/sbuilder等等])、全量(全盘扫描，无视一切生成物)
> 2. 针对手动配置的细分：对于文件夹有3种状态：白名单、全量、不勾选……如果父目录勾选了白名单，则全部子目录应用父目录的属性……可以在手动针对下属子目录再进行修改，比如kernel目录下可能存在tools目录，该目录我可以改成全量或者不勾选
> 3. 关于原先自动挡：转为手动配置(配置推荐)，如果扫描阶段发现符合情况的目录架构，则弹窗建议用户选择，并列出当前配置情况(即工作树)---你直接配置好，让用户确认，用户确认后，在进行下一步

用户的补充澄清（关键，影响设计）：

> 补充：仍排除 VCS 与依赖缓存，所有没必要的隐藏文件有必要排除

> 补充：也不用太严格，白名单也不可能面面俱到，我设想中的白名单，是严格按照能够解释的文件，然后有一定扩展的，至少不要漏文件

第二条补充改变了白名单档的语义——不是「严格到推不出就报错」，而是**「可解释闭包」：能推导的必须全推，扩展链一环都不能少，宁可多收不可漏收**。

## 二、三档终态定义

| 档位 | 语义 | 判档依据 |
|---|---|---|
| **白名单** | 可解释闭包：编译单元 → 同目录头 → `#include` 递归触达（含邻近 inc 目录解析、`-I` 为空时的工程内 inc 池）→ 头文件区。**零写死路径**，但扩展链必须完整 | `.cmd` / `.o` 推导 |
| **手动配置** | 目录三态（白名单 / 全量 / 不勾）+ 子目录覆盖父级 + 检测器预填推荐 | 检测器推荐 + 用户确认 |
| **全量** | 全树收录，只排除点开头目录/文件与依赖缓存 | 无 |

原先的 `tier: "auto"` 消失。它的职责拆成两半：

- **识别能力** → 归入「手动配置」的推荐器（`recommend_scope`）；
- **判档能力** → 归入各档自身（白名单靠 `.cmd`/`.o`，全量无条件）。

「删除写死路径」的准确含义：删掉 `fallback_full` / `always_include` / `artifact_roots` 这类**硬编码路径表**，不是删掉扩展逻辑。扩展逻辑（递归 include、邻近 inc 搜索、inc 目录池）全部保留并前移为白名单档的固有行为。

## 三、数据模型 v2

```json
{
  "version": 2,
  "name": "G10 推荐配置",
  "mode": "whitelist | manual | full",
  "arch": "auto",
  "dirs": {
    "kernel":            "whitelist",
    "kernel/tools":      "full",
    "kernel/tools/test": "off",
    "rootfs/buildroot":  "off"
  },
  "exclude_names": []
}
```

### 3.1 dirs 的继承语义

- `dirs` **只存显式覆盖节点**，不展开全树（大工程目录数万，展开会爆内存和 JSON 体积）。
- 键不存在 = **继承最近的显式祖先**；一直上溯到根仍无显式值，则取 `mode` 的语义。
- 取值 `whitelist` / `full` / `off` 三者之一。

解析函数：

```python
def _resolve_dir_state(rel, dirs, default):
    """rel='' 表示根。返回 whitelist|full|off。"""
    cur = rel.strip("/")
    while True:
        v = dirs.get(cur)
        if v in ("whitelist", "full", "off"):
            return v
        if not cur:
            return default
        cur = cur.rpartition("/")[0]   # 'kernel/tools' -> 'kernel' -> ''
```

复杂度 O(目录深度)，对每个目录调用一次，无需预先展开。

### 3.2 mode 与 dirs 的关系

- `mode = "whitelist"` → 全树白名单，**忽略 `dirs`**。这就是第 1 档「纯白名单」。
- `mode = "full"` → 全树全量，**忽略 `dirs`**。
- `mode = "manual"` → 读 `dirs`；根节点的 default 为 `whitelist`（见 §八 待定项①的结论）。

### 3.3 废弃字段（v1 → v2 迁移时丢弃并记录日志）

| 废弃字段 | 原用途 | v2 中的替代 |
|---|---|---|
| `tier` | `whitelist`/`full`/`auto` | `mode` |
| `manual` | 标记手选目录 | `mode == "manual"` |
| `include` | 收录的顶层目录列表 | `dirs` 中以 `full`/`whitelist` 表达的节点 |
| `always_include` | 无条件全收的目录通配 | 对应节点设 `full` |
| `fallback_full` | 白名单低覆盖时的整目录兜底 | 对应节点设 `full` |
| `artifact_roots` | 产物根（只读 `.cmd`/`.o`） | 由 walk 自然覆盖，无需声明 |
| `source_roots` | `-I` 相对路径解析基准 | 由 walk 的自然路径覆盖 |
| `header_roots` | 头文件区通配 | 由递归 include + inc 池覆盖 |

保留 `exclude_names`（默认空数组，不再写死 `test` / `release_tmp`）。

### 3.4 v1 迁移

```python
def _migrate_v1(cfg):
    mode = cfg.get("tier") or "auto"
    if mode == "auto":
        mode = "manual"          # 旧的自动档转手动配置
    dirs = {}
    for d in cfg.get("include") or []:
        if d and d != ".":
            dirs[d] = "whitelist" if mode == "whitelist" else "full"
    for d in cfg.get("fallback_full") or []:
        dirs.setdefault(d, "full")
    for d in cfg.get("always_include") or []:
        dirs.setdefault(d, "full")
    return {"version": 2, "name": cfg.get("name") or "迁移配置",
            "mode": mode, "arch": cfg.get("arch") or "auto",
            "dirs": dirs, "exclude_names": []}
```

迁移时输出一行日志：「旧配置中的 artifact_roots/source_roots/header_roots 已废弃（v2 由自动推导覆盖）；请重新运行推荐以获得更准确的配置」。

## 四、执行语义

| 目录状态 | walk 阶段 | 收录清单 | 头文件处理 |
|---|---|---|---|
| `off` | **剪枝**，目录不进 `all_rels` | 无 | 无（若被某个白名单单元的 `#include` 命中，记一条告警计数） |
| `full` | 全量 walk | 该子树全部 `CODE_EXTS` 文件 | 全部收录 |
| `whitelist` | 全量 walk（需要拿到 `.cmd`/`.o` 才能推导） | 单元 + 同目录头 + 递归 include 触达的头 + 头文件区 | 递归解析 |

### 4.1 off 剪枝的实现位置

`_walk_files()` 已有 `excl_names` / `excl_paths` 机制，增加一个 `state_of` 回调：

```python
def _walk_files(..., state_of=None):
    ...
    def _keep_dir(name, rel):
        if name.lower() in _skip:
            return False
        if state_of and state_of(rel) == "off":
            stats["pruned_off"] = stats.get("pruned_off", 0) + 1
            return False
        return True
```

剪枝发生在 **scandir 层**，即不进入该目录、不产生任何 SMB 往返以外的开销。这是本次重构最大的性能红利——SMB 上跳过 `rootfs/`（数万文件）或 `sbuilder/output/`（buildroot 产物）可省数十秒到数分钟，目前只能靠手工填 `exclude_paths`。

### 4.2 白名单目录推不出单元时的处理

用户补充明确「不用太严格，至少不要漏文件」。因此：

- `mode == "whitelist"` 的**根档**不可推导 → 若整树零单元，**自动整树降级为 full**，并在结束时弹总览；
- `manual` 档下某个 `whitelist` 目录零单元 → **该目录降级为 full**（仅该子树），其余目录不受影响；
- 两种情况均输出日志行与结束汇总，不阻塞建库。

### 4.3 统一排除规则（三档共用，全量档不豁免）

```
目录名 / 文件名以 "." 开头            → 排除
目录名 ∈ _SKIP_DIRS ∪ exclude_names  → 排除
__pycache__ / node_modules / .pytest_cache / .mypy_cache → 排除（已在 _SKIP_DIRS）
```

现状 `_SKIP_DIRS` 已含 `.git` `node_modules` `.svn` `.hg` `.history` `.cache` `.ua` `.codegraph` `.agents` `.codex` `.vscode` `.tmp_versions` `.buildroot-ccache` `__pycache__`。

新增：**任何 `.` 开头的目录一律剪枝**（现有实现依赖 `_keep_dir` 的白名单反向判断，`_ARTIFACT_DIRS` 里的 `.pio` / `.libs` 被特意保留用来读产物）。需要在 v2 里显式区分：

- 「点开头的源码相关目录」（如 `.libs`，内含合法 `.o`）→ 仅在 `whitelist` 状态的目录下保留，且其中文件只作为产物输入、不进最终 tags 清单；
- 其余点开头目录 → 一律剪枝。

## 五、推荐器（检测器 → 推荐配置）

`detect_scope()` 改造为 `recommend_scope()`，返回 `mode=manual` 的 v2 配置（含 `dirs` 表）以及每条推荐的**理由**（用于 UI 展示）。

### 5.1 扫描深度

只 listdir **2~3 层**（顶层 + 一级子目录 + 必要时二级），不读文件内容、不遍历全树。目标耗时：SMB 上 2~3 秒。

### 5.2 规则表

规则集中在模块常量 `_SCOPE_RULES`，便于单测与维护：

| 特征（仅看目录名与浅层标记文件） | 推荐状态 | UI 理由文案 |
|---|---|---|
| `kernel/` 下有 `arch/` 或 `.config` 文件 | `whitelist` | 标准 Kbuild 内核树，可按 `.cmd` 精确推导 |
| `uboot/`、`u-boot*/`、`seeboot/`、`bootloader/` | `whitelist` | 引导程序源码，有构建产物可推导 |
| `sbuilder/output/build` 存在 | `off` | buildroot 构建产物树，只读不索引 |
| `sbuilder/.buildroot-ccache` | `off` | ccache 缓存 |
| `rootfs/` 下有 `buildroot`/`errot`/`*_build` 且带 `output/` | `off`（子层若无产物则 `full`） | 根文件系统构建树 |
| `libs/hal_bsp/` | `whitelist`（同层有 `.o`）否则 `full` | HAL 源码与接口头 |
| 顶层同时有 `src/` 与 `inc/`（或 `include/`）且全树零 `.cmd` | `full` | MCU/IDE 工程，白名单不可推导 |
| `tools/` | `full` | 工具脚本，无编译产物 |
| 顶层 `.cmd` 数量 > 0 且存在 `kernel/` | 各子树按上表；顶层其余 → `whitelist` | 混合工程 |
| 无任何特征命中 | `full` | 未识别出构建系统，建议全量 |

┌─────────────────────────────────────────────────┐
│ 收录范围配置                    已识别：Kbuild  │

交互细节：

- **三态用互斥按钮组，不用 checkbox**。三态 checkbox 在深树里需要点击循环切换，误操作率高；互斥按钮一次点击直达目标状态。
- **继承态**：显示为空心按钮 + 灰字标注「继承自 kernel」。点击任一按钮即设为显式值；右键（或长按）可「恢复继承」。
- **搜索框**过滤目录名（大工程必需，测过 G10 有上千个目录）。
- **批量按钮**作用于「已展开且可见」的节点，避免误伤未展开的深树。
- 懒加载沿用现有 `/api/nav/scope_tree`（一次一层），新增返回字段：每个目录的推荐状态、文件数、是否有子目录。

### 6.3 配置复用

确认后写入 `DATA_DIR/nav-scopes/<md5>.json`（现有 `scope_store_path`）。下次进入该工程提示：

```

[沿用] [重新推荐]
```

### 6.4 建库结束汇总

建库完成后若发生过白名单降级，在结果面板追加一行可点击的提示：

```
⚠ 3 个目录白名单不可推导，已按全量收录：[查看详情] [严格白名单重建]
```

不阻塞、不影响建库成功状态。

### 7.1 排序层适配（易漏点）

`definition()` 中的 `rank()` 有一档：

```python
0 if c["in_build"] is True else 1,      # 编译白名单
```

`in_build` 来自 `manifest.compiled`（`.cmd`/`.o` 推出的源）。混合档下，`full` 目录里的源没有 `.o` 记录，会被降权，导致真定义输给白名单目录中的同名符号。

修法：`manifest.json` 增加 `full_dirs` 列表，`in_build` 判定改为「在 `compiled` 里 **或** 路径落在某个 `full_dirs` 之下」。

### 7.2 build() 重构的风险点

现有 `final_files` 的组装是单一档位逻辑，包含 8 处兜底：

1. `_units`（编译单元）
2. `_same_h`（同目录头）
3. `_reached_rel`（递归 include 触达）
4. `_always`（always_include 无条件全收）
5. `_fb`（fallback_full 兜底）
6. `manual` 逐目录核覆盖（零单元整目录兜底 / 低覆盖告警）
7. `always_include` 展开
8. `_dot_path` 过滤

改成「按目录分组」后，第 4/5/6 项直接删除（由目录状态取代），第 1/2/3 项需要在每个 `whitelist` 目录内独立执行，第 7/8 项保留。这是本次改动最容易漏的地方，必须逐项对照测试。

## 八、待定项与当前推荐

### ① manual 档未勾选目录的默认状态

**推荐：`whitelist`**。

理由：新出现的目录按白名单处理，推不出单元会自动降全量（§4.2），不会静默丢失；若默认 `off`，工程后续新增的目录会被无声排除，用户难以察觉。

### ② 白名单降级弹窗的时机

**推荐：不阻塞，建库结束后汇总**（§6.4）。

理由：现有 `ask_tier` 中途弹窗机制需要挂起建库线程等待用户输入，代码注释中已记录卡死风险（a432：「不能用裸 evt.wait()……建库线程会永久挂起」）。改为结束后汇总，用「严格白名单重建」按钮提供反悔路径，风险更低。

## 十、需要外网评审确认的点

1. **§3.1 的继承模型**是否足够表达真实工程？是否有「父目录全量、子目录白名单、孙目录又要全量」这类三级覆盖需求，当前模型可以表达（每层一条显式记录），但 UI 交互是否够直观？
2. **§4.3 点开头目录的处理**：现状为了读 `.libs` / `.pio` 里的 `.o` 特意保留了部分点目录。v2 改为「仅在 whitelist 目录下作为产物输入保留」，是否过于激进，会否导致某些工程的产物推导失效？
3. **§7.1 的 `full_dirs` 排序适配**：混合档下「全量目录的符号 vs 白名单目录的符号」谁优先，是否需要按目录状态再分层（如白名单优先于全量）？
4. **§5.2 规则表**是否有遗漏的工程形态（如 Zephyr、PlatformIO、ESP-IDF、Rust/Cargo、CMake+ninja 独立工程）？
5. **§3.3 的字段废弃**是否需要保留一个「兼容层」让 v1 配置继续工作一段时间，还是直接强制迁移？
