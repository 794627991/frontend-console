## 二、数据模型 v2

```jsonc
{
  "version": 2,
  "name": "G10 推荐配置",
  "mode": "whitelist | manual | full",
  "arch": "auto",
  "dirs": {
    "kernel":            "whitelist",
    "kernel/tools":      "full",
    "rootfs":            "off",
    "sbuilder":          "off"
  },
  "artifact_roots": ["sbuilder/output/build"],
  "exclude_names": []
}
```

- `dirs` 只存**显式覆盖节点**，不展开全树；键不存在 = 继承最近显式祖先
- `mode` 为 `whitelist`/`full` 时忽略 `dirs`；`manual` 才读
- `mode=manual` 的根默认值 = `whitelist`

### 2.1 继承解析

```python
def _resolve_dir_state(rel, dirs, default):
    """rel='' 表示根。返回 whitelist|full|off。O(目录深度)。"""
    cur = rel.strip("/")
    while True:
        v = dirs.get(cur)
        if v in ("whitelist", "full", "off"):
            return v
        if not cur:
            return default
        cur = cur.rpartition("/")[0]
```

### 2.2 废弃字段

`tier` / `manual` / `include` / `always_include` / `fallback_full` /
`source_roots` / `header_roots` / `exclude_paths` 全部废弃。
保留 `exclude_names`（默认空数组）。

## 三、扫描阶段剪枝（三档共用，全量档不豁免）

```
目录名以 "." 开头：
    在 whitelist 目录下      → 保留（作为产物输入，读 .cmd/.o；文件不进 tags）
    在 artifact_roots 下     → 保留
    其余                     → 剪枝
目录名 ∈ _SKIP_DIRS                      → 剪枝
目录名 ∈ {tmp, temp, tmpdir, tempdir}    → 剪枝（完整名匹配）
```

`_SKIP_DIRS` 现状：
`.git .svn .hg .history .cache .ua .codegraph .agents .codex .vscode
.tmp_versions .buildroot-ccache __pycache__ node_modules`

**要点**
- `tmp` 类**完整名匹配**，不误伤 `template` / `attempt`
- `tmp` 目录**无条件跳过**，不检查里面有没有 `.cmd`（用户定调）
- 点开头**文件**（`.foo.o.cmd`）必须保留 —— Kbuild 产物清单本身是隐藏文件
- **点目录的例外**（a398 审计 #23）：`.libs` / `.pio` 里的 `.o`/`.cmd` 是合法产物，
  剪掉会导致产物推导失效。故「whitelist 状态下保留」，靠 `files.txt` 写出端的
  `_dot_path` 过滤实现「文件不进 tags」的语义

实现：

```python
def _keep_dir(name, rel):
    if name.lower() in _skip:
        return False
    if name.lower() in _TMP_NAMES:            # tmp/temp/tmpdir/tempdir
        return False
    if name.startswith("."):
        st = state_of(rel) if state_of else None
        return st == "whitelist" or _in_artifacts(rel)
    if state_of and state_of(rel) == "off" and not _in_artifacts(rel):
        return False
    return True
```

实测依据：G10 `sbuilder/output/build/boot-regbin/tmp/poifiles` 有 35,532 个文件，
占该包绝大部分，且无 `.cmd` 价值。

## 四、推荐规则（核心）

### 4.1 指标定义

对每个目录独立计算：

| 指标 | 定义 |
|---|---|
| `src` | 源文件数，后缀 ∈ `.c .cpp .cc .cxx .s`，**不含头文件** |
| `o` | `.o` 文件数 |
| `cmd` | `.cmd` 文件数 |
| `code` | 代码文件数，含 `.h .hpp .hh` |
| `o_ratio` | `src / o`（`o=0` 时记 ∞） |
| `cmd_ratio` | `cmd / src`（`src=0` 时无意义） |
| `o_cmd_ratio` | `o / cmd`（`cmd=0` 时记 ∞） |

### 4.2 规则表（自上而下，命中即停）

#### L0 — 形态先验

| 条件 | 推荐 |
|---|---|
| 目录下有 `Config.in` + `package/` + `output/`（buildroot 特征） | `off` + `artifact_roots=[<dir>/output/build]` |

**为什么用形态不用名字**：E13 的 buildroot 目录叫 `sbuilder`，但换一个工程可能叫别的。
三个标志文件/目录的组合足以识别 buildroot。

**`artifact_roots` 取全部包（用户定调 2026-11-20）**

G10 的 `sbuilder/output/build` 有 62 个包。实测只有 `linux`（3,246 个 `.cmd`）和
`uboot`（475）指向用户源码，其余（`optee-head` 911、`busybox` 407 等）指向包内副本。

曾考虑只扫 linux+uboot（约 2 秒），但用户定调「白名单要对编译物递归全面，**不要落东西**」，
最终采用**扫全部 62 个包**（约 22 秒），并增加清理步骤：

```python
# 阶段 1 结束后，清理无法映射到收录集的 compiled 条目
_compiled_pruned = {k: v for k, v in compiled.items() if k.lower() in _rel_by_l}
if len(_compiled_pruned) < len(compiled):
    say("  产物源：%d 个 .cmd 指向收录集外的源码，已丢弃"
        % (len(compiled) - len(_compiled_pruned)))
    compiled = _compiled_pruned
```

**代价**：扫描 22 秒（vs 2 秒）；因清理步骤，`manifest.json` 大小保持原状。

#### L1 — 名称先验（推荐值，用户可改）

| 条件 | 推荐 |
|---|---|
| 完整名 ∈ `{rootfs, eroot, buildroot, build_root, rootfs_build}` | `off` |
| 名字含 `zoo` / `zoos` / `zmo` | `off` |
| 完整名 ∈ `{release, release_tmp, temp_log}` | `off` |

**说明**：L1 是「经验默认值」，不是数据推导。
实测 H9/H13 的 `rootfs` cmd_ratio 为 43~44%（技术上是正常源码树），
但按用户定调推荐 off —— 这类目录装的是第三方代码，日常不跳转。
用户想索引时手动改即可。

#### L2 — 数量先验（按序执行）

| 序 | 条件 | 推荐 |
|---|---|---|
| L2.1 | `code == 0` 且 `o == 0` 且 `cmd == 0` | `off` |
| L2.2 | `code < 5` | `off` |
| L2.3 | `o == 0` 且 `cmd == 0` 且 `code >= 5` | `full` |

#### L3 — 比值判定（有产物才进入）

```
① o_ratio < 0.8                              → whitelist + 告警（增量残留嫌疑）
② o_ratio <= 2                               → whitelist
③ o_ratio > 2：
     cmd_ratio >= 3%                         → whitelist
     o_cmd_ratio > 5：
          src < 2000                         → full
          src >= 2000                        → whitelist + 强告警
     o_cmd_ratio <= 5                        → whitelist
```

#### 未命中任何规则

`full` + 提示「未识别出构建系统，建议全量」

### 4.3 设计说明

**为什么主判据是 `o_ratio` 而不是 `cmd_ratio`**

`o_ratio`（源文件/`.o`）反映「产物覆盖率」——这是白名单能不能工作的直接前提。
`cmd_ratio`（`.cmd`/源文件）只作为补充，因为内核类工程只有 5~10% 的源文件参与当前
配置的编译，比值天然偏低，但 `.cmd` 里的构建描述是完整可信的。

**`cmd_ratio >= 3%` 这条的作用**

专门纠正内核类工程的误判。Linux 内核只编译当前平台/配置，`o_ratio` 通常 10~20。
若无此条，内核会被判 `full`（数万文件全收，tags 撑到数 GB）。

六平台实测内核 cmd_ratio：
G10 9.96% / H9 10.32% / E13 7.85% / H13 8.24% —— **稳定在 7.85~10.32%**，
距 3% 阈值有 2.6 倍余量。

**为什么 `o_cmd_ratio <= 5 → whitelist` 不加绝对数门槛**

H13 的 `uboot`（5,267 源 / 39 `.o` / 50 `.cmd`，`o_cmd_ratio=0.78`）会被判 whitelist，
漏收 5,228 个源文件。但用户已确认：**该工程 uboot 编译本身失败**，39 个 `.o` 是
失败残留，不是规则问题。为保持规则简洁，不加额外门槛。

**规则的责任边界**：
> 推荐规则基于「编译产物反映真实覆盖」的假设。
> 若工程编译失败导致产物稀少，推荐值可能偏离预期。
> 用户可在三态树上看到原始数据（源/`.o`/`.cmd`/比值）并手动覆盖。

## 六、执行语义

### 6.1 目录状态

| 状态 | walk | 收录清单 | 头文件 |
|---|---|---|---|
| `off` | 剪枝（scandir 层） | 无 | 若被白名单单元 include，需强制收录 + 告警 |
| `full` | 全量 | 该子树全部 `CODE_EXTS` | 全部 |
| `whitelist` | 全量（要拿产物） | 单元 + 同目录头 + 递归 include 触达 | 递归解析 |

### 6.2 `off` 与 `artifact_roots` 正交

| 组合 | 行为 |
|---|---|
| `off`，不在 `artifact_roots` | 完全剪枝，scandir 层不进 |
| `off`，在 `artifact_roots` | 扫 `.cmd/.o`，不收源码（「仅产物源」） |
| `whitelist` | 全量 walk + 扫产物 |
| `full` | 全量 walk，不需要产物 |

实测验证 `sbuilder/output/build` 的 `.cmd` 确实指向用户源码：

| 包 | `.cmd` 数 | 源指向 |
|---|---|---|
| linux | 3,246 | `arch/arm64/hikdrvlib/*.c` → 经 `source_roots` 映射回 `kernel/kernel_sdk` |
| optee-head | 911 | 相对路径 |
| uboot | 475 | `arch/arm/cpu/armv8/*.c` |
| busybox | 407 | 包内相对 |

**结论：`artifact_roots` 必须保留，不能删。**

### 6.3 `artifact_roots` 扫描的硬约束

实现时必须做到：

1. **保留 `_keep_ep` 逻辑**（a415R2 N10）：`exclude_paths` 里产物根的祖先要剔除，
   否则 `sbuilder/output` 被排除后 `artifact_roots=sbuilder/output/build` 扫不到
2. **同一套剪枝**：含 `tmp` 四个完整名、`.` 开头目录、`_SKIP_DIRS`
3. **环防护**：沿用 a415R2 实现（同名目录重复 **>3** 次剪枝，路径长度 >480 字符也剪）
   —— 注意：a398 注释里写的「>6」是设计时表述，a415R2 审计时已收紧到 >3
4. **取消检查**：每 500 文件一次
5. **点开头文件保留**：`.foo.o.cmd` 是合法产物

实测：G10 `sbuilder` 全树遍历 22 秒，无卡死（a405 的卡死是 codegraph 外部工具，非 Python walk）。

## 七、`off` 目录的头文件守卫

**问题**：`off` 目录在 scandir 层剪枝 → 不进 `all_dirs` → 不进 inc 池 →
依赖它的白名单单元丢失头文件 → 跳转静默失效。

**实测数据**（MCU_IPC，10 个 inc 目录）：

| 目录 | 头文件数 |
|---|---|
| `M5_trunk/App/Drivers/inc` | 21 |
| `M5_trunk/App/Middle/inc` | 16 |
| `M5_trunk/Firmware/Peripherals/inc` | 26 |
| 其余 7 个 | 3~23 |

**要求**：递归 include 解析时，若某个 include 命中的是 `off` 目录下的文件：

```
仍收录该头文件，并记一条告警：
「目录 X 标为 off，但其头文件被 N 个白名单单元引用——已强制收录」
```

理由：`off` 语义明确限定为「不收源码」，不该反过来影响头文件解析。

## 八、a562 改动必须整体搬迁（高风险）

### 8.1 两处改动，缺一不可

| 改动 | 作用 |

| `_lookup_prox()` / `_prox_dirs()` | 邻近 inc 目录解析（当前文件目录 + 父目录下的 `inc/`） |

### 8.3 对 v4 的影响

v4 §八说「保留并下沉 `_reached_rel`」。**如果实现时只搬 `_lookup_prox`
而丢掉 inc 池兜底，MCU 一类工程覆盖率会从 45 跌回 2。**

inc 池的构造（当前实现）：

_cand_dirs = set(all_dirs) | set(dirs_files)
for _d in sorted(_cand_dirs):

**注意**：`all_dirs` / `dirs_files` 来自 `_walk_files`。v4 里 `off` 目录被剪枝后

## 九、`nm_lock` 语义修正（v4 §7.4 终稿）

### 9.1 缺陷（实测确认，非本次重构引入）

`definition()` 的 `rank()` 中 `nm_lock` 排第 0 位、`file_local` 排第 1 位。
`nm_lock` 的判据是 `len(syms[symbol]) == 1`，含义是「只有一个 `.o` 编译了它」，
**不等于**「源码里只定义了一次」。

后果：从任何文件点该符号，都会被拽到 nm 源，**包括当前文件自己就是定义处**。

### 9.2 实测规模

| 平台 | 唯一锁定 | tags 多处定义 | **真实误伤** |
|---|---|---|---|
| H8 | 96,970 | 4,783 | **4,728** |
| H11 | 29,602 | 1,405 | **1,367** |

误伤 top（H8）：`flags` 1030 处、`mode` 448 处、`state` 312 处、`offset` 302 处。

### 9.3 修正方案（判据用 `out`，方案乙）

```python
# ① nm_cand 计算保留（原 nm_lock 变量名可留，语义改为候选）
nm_cand = None
nm_srcs = syms.get(symbol)
if nm_srcs and len(nm_srcs) == 1:
    nm_cand = nm_srcs[0]

# ② 建 out 时 nm_lock 位先置 False（不能删字段，rank() 会 KeyError）
"nm_lock": False,

# ③ 建完 out 后回填（用过滤后的 out，不是原始 cands）
if nm_cand and len(out) == 1 and out[0]["rel"] == nm_cand:
    out[0]["nm_lock"] = True
```

**为什么用 `out` 而不用 `cands`**

`cands` 是过滤前候选，含 a414 会剔除的 `file_scope` 候选。
用 `cands` 会让「符号在别处只有一处 file-scope static、本文件没定义」时
`len(cands)==2` 导致 nm_lock 失效——而那正是 nm 该赢的场景。

**三场景验证**

| 场景 | 判据 | 结果 |
|---|---|---|
| 闭源 SDK（tags 无候选，a362 用 nm 源生成 1 个） | `len(out)==1` | 锁定 ✅ |
| tags 多处但其余是 file_scope（a414 剔除后 out==1） | `len(out)==1` | 锁定 ✅ |
| 短符号冲突（`flags`/`mode`/`start`，tags 多处） | `len(out)>1` | 不锁定 ✅ |

### 9.4 实现要点

- `cands = _be.lookup(symbol)` **已在 `nm_lock` 计算之前**构建，无需调整顺序
- `"nm_lock": False` 不能删字段（`rank()` 直接读 `c["nm_lock"]`）
- 建议 `len(out) == 1`（而非 `<= 1`）并校验 `out[0]["rel"] == nm_cand`

## 十、排序层适配（4 个点）

### 10.1 两个 `in_build` 计算点

| 位置 | 用途 |
|---|---|
| `symbols()` 内 | 工作区符号面板 |
| `definition()` 内 | F12 跳转 |

两处逻辑相同但**独立实现**，都要改：

```python
# 原
in_build = rel in compiled
# 改
in_build = (rel in compiled) or _under_any(rel, full_dirs)
```

**只改一处会出现「符号面板正常、F12 仍降权」的割裂。**

### 10.2 两个排序点

| 位置 | 排序键 |
|---|---|
| `symbols()` 内 `out.sort(...)` | `(0 if c["in_build"] else 1, -c["dist"])` |
| `definition()` 内 `rank(c)` | 6 元组（含 `nm_lock`/`file_local`/`_vendor`/`in_build`/宏/`dist`） |

### 10.3 `full_dirs` 与 `compiled` 同级

`full` 目录的源码是「确定的、完整源码集合」，不应比白名单目录低一等。
两者同级，让 `dist` 决定胜负。

`manifest.json` 增加 `full_dirs` 列表供查询期使用。

### 12.1 `ask_tier` 四选一 + 首次触发

is_first = not os.path.isfile(os.path.join(root, ".fcpk-scope.json"))

### 12.2 `Cancelled` 加 `reason` 字段

```python
class Cancelled(Exception):
    def __init__(self, reason=""):
        super().__init__(reason)
        self.reason = reason
```

`reason == "reconfigure"` 时前端不显示「已取消」文案。

### 12.3 `nav_codegraph.py` 降级（内网承诺 P6 补）

现有代码把 scope 的 `exclude_paths` + `artifact_roots` + `exclude_names`
编译成 codegraph 的扁平 `exclude` 数组（起因 a405：codegraph 扫描器走进
`sbuilder/output` 的 SMB 自链环出不来）。

v2 数据模型变了，必须同步：

```python
for path, state in cfg.get("dirs", {}).items():
    if state == "off":
        for pat in (path, path + "/**"):
            need.append(pat)
for p in cfg.get("artifact_roots") or []:
    need.append(p); need.append(p + "/**")
```

**降级只需保证「不卡死」，不必精确。**

### 12.4 换根迁移

`rebind()` 末尾的 scope 迁移逻辑改为迁工程根 `.fcpk-scope.json`，
不是 `scope_store_path`。

### 12.5 删除 `scope_store_path` 整套

`load_scope` 只读 `工程根/.fcpk-scope.json`。
加载时校验每个 `dirs` key 是否存在，不存在打一行告警
`配置路径不存在：X（可能 checkout 不全）`，不中断建库。
