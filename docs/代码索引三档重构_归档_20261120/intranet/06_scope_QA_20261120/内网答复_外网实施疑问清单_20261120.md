## Q1. 推荐器规则表的完整定义 【P0】

### 1.1 四层规则完整定义

**层间优先级：自上而下，L0 命中即停，不再进入 L1/L2/L3。**

#### L0 — 形态先验（唯一一条）

| 判据表达式 | 推荐 | 理由文案 |
|---|---|---|
| `isfile(<dir>/Config.in)` 且 `isdir(<dir>/package)` 且 `isdir(<dir>/output)` | `off` + `artifact_roots=[<dir>/output/build]` | 「buildroot 构建树，产物只读」 |

**为什么用结构不用名字**：E13 的 buildroot 目录叫 `sbuilder`，但换个工程可能叫别的。
三个标志的组合足以识别。

#### L1 — 名称先验（3 条）

| 判据表达式 | 推荐 | 理由文案 |
|---|---|---|
| `dirname ∈ {rootfs, eroot, buildroot, build_root, rootfs_build}` | `off` | 「根文件系统，第三方代码为主，推荐不收录」 |
| `'zoo' in dirname or 'zoos' in dirname or 'zmo' in dirname` | `off` | 「成果物目录」 |
| `dirname ∈ {release, release_tmp, temp_log}` | `off` | 「发布/日志目录」 |

**L1 是经验默认值，非数据推导**。实测 H9/H13 的 `rootfs` cmd_ratio 达 43~44%
（技术上是正常源码树），但按用户定调推荐 off。用户可手动改。

#### L2 — 数量先验（3 条，按序）

| 序 | 判据表达式 | 推荐 | 理由文案 |
|---|---|---|---|
| L2.1 | `code == 0 and o == 0 and cmd == 0` | `off` | 「空目录」 |
| L2.2 | `code < 5` | `off` | 「代码极少」 |
| L2.3 | `o == 0 and cmd == 0 and code >= 5` | `full` | 「有代码但无编译产物，白名单不可推导」 |

#### L3 — 比值判定（有产物才进入）

```
① o_ratio < 0.8                              → whitelist + 告警「增量残留嫌疑」
② o_ratio <= 2                               → whitelist
③ o_ratio > 2：
     cmd_ratio >= 3%                         → whitelist
     o_cmd_ratio > 5：
          src < 2000                         → full
          src >= 2000                        → whitelist + 强告警「产物覆盖不足」
     o_cmd_ratio <= 5                        → whitelist
```

**未命中任何规则** → `full` + 提示「未识别出构建系统，建议全量」

### 1.2 三个比值的精确定义

| 名称 | 分子 | 分母 | 无分母时 |
|---|---|---|---|
| `src` | — | — | 源文件数，后缀 ∈ `.c .cpp .cc .cxx .s`，**不含头文件** |
| `o` | — | — | `.o` 文件数 |
| `cmd` | — | — | `.cmd` 文件数 |
| `code` | — | — | 代码文件数，**含** `.h .hpp .hh` |
| `o_ratio` | `src` | `o` | `o=0` 时记 `∞` |
| `cmd_ratio` | `cmd` | `src` | `src=0` 时无意义（不进 L3） |
| `o_cmd_ratio` | `o` | `cmd` | `cmd=0` 时记 `∞` |

**Q12 提到的那处矛盾**（`实测数据汇总` §六）已确认是文档表述问题：
`o_ratio = 3.18`（340/107），`o_cmd_ratio = ∞`（107/0）。两个值都对，
但写在同一句里容易混淆。规则的判据是 `o_cmd_ratio > 5`（∞ > 5 成立），不是 3.18。

### 1.3 代码数据形态建议

建议用 Python 常量 + 纯函数，**不用 JSON**（规则含逻辑分支，JSON 表达不了）：

```python
_SCOPE_RULES_VERSION = 2

# L1 名称表
_L_NAME_OFF = {"rootfs", "eroot", "buildroot", "build_root", "rootfs_build"}
_L_NAME_ZOO = ("zoo", "zoos", "zmo")
_L_NAME_REL = {"release", "release_tmp", "temp_log"}

def _rule_level0(path):
    """buildroot 形态。返回 (state, artifact_root) 或 None。"""
    if (os.path.isfile(os.path.join(path, "Config.in"))
            and os.path.isdir(os.path.join(path, "package"))
            and os.path.isdir(os.path.join(path, "output"))):
        return ("off", os.path.join(path, "output", "build"))
    return None

def _rule_level1(name):
    n = name.lower()
    if n in _L_NAME_OFF:
        return "off", "根文件系统，第三方代码为主"
    if any(z in n for z in _L_NAME_ZOO):
        return "off", "成果物目录"
    if n in _L_NAME_REL:
        return "off", "发布/日志目录"
    return None

def _rule_level2(code, o, cmd):
    if code == 0 and o == 0 and cmd == 0:
        return "off", "空目录"
    if code < 5:
        return "off", "代码极少"
    if o == 0 and cmd == 0:
        return "full", "有代码但无编译产物"
    return None

def _rule_level3(src, o, cmd):
    """返回 (state, reason, warn)。"""
    o_ratio = (src / float(o)) if o else float("inf")
    cmd_ratio = (cmd / float(src)) if src else 0.0
    o_cmd = (o / float(cmd)) if cmd else float("inf")
    if o_ratio < 0.8:
        return "whitelist", "增量残留嫌疑", True
    if o_ratio <= 2:
        return "whitelist", "", False
    if cmd_ratio >= 0.03:
        return "whitelist", "有完整构建描述", False
    if o_cmd > 5:
        if src < 2000:
            return "full", "产物覆盖不足", False
        return "whitelist", "产物覆盖不足但规模过大", True
    return "whitelist", "", False
```

**`_SCOPE_RULES_VERSION` 的用途**：写进 `meta.json`，方便后续规则升级时
判断旧推荐结果是否需要重算。

## Q2. `_norm_scope` 的严格校验 【P0】

### 2.1 `dirs` 的 key：必须是相对路径

```python
def _norm_dirs(dirs):
    if dirs is None:
        return {}
    if not isinstance(dirs, dict):
        return None
    out = {}
    for k, v in dirs.items():
        if not isinstance(k, str) or not isinstance(v, str):
            return None
        p = k.strip().replace("\\", "/").strip("/")
        if p == "" or p == ".":
            return None                      # 根不能有显式状态
        if p.startswith("/"):
            return None                      # 绝对路径
        segs = [s for s in p.split("/") if s]
        if not segs:
            return None
        if ":" in segs[0] or segs[0].startswith("\\\\"):
            return None                      # 盘符/UNC
        if any(s == ".." for s in segs):
            return None                      # 逃逸
        st = v.strip().lower()
        if st not in ("whitelist", "full", "off"):
            return None
        out["/".join(segs)] = st
    return out
```

**与你倾向一致：拒绝绝对路径与 `..`。**

### 2.2 未知字段：v1 配置不报 bad，走「当无配置」路径

两者不冲突，因为**判定顺序**是：

```python
def load_scope_v2(root):
    p = os.path.join(root, ".fcpk-scope.json")
    if not os.path.isfile(p):
        return None, "none"
    raw = _read_json(p) or {}
    if raw.get("version") != 2:
        # v1：不校验未知字段，直接当无配置
        return None, "v1-deprecated"
    # v2：严格校验
    ok, sc = _norm_scope_v2(raw, root)
    return (sc, "project") if ok else (None, "bad:" + sc)
```

即：**先看 `version`，v1 直接绕过校验**。v2 才走严格未知字段检查。

v2 的已知字段白名单：

```python
_KNOWN_V2 = {"version", "name", "mode", "arch", "dirs",
             "artifact_roots", "exclude_names"}
```

### 2.3 `tree` 重复 key

v2 用 **dict** 不是数组，JSON 对象天然去重（后写的覆盖先写的）。
`_norm_dirs` 遍历 dict 时不会遇到重复 key。

若用户手写数组形式（`[{path, state}, ...]`）——**v2 不支持数组形式**，
`dirs` 不是 dict 时直接判 bad。

## Q3. `artifact_roots` 的 UI 表达 【P0】

### 3.1 UI：独立区域 + 行内标记，两者都要

**推荐做法**：

```
┌─────────────────────────────────────────────┐
│ ▼ sbuilder     [白·全·不]   5677 源 · 1846 单元  │
│     检测到 buildroot 结构                     │
│     ☑ 作为产物源（扫描 output/build，不收录源码）│
└─────────────────────────────────────────────┘
```

- 目录行内有一个**独立复选框**「作为产物源」，只在 `off` 状态下显示
- 弹窗底部再有一个汇总区「仅产物源：sbuilder/output/build [×]」

**理由**：复选框挂在目录行上，语义最直观（用户能理解为「这个目录我要产物不要源码」）。
底部汇总区方便快速查看/删除全部产物源。

### 3.2 `whitelist` 目录加「产物源」标记：无意义，应禁用

`whitelist` 本来就扫产物。UI 上：
- `whitelist` / `full` 状态下，「作为产物源」复选框**灰显禁用**
- 切到 `off` 时自动可用

### 3.3 `artifact_roots` 条目不在 `dirs` 里

**允许，且推荐器会自动生成这种组合**。

语义：

| `dirs[path]` | 在 `artifact_roots` | 实际行为 |
|---|---|---|
| 无（继承父级状态） | 是 | 按继承状态走；若是 `off`，则「仅产物源」 |
| `off` | 是 | 仅产物源 |
| `whitelist` | 是 | 白名单（产物源标记冗余，无额外效果） |
| `full` | 是 | 全量（产物源标记冗余） |

**推荐器生成 L0 结果时**：`dirs["sbuilder"] = "off"` 且
`artifact_roots = ["sbuilder/output/build"]`——两者都写，语义最明确。

若用户后来删掉 `dirs["sbuilder"]`，但保留 `artifact_roots` 条目，
则 `sbuilder` 继承根默认（`manual` 模式 = `whitelist`），产物源标记失效。

**建议 UI 上加约束**：删除 `dirs[path]` 时，若该 path 或其祖先在
`artifact_roots` 里，提示「同时移除产物源标记？」。

## Q5. a562 的 inc 池在按目录分组后如何执行 【P1】

### 5.1 采用方案 A（工程级），但补一个修正

```
方案 A 修正版：
  1. 全树 walk（whitelist + full 目录都走，off 剪枝）
  2. 全工程一次性扫 .cmd → 若 -I 为空，建**工程级** inc 池
  3. 对每个 whitelist 目录：单元 → 同目录头 → _resolve_includes(工程级 -I + inc 池)
  4. 对每个 full 目录：全收
```

**关键修正**：第 2 步的 inc 池必须建在**工程级**，不能下沉到目录级。

理由（实测）：MCU_IPC 的 `adc.c` 在 `App/Drivers/src/`，它需要的 `init.h` 在
`App/Middle/inc/`、`delay.h` 在 `App/Drivers/inc/`。若按目录独立建池，
`App/Drivers/inc` 只能看到自己的头，跨模块的头全丢。

实测对比：

| 配置 | `adc.c` 触达头文件 |
|---|---|
| 只有 `_lookup_prox`（目录级） | 2 个 |
| `_lookup_prox` + 工程级 inc 池 | 45 个 |

### 5.2 具体实现建议

现有的 inc 池兜底代码（`build()` 里 `if not _inc_dirs:` 分支）**整体保留**，
位置不变（在 stage 1 之后、stage 3 之前），只是**作用域改为全工程**。

按目录分组后：

```python
# 阶段 1：全树 walk（off 剪枝，artifact_roots 特殊处理）
# → 得到 all_rels / dirs_files / all_dirs / compiled

# 阶段 1.5：工程级 -I 提取 + inc 池兜底（现有代码，位置不变）
_inc_dirs, _n_cmd = _extract_inc_dirs(cmd_abs, _inc_bases, ...)
if not _inc_dirs:
    # 内核布局兜底 + inc 池兜底（a562）
    ...

# 阶段 2：按目录分组
for top_dir, state in grouped_dirs.items():
    if state == "whitelist":
        units = units_in(top_dir)
        reached = _resolve_includes(units, _inc_dirs, ...)   # 用工程级 -I
        final_files |= units | same_h | reached
```

**注意**：`_resolve_includes` 的 `inc_dirs` 参数传工程级 `_inc_dirs`，
不要每个目录重新算。

除正确性问题外，还有性能问题：MCU 工程 12 个 inc 目录 × 每个 whitelist 目录
独立建池 = 12 × N 次重复扫描。G10 有 200 个一级目录，开销不可接受。

## Q6. `off` 目录头文件强制收录的追溯范围 【P1】

### 6.1 追溯深度：递归，但加两个上限

**要递归**。理由：`a.h` 被引用（收录），`a.h` 又 `#include "b.h"`，
若不收 `b.h`，`a.h` 里的类型/宏引用会断。

**上限**：

| 上限 | 值 | 说明 |
|---|---|---|
| 深度 | 32 层 | 与现有 `_resolve_includes` 的 `max_depth` 一致 |
| 文件数 | 单次递归最多 500 个 | 防「off 目录里有循环引用」把整树拉进来 |

超过上限时记一条告警：「`off` 目录 X 的头文件递归超过 N 个，已截断」。

### 6.2 `off` 目录里的 `.c`：**不收录**

你的倾向正确。理由：
- `off` 的本意是「不收源码」
- `#include "foo.c"` 是模板技巧，极罕见
- 收 `.c` 会让 `off` 目录的语义变模糊

**但 `.h` 里如果 `#include "foo.c"` 呢？**——按「只收 `.h`」规则，
`foo.c` 不收录。这是已知的边界情况，记告警即可：
「`off` 目录中的源码文件 X 被头文件引用，因 off 语义未收录」。

### 6.3 告警粒度：每个 `off` 目录一条汇总

```
⚠ 目录 rootfs 标为 off，但其 3 个头文件被 12 个白名单单元引用——已强制收录
   build/busybox.h / usr/include/stdio.h / ...
```

理由：逐文件告警在大型工程上会刷屏（rootfs 可能有上千引用）。

### 6.4 性能：按需回读，不预先扫描

**你的理解正确**。执行顺序：

```
1. 主 walk：off 目录在 scandir 层剪枝，**完全不进**
2. 递归 include 解析时，若某个 #include 命中 off 目录下的文件：
   a. 检查该文件是否是 .h（.c 不收）
   b. 是 → 直接读该文件（单次 open，不走 walk）
   c. 递归解析该 .h 的 #include，同样按需回读
   d. 记录已强制收录的文件（避免重复）
3. 结束后汇总告警
```

**关键点**：`off` 目录的**目录结构**（哪些目录存在、目录名叫什么）不需要预先扫。
只有在 `#include` 命中时，才 `os.path.isfile()` 检查单个路径。

这样 `off` 剪枝的性能收益**完全保留**——只有真正被引用的文件才产生 I/O。

**但有个例外**：inc 池的构造需要知道工程内有哪些 `inc/` 目录。
如果这些 `inc/` 目录在 `off` 子树下，池里就没有它们。

**处理建议**：inc 池构造时，除了 `all_dirs ∪ dirs_files`，额外扫描
`off` 目录的**一级子目录名**（只 listdir，不递归），把 `inc/`/`include/`
加进池。

```python
for off_dir in off_dirs:
    try:
        with os.scandir(off_dir) as it:
            for e in it:
                if e.is_dir() and e.name.lower() in (
                        "inc", "include", "includes", "header", "headers"):
                    pool_candidates.add(e.path)
    except OSError:
        pass
```

这是浅层 listdir（每个 off 目录一次），开销可接受。

## Q7. `full_dirs` 的粒度与 `manifest.json` 结构 【P1】

### 7.1 存显式节点，不展开

**与你倾向一致**：`full_dirs` 存**显式** full 节点（如 `["kernel/tools", "libs"]`），
查询期做前缀匹配。

理由：G10 全量档展开后可能有数万个目录，`manifest.json` 会膨胀到几 MB。

### 7.2 前缀匹配性能

**内网实测**：H8 库 `symbols.json` 有 111,502 个符号，`definition()` 单次调用
平均 12ms（含 IO 缓存）。若加 `full_dirs` 前缀匹配（N<20 × M<50 = 1000 次字符串比较），
增量 < 0.5ms。

**可接受，无需优化。**

若未来 N 增长到上百个，可改用 trie 或按 `rel` 长度排序后提前终止。

### 7.3 旧库兼容

```python
full_dirs = mf.get("full_dirs") or []
```

## Q8. `nm_lock` 方案乙的精确定义 【P1】

### 8.1 你的理解正确：两个版本行为等价

| 场景 | `len(out)<=1` 版 | `len(out)==1 and out[0]["rel"]==nm_cand` 版 |
|---|---|---|
| `out` 为空 | 循环不执行 → 不锁定 | 条件不满足 → 不锁定 |
| `out` 只有 1 个且是 nm 源 | 循环命中 → 锁定 | 条件满足 → 锁定 |
| `out` 只有 1 个但不是 nm 源 | 循环不命中 → 不锁定 | 条件不满足 → 不锁定 |
| `out` 多个 | 循环可能命中 → 锁定 ⚠️ | 条件不满足 → 不锁定 ✅ |

**唯一差异在最后一行**：`len(out) <= 1` 版在 `out` 有多个候选时，
循环仍会遍历，若某个候选的 `rel == nm_cand` 就会被标 True。

但这与我验证的三场景结论冲突——「短符号冲突时 `len(out)>1` 应不锁定」。

**所以你的原稿 `len(out) <= 1` 在 `out>1` 时也会锁定 nm 源候选**，
这不是我建议的语义。

**内网建议的 `len(out) == 1` 才能保证「多候选时不锁定」。**

**结论：两者**不等价**，`len(out) == 1` 版才是正确的。**

我 v3 文档里写「两者等价」是因为看代码时漏了 `out>1` 时循环仍会执行这一点。
感谢外网指出，已更正。

### 8.2 最终实现

```python
# ① nm_cand 保留（原 nm_lock 变量名可留）
nm_cand = None
nm_srcs = syms.get(symbol)
if nm_srcs and len(nm_srcs) == 1:
    nm_cand = nm_srcs[0]

# ② 建 out 时 plnm_lock 位先置 False
"nm_lock": False,

# ③ 建完 out 后回填（严格 == 1）
if nm_cand and len(out) == 1 and out[0]["rel"] == nm_cand:
    out[0]["nm_lock"] = True
```

## Q15. `_walk_files` 的 `state_of` 回调签名与性能 【P2】

### 15.1 并发读 `dirs` dict：安全

Python dict 的读操作在 GIL 下是原子的。`dirs` 是只读（建库开始后不再修改），
8 个 worker 并发读安全。

**但建议加一层缓存**：`_resolve_dir_state` 每次上溯目录链，
对同一目录多次调用会重复计算。

```python
_state_cache = {}          # rel -> state
_state_lock = threading.Lock()

def _state_of(rel):
    v = _state_cache.get(rel)
    if v is not None:
        return v
    st = _resolve_dir_state(rel, dirs, default)
    with _state_lock:
        _state_cache[rel] = st
    return st
```

缓存无上界会内存泄漏。加 `len > 100000` 时清空（与现有 `_exists` 缓存同款策略）。

### 15.2 性能实测

内网实测（H8，727,794 个 tags）：

| 项目 | 耗时 |
|---|---|
| `_walk_files` 全树（8 worker） | 约 90 秒 |
| 每目录 `_resolve_dir_state`（深度 3~5） | < 0.01ms |
| 预估总增量（3 万目录 × 5 层） | < 15ms |

**可忽略。** 你的估算（< 10ms）接近。

**注意**：若目录数达到十万级，增量会到 50ms。建议缓存（见上）。
