## 三、实锤详证

### 3.1 FD-1（P1）：高并发查询 + 切档并发的组合负载击杀服务器进程——3/3 复现，静默无痕

- **负载形态**（attack1.py，20 线程）：definition 三库交替×4（fixture 大库/fixture 小库/根库，纯 GET）+ def 单库×5 + symbols×2 + references×2 + scope=file×2 + status/libs×1 + poll×1 + **reindex 三档循环×2** + cancel 干扰×1。
- **三次死亡时间线**（看门狗 1s 采样 + Flask 访问日志）：

| 死亡 | 实例（PID） | 存活时长 | 死亡时资源 | 最后日志 | 取证 |
|---|---|---|---|---|---|

| B | 2572（并行组 09:57 拉起） | ~11s | ws 63MB / h 244 / th 9-10（平稳） | 10:00:07 大量 200，10:00:08 `POST /api/nav/reindex 200`（accept）为最后一行 | timeline1b.tsv：8.3s 最后 OK → 11.3s FAIL → GONE；客户端 10054 远程主机强迫关闭 |

- **死亡痕迹为零**：三次均无 Flask Traceback（日志尾部全为 200/409 正常行）；`~/.serialconsole_pro/crash_dump.log` 停在 11-05 13:34（本轮零写入——注意 python -c 直启形态不挂 main.py 的 faulthandler）；Windows Application 日志无今日 Python 进程的 WER 1000/1001（仅 EdgeUpdate 噪声）。进程表现等同被 TerminateProcess：正常服务中直接消失。
- **变量分离（降配对照，attack_min.py）**：
  | 实验 | 形态 | 时长 | 结果 |
  |---|---|---|---|
  | pure | 18 线程纯查询（三库交替 def/sym/ref/scf/poll/status/libs，无 reindex/cancel） | 30s | **存活**，3100 请求全 200 零空结果，ws 64-65MB、h 212-284 振荡回落 |

  | attack1 | 20 线程（查询风暴 + reindex 并发 + cancel） | 60s | **3/3 死亡**（11~19s） |
  触发面收敛为：**≥16 线程查询风暴与 reindex 切档并发同时存在**。任一单独存在均安全。
- **与上轮 D-1 的形态对比**：a392 死亡是"孤儿连接泄漏 → 句柄/内存线性爬升（249→2698、66→505MB）→ 50-60s 死"；a393 多槽版无任何爬升（63-484MB 平稳）但 **11-19s 即死**。修复消除了泄漏本身（pure/mix 对照证明多槽缓存工作正常），没有消除死亡，且死亡显著提前。
- **黑盒机制假说（不定论）**：reindex work 开头 `_close_tagdb()` 清空全部库连接，与 20 并发线程的 `_get_tagdb()` 重建连接在最热点窗口交叠；死亡无 Python 层痕迹，指向 native 层（sqlite3 C API 连接生命周期竞态或 mmap 撤销竞态）直接带走进程。需白盒/native 取证（WinDbg attached 复现一次即可定论）。
- **影响面**：单用户正常使用（几个面板并发查询 + 手动切档）大概率达不到触发面；但脚本化/CI/多面板齐发场景（恰是上轮 D-1 的同款场景）下服务约 15 秒内凭空消失，无日志、无转储、无自动重启，用户表现为"工具消失"。上轮 D-1 报告的"满载死亡"在本轮修复版上**原样保留且加速**。
- **伴随现象**：死亡 C 的窗口中，proj2（未被 reindex 的小库）查询出现 6 次空结果（def 空 2 + symbols 空 4 / 各自总量约 40-80 次）——切档窗口内查询有一过性降级（与 _close_tagdb 全局清空 + 重连窗口吻合）。攻击 2 的 6845 次查询零空结果，说明低并发下该窗口几乎拍不到。
