# 代码索引三档改造 · 设计稿 v1

> 目标读者：前端控制台（本仓）与内网侧（此前做过同功能设计）两方。
> 本文档用于两边汇总对齐，不含实现代码。
> 生成日期：2026-11-20

---

## 一、目标

把现有「自动档 + 白名单优先硬覆盖」改造成**三档显式选择**，并把「收录范围」从平铺 `include` 升级为**支持父子覆盖的三态树**。

| 档 | 语义 | 目录名先验 |
|---|---|---|
| 白名单（严格） | 全树找 `.cmd/.o` 推编译单元；头文件只走 `-I` + BFS `#include` | **无** |
| 手动配置 | 用户在三态树上逐个决策；推荐引擎给初值 | 仅推荐用 |
| 全量 | 整树全收，无视产物 | 无 |

**核心纪律**：硬编码目录名从「判档依据」降级为「推荐引擎的先验词表」——

> **推荐可以有先验，执行不许有先验。**

这是本次重构最该守的一条线。判断「这是不是内核目录」可以用 `arch/` + `.config`；
但建库时不能因为目录叫 `kernel` 就特殊对待。

## 二、数据模型

```jsonc
{
  "version": 2,
  "mode": "whitelist | manual | full",
  "arch": "auto", "name": "...",
  "tree": [
    {"path": "kernel",        "state": "whitelist"},
    {"path": "kernel/tools",  "state": "full"},
    {"path": "rootfs",        "state": "off"}
  ],
  "artifact_roots": [], "source_roots": [], "header_roots": [],
  "exclude_names": [], "exclude_paths": []
}
```

**只存显式决策**，继承靠求值。`resolve_tree()` 按最长前缀解析，输出：

```python
{ "full_dirs": [...], "wl_dirs": [...], "off_dirs": [...] }
```

好处：

- JSON 小且可 review（只记用户动过的节点）
- 父改一处，全树跟随
- 覆盖关系一眼可见

### 三态语义（最容易各说各话的一处，先钉死）

| 态 | 含义 | **不是** |
|---|---|---|
| `whitelist` | 子树文件进「白名单**候选池**」，最终收不收由 `.cmd/.o` 推导决定 | 不是「这个目录全收」 |
| `full` | 子树内所有代码文件直接收录，无视产物 | 不是「无视一切」——剪枝仍生效 |
| `off` | 整枝不进索引 | 不是「不读」——产物仍可扫 |

## 三、剪枝策略（两套，按档位切换）

| 类别 | 全量档 | 白名单档 |
|---|---|---|
| 隐藏目录/文件 | 全跳 | 产物扫描**进**；代码收录跳 |
| 工具缓存 `.cache` / `.codegraph` / `.ua` | 跳 | 跳 |
| `node_modules` / `__pycache__` | 跳（「有用的全量」） | **进**（判「编译过」的证据） |
| 生成物目录（`sbuilder/output` 等） | 跳 | 按树态 |

### 为什么白名单档不能跳隐藏目录

Kbuild 的产物清单本身是隐藏文件（`.foo.o.cmd`），中间产物常藏在 `.libs/`、`.tmp_versions/`。
跳掉隐藏目录 = 产物推导直接归零。`nav_index.py:376` 的 a398 审计已经钉过这条。

### 「全量」不是真全盘

用户定调：“所有隐藏该跳跳，没用的就不要，全量也只是有用的全量。”
因此全量档仍跳：隐藏目录、工具缓存、生成物目录。`node_modules`/`__pycache__` 属生成物，也跳。

## 四、产物扫描

**全树扫，无 `artifact_roots` 加速路径。** 与代码 walk 同一次遍历（8 worker 并发 / 网盘单线程）。

白名单档要求：

- 无目录名先验
- 产物扫描覆盖全树，含隐藏目录、隐藏文件
- 不能落东西（用户原话：“白名单要对编译物递归全面，不要落东西”）

**必要条件**：进度每秒刷新 + 随时可取消（`should_cancel` 现有机制）。

**代价说明**：14 万文件的 SMB 工程，产物扫描从「只进 sbuilder/output」变成「整树扫一遍」。
这**不是新增开销，是恢复原本的遍历范围**——`.cmd` 本来就散在源码树内，只是此前被 `exclude_paths` 挡了。

## 五、推荐引擎（取代 `detect_scope`）

`recommend_scope(root)` 返回**树 + 每节点证据 + 预估**：

```
sbuilder/output/build → 产物外挂区（3421 个 .cmd）           [off]
kernel                → 内核源码（.config + 892 .o）         [whitelist]
kernel/tools          → 纯脚本无产物                          [full]
uboot                 → bootloader（探测 arch/*/include）     [whitelist]
libs/hal_bsp          → HAL（1400 文件，产物推导覆盖不全）    [full]
rootfs                → 解压根文件系统，非源码                [off]
```

前端弹窗展示：树 + 证据 + 预估（代码文件数 / 预计耗时）。
用户改完点确认才建库 —— 然后不再中途问（除非覆盖率异常，见下）。

### 硬编码目录名的归宿

现有 `detect_scope` 里的 `kernel/kernel_sdk`、`uboot/`、`libs/hal_bsp`、`sbuilder/output` 等
**全部移进推荐引擎的先验词表**，不参与建库决策。

## 六、中途询问（保留，扩展为四选一）

现有 `ask_tier(info)` 返回 `full / whitelist / cancel`，扩展为：

```python
"full" | "whitelist" | "reconfigure" | "cancel"
```

`reconfigure` 复用现有取消路径（`raise Cancelled(...)`），前端收到后：

1. 关进度面板
2. 打开三态树（推荐树已就绪，用户就地改）
3. 点确认
4. 重新 POST `/api/nav/build`

**复杂度增量约 30 行，无新线程、无新状态机。**

触发条件沿用现有：白名单单元占收录集源码比例 `< 2%`。

## 九、四个必须提前处理的坑

1. **产物扫描 ≠ 收录范围**
   勾了 `off` 的目录里的 `.cmd` 仍要扫 —— 它的源可能就在别处。
   现有 `artifact_roots` / `include` 的分离不能拆。

2. **codegraph 是外部工具**
   它只认扁平 `exclude` 数组。三态树必须能降级编译成它的形式，
   否则 g10 那种 SMB 自链环会重新卡死。降级只需保证「不卡死」，不必精确。

3. **`off` 不等于不扫产物**
   `off` 只决定「不收进索引」，不决定「不读」。

4. **「全量」不是真全盘**
   隐藏目录、工具缓存、生成物目录仍跳。

## 十二、待内网侧对齐的 5 个点

1. **`artifact_roots` 加速路径**：本方案是**删掉**它、改全树扫。内网侧若已有实现，判断是否同意删除，或给出保留理由。
2. **`whitelist` 态语义**：本方案是「候选池，最终由 `.cmd/.o` 定」。
   内网侧是否理解为「目录直接全收」？这是最容易各说各话的一处，必须先对齐。
3. **`off` 目录的产物是否仍扫**：本方案 **扫**。若内网方案是不扫，会漏编译单元。
4. **旧 v1 配置**：本方案不兼容 + 建库后写工程根 v2。
   内网侧若已实现 v1 升级器，讨论是否保留。
5. **`nav_codegraph` 的树 → exclude 降级**：是否已在内网设计里覆盖。
   外部 codegraph 是硬约束，降级只需「不卡死」，无需精确。
