## 二、核心纪律与两处「已知妥协」

> **推荐可以有先验，执行不许有先验。**

这条铁律在实施中会遇到两类情形，必须**分开表述**，不能都用「不是先验」一句话带过：

### 2.1 `.libs` / `.pio` 点目录 → 不是名字先验 ✅

- 规则：点目录在 `whitelist` 状态下作为**产物输入**保留（读 `.cmd/.o`，文件不进 tags 清单）
- 判据：**任何名字**的点目录都同样处理，不针对特定名字
- 结论：符合铁律

### 2.2 `libs/hal_bsp` → 是名字先验 ⚠️ 已知妥协

- 规则表：`libs/hal_bsp/` 同层有 `.o` → `whitelist`，否则 `full`
- 真相：这条规则**只有这个名字**才特殊处理，是名字先验的典型形态
- 为什么只能这样：它真正想表达的是「**某子树产物推导覆盖不全时推荐 `full`**」，
  但推荐器只有 2~3 秒预算（§五），做不到先扫描再判断，只能退化成名字匹配
- **文档必须写明**：

> `libs/hal_bsp` 这条本质是「产物推导覆盖不全 → 推荐 full」的快速近似。
> 用户可随时在树上改成任意状态；**推荐结果不影响执行正确性**。

## 三、数据模型 v2

```jsonc
{
  "version": 2,
  "name": "G10 推荐配置",
  "mode": "whitelist | manual | full",
  "arch": "auto",
  "dirs": {
    "kernel":            "whitelist",
    "kernel/tools":      "full",
    "kernel/tools/test": "off",
    "rootfs/buildroot":  "off"
  },
  "artifact_roots": ["sbuilder/output/build"],
  "exclude_names": []
}
```

### 3.1 `dirs` 继承语义

只存**显式覆盖节点**，不展开全树。键不存在 = 继承最近显式祖先；上溯到根仍无值 → 取 `mode` 语义。

```python
def _resolve_dir_state(rel, dirs, default):
    """rel='' 表示根。返回 whitelist|full|off。O(目录深度)。"""
    cur = rel.strip("/")
    while True:
        v = dirs.get(cur)
        if v in ("whitelist", "full", "off"):
            return v
        if not cur:
            return default
        cur = cur.rpartition("/")[0]
```

采用 `dict` 而非 `[{path,state}]` 数组：查表 O(1)、JSON 更小。

### 3.2 mode 与 dirs

| mode | dirs | 根 default |
|---|---|---|
| `whitelist` | 忽略 | — |
| `full` | 忽略 | — |
| `manual` | 生效 | `whitelist` |

根默认 `whitelist` 的理由：新出现的目录按白名单处理，推不出单元会自动降全量（§4.3），
不会静默丢失；若默认 `off`，工程后续新增目录会被无声排除。

### 3.3 v1 处理：不兼容

读到 v1（缺 `version: 2`）时：

1. 日志：`旧格式配置已废弃，本次按推荐器重新生成`
2. 当无配置处理，走推荐器
3. 建库成功后写 v2 覆盖工程根 `.fcpk-scope.json`

**不实施**内网 §3.4 的 `_migrate_v1()`。

### 3.4 配置落盘：方案 A（只写工程根）

**删除 `scope_store_path` 整套**。`load_scope` 只读 `工程根/.fcpk-scope.json`。

配套改动：

1. **加载校验**（内网 §一 建议采纳）：每个 `dirs` key 不存在时打一行日志
   `配置路径不存在：X（可能 checkout 不全）`，**不中断建库**。
   理由：配置进 SVN 后，别人可能只 checkout 部分目录。

2. **换根迁移**（`nav_index.rebind()` 末尾，a415R2 N11 那段）：
   原逻辑迁 `scope_store_path(old)` → `scope_store_path(new)`，
   改为迁 `old_root/.fcpk-scope.json` → `new_root/.fcpk-scope.json`。
   **注意**：该项在 `nav_index.py` 的 `rebind()` 内，**不在** `nav_api.py`
   （内网评审 §一 提到的 `nav_api.py:305` 是 `ask_tier` 的 `work()`，坐标有误）。

3. **`nav_api.py` 两处引用删除**：`scope_store_path(root)` 的调用点
   （`build` 成功落盘处、`scope_clear` 删除处）。

**「首次建库」判据因此简化为一层**：


## 四、执行语义

### 4.1 两个正交维度（关键修正）

```
目录状态 whitelist / full / off   →  决定「是否收录源码进索引」
artifact_roots 列表                →  决定「是否扫 .cmd/.o 推产物」
```

| 组合 | 行为 |
|---|---|
| `off`，不在 `artifact_roots` | **完全剪枝**，scandir 层不进（最大性能收益） |
| `off`，在 `artifact_roots` | **扫 `.cmd/.o`，不收源码**（「仅产物源」） |
| `whitelist` | 全量 walk + 扫产物（白名单固有行为） |
| `full` | 全量 walk，不需要产物 |

这样 `sbuilder/output/build` 的推荐（`off` + `artifact_roots`）语义自洽：
**它不收录任何源码（那是 buildroot 产物树），但它的 `.cmd` 是 kernel 白名单的真源（必须扫）。**

### 4.2 为什么 `off` 仍可能要扫产物

海思典型 out-of-tree 构建：`.o` 在 `out/obj`、`.c` 在 `source`。
若 `out/obj` 被 `off` 剪枝且不扫产物，整个工程白名单推导归零。
a415R2 的 bmap 兜底正为这种「产物与源码分离」的形态存在。

### 4.3 白名单目录零单元/低覆盖（定稿版）

| 情形 | 处理 |
|---|---|
| 完全零单元 + **首次**建库 | **暂停询问**（全量 / 严格白名单 / 重新配置 / 取消） |
| 完全零单元 + **已有配置** | 自动降全量，结束汇总提示 + 「严格白名单重建」按钮 |
| 有单元但覆盖率 < **2%** | 自动降全量，结束汇总告警（不询问） |

「首次」判据见 §3.4。

### 4.4 剪枝规则

```
目录名以 "." 开头            → 排除（例外见 4.5）
目录名 ∈ _SKIP_DIRS          → 排除
__pycache__ / node_modules   → 排除（已在 _SKIP_DIRS）
```

### 4.5 `_keep_dir` 实现（必须前缀匹配）

v2 写的 `rel not in _artifact_roots` 是**精确匹配**，有两个 bug：

1. `sbuilder` 这一级不匹配 `sbuilder/output/build` → 被剪 → 永远走不到子目录
2. 反过来，`artifact_roots` 的**后代**也要进去扫

正确实现：

```python
def _in_artifacts(rel_l, arts_l):
    if rel_l == "":
        return True                     # 根永不剪
    for a in arts_l:
        if rel_l == a:                  # 就是产物源目录
            return True
        if a.startswith(rel_l + "/"):   # 是产物源的祖先：必须放行才能下去
            return True
        if rel_l.startswith(a + "/"):   # 是产物源的后代：要进去扫 .cmd/.o
            return True
    return False

def _keep_dir(name, rel):
    if name.lower() in _skip:
        return False
    if state_of and state_of(rel) == "off" and not _in_artifacts(rel, _arts_l):
        stats["pruned_off"] = stats.get("pruned_off", 0) + 1
        return False
    return True
```

剪枝发生在 **scandir 层**——SMB 上跳过 `rootfs/`（数万文件）可省数十秒至数分钟。

## 五、推荐器

`detect_scope()` → `recommend_scope()`，返回 `mode=manual` 的 v2 配置 + 每项理由。

### 5.1 扫描深度

只 listdir **2~3 层**，不读文件内容、不遍历全树。目标 SMB 2~3 秒。

### 5.2 规则表（`_SCOPE_RULES` 常量）

| 特征 | 推荐 | UI 理由 |
|---|---|---|
| `kernel/` 下有 `arch/` 或 `.config` | `whitelist` | 标准 Kbuild 内核树，可按 `.cmd` 精确推导 |
| `uboot/` `u-boot*/` `seeboot/` `bootloader/` | `whitelist` | 引导程序源码，有构建产物可推导 |
| `sbuilder/output/build` 存在 | `off` + `artifact_roots` | buildroot 构建产物树，只读不索引 |
| `sbuilder/.buildroot-ccache` | `off` | ccache 缓存 |
| `rootfs/` 下有 `buildroot`/`errot`/`*_build` 且带 `output/` | `off`（子层无产物则 `full`） | 根文件系统构建树 |
| `libs/hal_bsp/` | 同层有 `.o` → `whitelist`，否则 `full` | **已知妥协**（见 §2.2） |
| 顶层同时有 `src/` 与 `inc/`（或 `include/`）且全树零 `.cmd` | `full` | MCU/IDE 工程，白名单不可推导 |
| `tools/` | `full` | 工具脚本，无编译产物 |
| 顶层 `.cmd` > 0 且有 `kernel/` | 各子树按上表，其余 → `whitelist` | 混合工程 |
| 有 `compile_commands.json`（根目录或 `build/`） | 不推荐状态，只**提示** | 「该工程用 CMake，白名单不可推导，建议选全量档」 |
| 无任何特征命中 | `full` | 未识别出构建系统，建议全量 |

**CMake 行是提示而非推荐**（用户定调：本次不做支持，后续再说）。
用户仍可在树上手动设状态，只是推荐器帮不上。

## 七、排序层适配：4 个点（v2 只发现一半）

### 7.1 两个 `in_build` 计算点

| 位置 | 用途 |
|---|---|
| `symbols()` 内（a5xx 待标记） | 工作区符号面板 |
| `definition()` 内（a5xx 待标记） | F12 跳转 |

两处逻辑相同但**独立实现**，都要改：

```python
# 原
in_build = rel in compiled
# 改
in_build = (rel in compiled) or _under_any(rel, full_dirs)
```

### 7.2 两个排序点

| 位置 | 排序键 |
|---|---|
| `symbols()` 内 `out.sort(...)` | `(0 if c["in_build"] else 1, -c["dist"])` |
| `definition()` 内 `rank(c)` | 6 元组，含 `nm_lock` / `file_local` / `_vendor` / `in_build` / 宏 / `dist` |

**只改一处会出现「符号面板正常、F12 仍降权」的割裂**——这正是 v2 的疏漏。

### 7.3 `full_dirs` 与 `compiled` 同级

**采纳三方结论**：`full` 目录的源码是「确定的、完整的源码集合」，
不应比白名单目录（只收了推导出的部分）低一等。两者同级，让 `dist` 决定胜负。

`manifest.json` 增加 `full_dirs` 列表供查询期使用。

### 7.4 `nm_lock` 不降权（外网立场，与内网建议相反）

内网 §7.1 建议：`full` 目录的候选不享受 `nm_lock`，理由是「防真定义输给假定义」。

**外网反对，理由**：

`nm_lock` 的定义是「`.o` 符号表**证明**该源定义了此符号」，
它恰恰是「不是假定义」的证据，不是优先级偏好。

真实竞争场景只剩一种：某符号在 `full` 目录有定义、在白名单目录也有同名且有 `.o`。
此时白名单目录的符号**确实被编译进了产物**，让它赢符合证据。

若某符号只在 `full` 目录有定义（未编译），它拿不到 `nm_lock`，
但此时**没有竞争对手**，`nm_lock=False` 不影响排序。

**结论**：`nm_lock` 保持 `rank()` 第 0 位不变。

**待内网反证**：若有反例工程，请给具体符号名 + 两侧路径 + `nm` 输出，
三方对照核。在此之前不改。

### 9.2 `Cancelled` 加 `reason` 字段（内网建议采纳）

`raise Cancelled` 会走现有「用户取消」路径，前端会显示「已取消」字样——
但用户是「要重新配置」，不是真取消。

```python
class Cancelled(Exception):
    def __init__(self, reason=""):
        super().__init__(reason)
        self.reason = reason
```

`reason == "reconfigure"` 时前端不显示取消文案，直接打开三态树。

### 9.3 触发条件

只在「首次建库」（§3.4 判据）时触发暂停询问。已有配置后重建时，
零单元/低覆盖一律自动降级 + 汇总告警（§4.3）。

```python
# v2：dirs 中所有 off 节点 + exclude_names + artifact_roots 展开成通配
for path, state in cfg.get("dirs", {}).items():

        for pat in (path, path + "/**"):

for p in cfg.get("artifact_roots") or []:
    need.append(p); need.append(p + "/**")
```
