## 一、`nm_lock` 缺陷：确认与量化

### 1.1 缺陷机制（代码实证）

`definition()` 的排序 `rank()`：

```python
return (
    0 if c["nm_lock"] else 1,          # 第 0 位
    0 if c["file_local"] else 1,       # 第 1 位
    ...
)
```

`nm_lock` 的计算：

```python
nm_lock = None
nm_srcs = syms.get(symbol)
if nm_srcs and len(nm_srcs) == 1:
    nm_lock = nm_srcs[0]
```

`len(nm_srcs) == 1` 的含义是「**只有一个 `.o` 编译了该符号**」，
**不等于**「源码里只定义了一次」。

`nm_lock` 排第 0 位 → 只要命中，从任何文件点该符号都会被拽到 nm 源，
**包括当前文件自己就是定义处的情况**（`file_local` 排第 1 位，被压）。

## 二、外网方案乙验证：成立

### 2.1 方案乙内容

```python
# nm_lock 位先置 False，建完 out 后回填
if nm_cand and len(out) == 1 and out[0]["rel"] == nm_cand:
    out[0]["nm_lock"] = True
```

判据用**过滤后的 `out`**（不是原始 `cands`）。

### 2.2 三场景实测

| 场景 | 判据 | 结果 | 实测 |
|---|---|---|---|
| A. 闭源 SDK（tags 无候选，a362 用 nm 源生成 1 个） | `len(out)==1` | 锁定 ✅ | 逻辑正确（数据结构保证） |
| B. tags 多处但其余是 `file_scope`（a414 剔除后 out==1） | `len(out)==1` | 锁定 ✅ | H8 上未找到此类符号，说明该场景罕见；a414 的价值不受影响 |
| C. tags 多处且真竞争（`flags`/`mode`/`start`） | `len(out)>1` | 不锁定 ✅ | H8 实测 4,728 个、H11 1,367 个全部停止锁定 |

**结论**：方案乙在三场景下行为全部正确。**外网判断准确，内网方案（用 `cands`）在场景 B 会误伤。**

### 2.3 一项实现补充（外网示例未明说）

`:3493` 的 `"nm_lock": bool(nm_lock and rel == nm_lock)` 必须改成 `"nm_lock": False`，
**不能删掉该字段**。`rank()` 在 `nav_index.py` 的 a414 段直接读 `c["nm_lock"]`，
字段缺失会 `KeyError`。

另外建议 `len(out) == 1` 而非 `<= 1`，并加 `out[0]["rel"] == nm_cand` 校验——
防御「tags 恰好只有一处定义、但那处不是 nm 源」的增量构建残留场景。

## 三、a562 兼容性：**高风险，必须写入 v4**

### 3.1 问题

a562 有两处改动，合起来才有效：

| 改动 | 作用 | 位置 |
|---|---|---|
| `_lookup_prox()` | 邻近 inc 目录解析（当前文件目录 + 父目录下的 `inc/`） | `_resolve_includes()` 内 |
| `-I` 为空时并入工程内 inc 池 | 跨模块头文件搜索 | `build()` 的 `if not _inc_dirs:` 分支 |

### 3.2 实测：两者缺一不可

MCU_IPC 工程，从 `M5_trunk/App/Drivers/src/adc.c` 发起（该文件有 7 个 `#include`）：

| 配置 | 触达头文件 | `init.h` | `delay.h` | `printf.h` | `version.h` |
|---|---|---|---|---|---|
| A. 只有 `_lookup_prox`（`-I=[]`） | **2 个** | ✗ | ✗ | ✗ | ✗ |
| B. `_lookup_prox` + inc 池 | **45 个** | ✓ | ✓ | ✓ | ✓ |

**A 只找到 `adc.h`（同目录）和 `gd32f1x0_conf.h`（被 adc.h 相对引用）。**

B 比 A 多出的 43 个头文件全部是**跨模块**的：

```
commun.h / delay.h / gpio.h / heart_beat.h / heater_ctl.h / init.h /
light_ctl.h / main.h / motor.h / printf.h / resource.h / systick.h /
temperature.h / timer.h / uart.h / vd_delay.h / version.h /
gd32f1x0_{adc,can,cec,cmp,crc,dac,dma,exti,fmc,gpio,i2c,ivref,iwdg,
          lcd,mcudbg,misc,opamp,pwr,rcc,rtc,spi,syscfg,timer,tsi,
          usart,wwdg}.h
```

### 3.3 对 v4 的直接影响

v4 §八「重写 build()」说：

> **保留并下沉** 1/2/3（在每个 `whitelist` 目录内独立执行）

第 3 项 `_reached_rel` 指的是递归 include 触达。**如果外网只保留 `_lookup_prox`
而丢掉 inc 池兜底**，MCU 一类工程的覆盖率会从 45 跌回 2。

**外网必须知道**：a562 的两处改动是一个整体，不能只搬一处。

### 3.4 三态树带来的新风险（实测分析）

**机制**：inc 池的来源是 `all_dirs ∪ dirs_files`，两者都由 `_walk_files` 产出。
v4 里 `off` 目录在 scandir 层剪枝 → 不进 `all_dirs` → **不进 inc 池**。

**后果**：若某个含头文件的目录被标 `off`，其头文件不再作为 `-I` 搜索路径，
依赖它的白名单单元会丢失这些头 → tags 里没有 → 跳转失效。

**MCU_IPC 实际 inc 目录分布**（10 个）：

| 目录 | 头文件数 | 典型状态 |
|---|---|---|
| `M5_trunk/App/Drivers/inc` | 21 | whitelist |
| `M5_trunk/App/Middle/inc` | 16 | whitelist |
| `M5_trunk/App/User/inc` | 3 | whitelist |
| `M5_trunk/Firmware/Peripherals/inc` | 26 | whitelist 或 full |
| `M6_trunk/App/{Drivers,Middle,User}/inc` | 9/14/3 | whitelist |
| `M6_trunk/Firmware/*/Include` | 2/23/5/12 | whitelist 或 full |
| `M6_trunk/comp_download/.../inc` | 1 | off（第三方库，无人引用） |

**风险判定**：
- `whitelist` / `full` 目录不被剪枝 → inc 池正常 → 无风险
- 只有 `off` 目录会从池里消失
- 用户把含头文件的目录标 `off` 本身就不合理，**但 v4 必须有守卫**

### 3.5 建议的守卫（请外网在 v4 实现）

```python
# 递归 include 解析时，若某 include 命中的是 off 目录下的文件
# （即 _lookup_prox 或 inc 池找到了，但该目录被标 off），两条路：
#
# 方案 1（推荐）：仍收录该头文件，但记一条告警
#   「目录 X 标为 off，但其头文件被 N 个白名单单元引用——已强制收录」
#   理由：正确性优先。用户标 off 通常是"不要索引这个源码树"，
#         不是"不要这个头文件"（后者在 C 工程里几乎不可能是有意为之）
#
# 方案 2：不收录，只告警
#   风险：跳转静默失效，用户难察觉
```

**内网推荐方案 1**：`off` 语义明确限定为「**不收源码**」，
头文件被引用时按依赖强制收录并告警。这与 v4 §四.1 的正交化设计一致——
`off` 决定源码收录，不该反过来影响头文件解析。
