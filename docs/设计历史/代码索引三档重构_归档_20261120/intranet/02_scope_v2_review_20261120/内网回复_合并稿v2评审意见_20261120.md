## 三、必修正 3：`off` 到底扫不扫产物，文档里说法打架

### 3.1 矛盾点

| 位置 | 原文 |
|---|---|
| §4.1 表格 | `off` → 产物扫描列写的是 **「不扫」** |
| 冲突 4 | `artifact_roots` = 「用户显式标记的**仅产物源**目录列表。推荐器会自动填充（如 `sbuilder/output/build`）」 |
| §5.2 规则表 | `sbuilder/output/build` 存在 → **`off` + `artifact_roots`** |

`sbuilder/output/build` 同时是 `off` 又在 `artifact_roots` 里。
按 §4.1 它不扫产物，按 §5.2 它要扫。**自相矛盾。**

### 3.2 建议：把「收录」与「扫产物」定义为两个正交维度

```
目录的应用状态（whitelist / full / off）  → 决定「是否收录源码进索引」
artifact_roots 列表                        → 决定「是否扫 .cmd/.o 推产物」
```

两者独立判定：

| 组合 | 行为 |
|---|---|
| `off`，且不在 `artifact_roots` | **完全剪枝**，不进入该目录（scandir 层剪，最大性能收益） |
| `off`，但在 `artifact_roots` | **扫 `.cmd/.o`，不收源码**（等价于「只读产物源」） |
| `whitelist` | 全量 walk，扫产物（这是白名单的固有行为） |
| `full` | 全量 walk，不需要产物（全收） |

这样 `sbuilder/output/build` 的推荐（`off` + `artifact_roots`）语义就自洽了：
**它不收录任何源码（正确，那是 buildroot 产物树），但它的 `.cmd` 是 kernel 白名单的真源（必须扫）。**

### 3.3 为什么这条很重要

海思典型的 out-of-tree 构建：`.o` 在 `out/obj`、`.c` 在 `source`。
如果 `out/obj` 被 `off` 剪枝且不扫产物，整个工程的白名单推导归零。
a415R2 的 bmap 兜底正是为这种「产物与源码分离」的形态存在的。

用户的「可标记为仅产物源」这个决策，实际就是给了 `off + artifact_roots` 这个组合一个入口。

### 3.4 §4.4 的 `_keep_dir` 代码需要同步改

合并稿 §4.4 给的是：

```python
def _keep_dir(name, rel):
    if name.lower() in _skip:
        return False
    if state_of and state_of(rel) == "off" and rel not in _artifact_roots:
        stats["pruned_off"] = ...
        return False
    return True
```

这个 `rel not in _artifact_roots` 是**精确匹配**。但 `artifact_roots` 里存的是
`sbuilder/output/build`，而 `_keep_dir` 收到的是**逐级目录**（先 `sbuilder`，
再 `sbuilder/output`，再 `sbuilder/output/build`）。

`sbuilder` 这一级不匹配 `sbuilder/output/build` → 会被剪掉 → 永远走不到子目录。

**必须改成前缀匹配**：

```python
# 目录 rel 是 artifact_roots 中某项的祖先 或 其后代，都不能剪
def _in_artifacts(rel_l):
    for a in _arts_l:
        if rel_l == a or rel_l.startswith(a + "/") or a.startswith(rel_l + "/"):
            return True
    return rel_l == ""    # 根永远不剪
```

第二、三个条件是关键：`a.startswith(rel_l + "/")` 让祖先不被剪；
`rel_l.startswith(a + "/")` 让后代不被剪（后代要进去扫 `.cmd/.o`）。

## 七、建议确认（不阻塞）的三点

### 7.1 `full_dirs` 与 `compiled` 同级排序 —— 内网确认

外网答「同级，让 dist 决定胜负」。**内网同意**，理由比外网给的理由更强：

用户显式选了 `full` 的目录，里面的源码是「**确定的、完整的源码集合**」，
比白名单目录（只收了推导得出的部分）信息更完整，没有理由降权。

补充一点：`nm_lock`（nm 符号锁定）目前在 `rank()` 里是**最高优先级**
（第 0 位）。这是正确的——它代表「`.o` 符号表证明这个源定义了该符号」，
比「在不在收录清单里」更强。但要注意：`full` 目录**不产生 `.o` 映射**，
所以 `full` 目录里的源永远拿不到 `nm_lock`。

**若某符号同时存在于 `full` 目录（真定义）和白名单目录（有 `.o` 记录）**，
`nm_lock` 会让白名单目录赢。这与「同级」结论冲突。

**建议**：`nm_lock` 这一档加条件——仅当该候选本身在白名单单元内时生效。
即：

```python
0 if (c["nm_lock"] and c["in_build"] is not True_from_full) else 1
```

简化版：`full` 目录的候选不享受 `nm_lock` 降权，直接与白名单候选按 `dist` 比。

请外网确认这个补充是否合理。

### 7.2 CMake `compile_commands.json` 支持 —— 内网确认纳入 P7

外网 §5.3 的分析是对的，这是**功能缺口**不是形态问题。

但内网要补一条现状事实：

`_parse_cmd_file()`（`nav_index.py:682`）只解析 Kbuild `.cmd` 的
`gcc -c -o ... src.c` 形式。`compile_commands.json` 是 JSON 数组，
格式完全不同（`[{"directory": "...", "file": "...", "command": "..."}]`）。

所以「约 60 行解析」估得偏低，实际还要处理：
- `command` 字段里 `-I` 参数提取（复用现有 `_extract_inc_dirs` 的解析逻辑，但输入格式不同）
- `directory` 与 `file` 的相对路径拼接（`file` 可能是相对 `directory` 的）
- CMake 的 `build/` 目录可能在工程根、也可能在 `out/`、`cmake-build-*/` 等位置

**估 100~150 行**，P7 独立项合适，但要预留这个量级。

### 7.3 `ask_tier` 收窄为「首次触发」—— 三方共定，内网确认

同意。补充一处实现细节：

现有 `ask_tier` 的返回通道在 `nav_api.py:278-302`，用户选择通过
`_state["ask_tier"]` 传递，前端轮询 `/api/nav/poll` 拿 `ask_tier.info`，
再 POST `/api/nav/tier` 回填。四选一只需扩展：

- `nav_tier` 端点校验 `choice in ("full","whitelist","reconfigure","cancel")`
- `reconfigure` 走 `raise Cancelled(...)`，前端捕获后打开三态树

**注意**：`raise Cancelled` 会走现有的「用户取消」路径，需要在
`nav_api.py` 里区分「真取消」与「重新配置」，否则前端会显示「已取消」字样。

建议给 `Cancelled` 加一个 `reason` 字段，`reason="reconfigure"` 时前端
不显示取消文案、直接开树。
