# 规则验证记录（含失败案例）

日期：2026-11-20
用途：记录推荐规则的演进过程、被否决的方案、以及验证中发现的问题。
**外网实现时应理解「为什么规则长这样」，避免重复踩坑。**

---

## 一、规则演进时间线

| 阶段 | 规则 | 问题 |
|---|---|---|
| 初版 | `源文件/o > 2` → full | kernel 被判 full（14.20）|
| 二版 | 加 `cmd_ratio ≥ 3%` → whitelist | 修正 kernel，但 H13 uboot 仍误判 |
| 三版 | 加 `o_cmd_ratio ≤ 5` | 基本可行 |
| 四版（终版） | 见下 | 定稿 |

## 二、被否决的方案

### 2.1 否决：「源文件数 < 2000 → full」作为主判据

**提出**：用户最初设想「比值 >2 且源码规模 <2000 全量，>2000 白名单」

**否决原因**：内核比值 14.20 远超 2，但规模 32,594 > 2000，会判白名单——
这时恰好判对，但逻辑是「碰巧的」。若有工程内核只有 1,500 个源文件，就会判 full。

**替代**：改用 `cmd_ratio` 作为主纠正判据，`2000` 只作为 `o_cmd_ratio > 5` 分支
的「全量代价是否可接受」判断。

### 2.2 否决：加「`.o` 数 ≥ 100」门槛

**提出**：为拯救 H13 `uboot`（39 个 `.o`，`o_cmd_ratio=0.78` 被判 whitelist 是错的）

**否决原因**：用户明确要求「尽可能少规则，现在已经很复杂了」。
且用户说明 H13 uboot 编译本身失败，39 个 `.o` 是异常输入，不应让规则为异常输入变形。

**后果**：H13 uboot 会漏收 5,228 个源文件。用户可在树上看到原始数据后手动改全量。

### 2.3 否决：引入「覆盖率」概念

**提出**：用 `o / src`（产物覆盖率）判断「是否大量源码未编译」

**否决原因**：内核覆盖率天然只有 5~8%（只编译当前平台配置），
覆盖率低不代表白名单错。这个概念引入后需要额外规则区分，违反「少规则」原则。

**替代**：`o_ratio`（`src / o`）已表达同样的信息，只是方向相反。

### 2.4 否决：`cmd_ratio` 阈值降到 2%

**提出**：H13 `modules` 是 2.84%，刚好卡在 3% 以下

**否决原因**：用户定调「不用，就这样」。2.84% 走 `o_cmd_ratio=7.66 > 5` +
`src 1763 < 2000` → 判 full，符合「编译不全该全量」的语义。

### 2.5 否决：`files.txt` 作为数据源

**提出**：用索引库的 `files.txt` 统计源文件数，比磁盘扫描快

**否决原因（实测证伪）**：

| 目录 | `files.txt` 口径 o_ratio | 磁盘实际 o_ratio |
|---|---|---|
| G10 kernel | 1.00 | **14.20** |
| H8 uboot | 1.00 | **3.18** |

差 14 倍。`files.txt` 是白名单档的「已收录文件清单」，
未编译的源码根本不在里面，天然接近 1.00。

**结论：推荐器必须直接数磁盘文件。**

## 三、验证中发现的问题

### 3.1 `sbuilder` 被判 whitelist（严重）

**现象**：G10 `sbuilder` 有 1,093 个 `.cmd`、1,846 个 `.o`、5,677 个代码文件，
按数值规则判 whitelist。

**问题**：它是 buildroot 源码树，`.cmd` 指向 buildroot 自己下载的第三方包，
不是用户要跳转的代码。

**修复**：新增 L0 形态判据（`Config.in` + `package/` + `output/`）→
`off` + `artifact_roots`。

**验证**：E13 的 sbuilder 同样命中 L0（38,907 源文件），符合实际。

### 3.2 H8 `uboot/seeboot` 被判 whitelist

**现象**（第一轮普查，深度 4 层）：
```
uboot: 0 .cmd, 2 .o, 291 代码文件
```
按规则 `o != 0` → 进 L3，`o_ratio = 291/2 = 145.5`，
`cmd_ratio = 0%`，`o_cmd_ratio = 2/0 = ∞` → `src 291 < 2000` → full。

**判别正确，但触发过程有误**——第一轮普查深度不够，没扫到 `seeboot` 内部的
107 个 `.o`。

**第二轮完整遍历**：
```
uboot/seeboot: 340 源 / 107 .o / 0 .cmd
```
`o_ratio = 3.18`，仍判 full（`cmd_ratio=0%`、`o_cmd_ratio=∞`）。**结论不变。**

### 3.3 扫描卡死的假象

**现象**：普查脚本在 `sbuilder` 上卡住 10+ 分钟无输出。

**排查**：
1. 单测 `sbuilder` 全树遍历 → **22 秒完成**
2. 发现同时有两个 Python 进程跑 W: 盘，SMB 串行化互相拖慢
3. 还叠加了我自己脚本的环防护 bug（`seen` 元组累加导致 O(n²)）

**真相**：不是 SMB 问题，是并发 + 脚本 bug。

**对实现的启示**：
- `artifact_roots` 扫描要避免与其他扫描并发
- 环防护用 dict 计数而非元组累加

### 3.4 `sbuilder/output/build` 有超大目录

**实测**：

| 包 | 文件数 | 遍历耗时 |
|---|---|---|
| linux | 76,352 | 10.0s（超时中断） |
| uboot | 23,428 | 4.8s |
| boot-regbin | 35,867 | 1.2s |
| boot-regbin/tmp/poifiles | **35,532** | 1.3s |

`tmp/poifiles` 一个目录就 3.5 万文件。**`tmp` 类剪枝是必需的**，不是优化。

### 3.5 `rootfs` 数据与推荐值不一致

**实测**：H9 `rootfs` cmd_ratio 43.85%，H13 44.17% —— 是正常编译的源码树。

**但用户定调推荐 off**：这类目录装的是 busybox/dropbear 等第三方代码，日常不跳转。

**处理**：作为 L1 名称先验保留，文档明确标注「经验默认值，非数据推导」。

## 五、对实现的提醒

1. **不要用 `files.txt`** 算任何覆盖率指标
2. **`tmp` 类目录必须跳**（完整名匹配，不跳 `template`）
3. **`artifact_roots` 扫描要保留 `_keep_ep`**（a415R2 N10），否则扫不到
4. **扫描要显示进度**（用户强要求）
5. **`off` 目录的头文件被引用时要强制收录 + 告警**（否则 MCU 类工程静默失效）
6. **a562 的两处改动必须整体搬迁**（`_lookup_prox` + inc 池）
