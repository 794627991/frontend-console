### 1.4 不能用 `shallow_probe`

现有 `shallow_probe` 是 `hits >= 60` 早退，**精确统计不能复用它**。

### 1.5 性能优化建议

六平台实测显示，**`kernel` 和 `sbuilder` 占 70% 以上耗时**。

若需优化：
- `kernel` 类目录（`src` 数万）不可避免要全扫
- `sbuilder` 类（L0 命中后）**不需要扫**——直接按 L0 判 `off`，
  但需要扫 `output/build` 下的 `linux`/`uboot` 包（约 2 秒）

**建议实现顺序**：
```
1. 先 listdir 顶层（0.1 秒）
2. 对每个顶层目录跑 L0/L1/L2（都不需要深扫，见下）
3. 只剩需要 L3 判定的目录才全扫
```

L0/L1/L2 的判据：
- L0：`isfile(Config.in) + isdir(package) + isdir(output)` — 3 次 stat
- L1：纯名字判断 — 0 次 I/O
- L2.1：`code==0 and o==0 and cmd==0` — 需要扫，但空目录很快
- L2.2：`code < 5` — 需要扫
- L2.3：`o==0 and cmd==0` — 需要扫

**L2 全都要扫**，所以优化空间主要在 L0/L1。

实测 `sbuilder` 22 秒可以省掉（L0 命中直接判，只扫 `output/build/linux` + `uboot` 约 2 秒），
**G10 总耗时从 32 秒降到约 12 秒**。

E13 同理：48 秒 → 约 22 秒。

**是否接受这个优化？（先 L0/L1 短路，只对 L3 目录全扫）**

## W3【P1】`code` 与 `src` 的判定口径 ☑

### 3.1 `src` **含** `.S`（大写）——内网脚本没漏

**核实过程**：外网怀疑我的普查漏了大写 `.S`。

我的脚本用的是：
```python
low = e.name.lower()
ext = os.path.splitext(low)[1]
if ext in UNIT:      # UNIT = {'.c','.cpp','.cc','.cxx','.s'}
```

`lower()` 把 `.S` 归一到 `.s`，**没有漏**。

**实测验证**（G10 kernel）：

```
.c = 31,231    .s = 3    .S = 1,343    头文件 = 24,101
源文件合计 = 32,577（我的表报 32,594，差 17 是 .cpp/.cc）
```

**1,343 个 `.S` 已包含在 `src` 里。**

### 3.2 但这是**实现隐患**，必须写进代码规范

现有代码的常量大小写不一致：

```python
CODE_EXTS = {".c", ".h", ".cpp", ".hpp", ".cc", ".cxx", ".hh", ".hxx",
             ".py", ".js", ".mjs", ".cjs", ".ts", ".java", ".go", ".rs",
             ".s", ".S"}          # ← 含大写 .S
_UNIT_EXTS = {".c", ".cpp", ".cc", ".cxx", ".s"}   # ← 全小写，无 .S
```

**如果实现时写 `os.path.splitext(name)[1] in _UNIT_EXTS`，大写 `.S` 会被漏掉。**

后果：G10 kernel 的 `src` 少算 1,343 个（4%），`cmd_ratio` 从 9.96% 变成 10.36%，
`o_ratio` 从 14.20 变成 15.51。**不改变判定，但数据不准。**

**要求**：推荐器的文件分类必须：

```python
ext = os.path.splitext(name.lower())[1]   # 先 lower
if ext in _SRC_EXTS:      # 全小写集合，含 '.s'
    src += 1
```

### 3.3 `code` 的口径：用 `CODE_EXTS` 全集

**确认采用 `CODE_EXTS` 全集**（含 `.py .js .mjs .cjs .ts .java .go .rs`）。

理由：
- 与现有建库逻辑一致（`_walk_files` 用 `CODE_EXTS` 判代码文件）
- 纯 Python/JS 工程不会因 `code=0` 被 L2.1 误判 `off`

**注意**：本文档 W2 表格里的 `code` 列**只算 C 系**（我的普查脚本口径）。
若改用 `CODE_EXTS` 全集，纯脚本目录的 `code` 会变大。

**对判定的影响**：仅 L2.1（`code==0`）和 L2.2（`code<5`）受影响。
实测 H8 `release_tmp` 的 `code=80`（C 系），若含脚本会更大 → 但 L1 名称先验
先命中 `off`，不影响。

### 3.4 `src` 是**磁盘实际文件数**，不是 `.cmd` 解析数

**确认：`src` = 磁盘上的源文件数。**

理由：
- `.cmd` 解析会有失败率（G10 sbuilder 的 linux 包 3,246 个 `.cmd` 里 945 个解析失败）
- 磁盘计数稳定、可复现
- `cmd` 才是「解析成功的构建描述数」

**两者独立统计，不做交叉校验。**

## W4【P1】`artifact_roots` 的 `.cmd` 归属与 `src` 计数 ☑

### 4.1 三条口径

| # | 问题 | 答复 |
|---|---|---|
| 1 | `.cmd` 归给谁 | **归源文件所在目录**（`compiled` 的键是源文件 rel 路径） |
| 2 | 是否跨目录重复计数 | **`compiled` 不重复**（dict 去重）；**推荐器统计不重复**（见 4.2） |
| 3 | `sbuilder` 自身状态 | **`off` + `artifact_roots`**，L0 已验证命中 |

### 4.2 推荐器统计时**不扫** `artifact_roots` 的 `.cmd`

**这是关键。**

若推荐器把 `sbuilder/output/build/linux` 的 3,246 个 `.cmd` 算进 `sbuilder` 的统计：

```
sbuilder: src = 783（sbuilder 自己的源码）
          cmd = 3,246（来自 output/build/linux）
          cmd_ratio = 414%  → 判错
```

**正确做法**：推荐器只统计**真实源码目录**的 `.cmd`。
`artifact_roots` 目录的 `.cmd` 在**建库阶段**才扫（用于 `compiled` 表）。

```python
# 推荐器统计（只看真实源码）
for d in top_dirs:
    if state == "off" and in_artifact_roots:
        # 推荐统计时跳过，但记下它是产物源
        continue
    src, o, cmd = count_reals(d)
```

### 4.3 `sbuilder` 自身推荐 = `off` + `artifact_roots`（已实测验证）

**L0 判据在 G10 上确实命中**：

```
Config.in  → W:\work\linux\g10\g10_trunk\sbuilder\Config.in      ✓ 存在
package/   → W:\work\linux\g10\g10_trunk\sbuilder\package        ✓ 存在
output/    → W:\work\linux\g10\g10_trunk\sbuilder\output         ✓ 存在
```

→ `off` + `artifact_roots`

**E13 同样命中**（`sbuilder/output/build` 有 45 个包）。

### 4.4 `artifact_roots` 的推荐范围：只取 `linux` / `uboot` 包

**用户定调（本轮）**：
> 只设成 `sbuilder/output/build/linux` 和 `uboot`（有用户源码的那两个）。
> 反正都是推荐值，用户不满意自己改。

**实测依据**：

G10 的 `sbuilder/output/build` 有 62 个包，只有少数 `.cmd` 指向外部源码：

| 包 | `.cmd` 数 | 指向 |
|---|---|---|
| `linux` | 3,246 | `kernel/kernel_sdk/*.c` ✅ |
| `uboot` | 475 | `uboot/*/` ✅ |
| `busybox-1.36.1` | 407 | 包内副本 `applets/*.c` ❌ |
| `hikio-head` | 35 | 包内 ❌ |
| `fubus-kmod-head` | 25 | 包内 ❌ |
| 其余 57 个包 | 0 或极少 | — |

**推荐器实现（名字启发式）**：

```python
def _l0_artifact_roots(sbuilder_path):
    """L0 命中后，推荐 artifact_roots。
    只取 buildroot 内置的 linux / uboot 包（这两个包固定存在，源码外置）。"""
    build = os.path.join(sbuilder_path, "output", "build")
    out = []
    for pkg in ("linux", "uboot", "u-boot", "kernel"):
        p = os.path.join(build, pkg)
        if os.path.isdir(p):
            out.append(rel(p))
    return out
```

**实测结果**：
- G10 → `["sbuilder/output/build/linux", "sbuilder/output/build/uboot"]`
- E13 → `["sbuilder/output/build/linux"]`（E13 无独立 uboot 包）

**为何用名字**：buildroot 的 `package/linux/`、`package/uboot/` 是内置固定包名。
这是**推荐值**，用户可在 UI 上增删。

**备选方案（若外网认为名字先验太重）**：
`artifact_roots = [<sbuilder>/output/build]`（全包），
由 `_parse_cmd_file` 的 `source_roots` 映射自动过滤掉无法映射的 `.cmd`。
代价：多扫 60 个包，约 20 秒。

**内网推荐名字启发式（快），用户已确认。**

## 附 A：新增规则 `cmd == 0 → full`（用户已确认）

L3③ 的 `o_cmd_ratio > 5` 分支新增一条前置判断：

```
o_cmd_ratio > 5：
     cmd == 0        → full（无构建描述，白名单必然为空）    ← 新增
     src < 2000      → full
     src >= 2000     → whitelist + 强告警
```

### A.1 为什么需要

纯应用工程（无 Kbuild）的典型形态：

| 形态 | `o` | `cmd` | 原规则判定 | 问题 |
|---|---|---|---|---|
| 没编译过 | 0 | 0 | L2.3 → full | ✅ |
| 编译过、小工程 | >0 | 0 | L3③ src<2000 → full | ✅ |
| **编译过、大工程**（src≥2000） | >0 | 0 | L3③ → **whitelist** ❌ | 白名单推导必然为空 |

`cmd == 0` 时，白名单的编译单元推导**必然是 0 个**，判 `whitelist` 会导致：
建库时走「零单元」路径 → 首次询问 / 后续自动降全量 → 推荐值与实际执行矛盾。

### A.2 对六平台数据的影响

**无影响**——现有六平台所有 `cmd==0` 的目录都满足 `src < 2000`：

| 目录 | src | `.o` | `.cmd` | 判定 |
|---|---|---|---|---|
| H8 uboot | 340 | 107 | 0 | full |
| H8 tools | 703 | 380 | 0 | full |
| H11 tools | 301 | 29 | 0 | full |
| E13 tools | 252 | 2 | 0 | full |
| H13 tools | 297 | 4 | 0 | full |
| MCU M6_trunk | 88 | 60 | 0 | full |

### A.3 完整 L3（定稿）

```
① o_ratio < 0.8                              → whitelist + 告警（增量残留嫌疑）
② o_ratio <= 2                               → whitelist
③ o_ratio > 2：
     cmd_ratio >= 3%                         → whitelist
     o_cmd_ratio > 5：
          cmd == 0                           → full          ← 新增
          src < 2000                         → full
          src >= 2000                        → whitelist + 强告警
     o_cmd_ratio <= 5                        → whitelist
```
