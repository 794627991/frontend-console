## N1【P1】推荐器扫描粒度：采用 B（完整子树）☑

### 1.1 矛盾澄清

| 文档 | 说法 |
|---|---|
| 终版方案 §一/§11.1/§13 | 「顶层 + 一级子目录」 |
| 内网答复 W1 | 「完整扫描顶层 N 个目录的子树」 |

**W-答复（完整子树）是正确的，终版方案的表述是错的。**

「顶层 + 一级子目录」这个措辞我本意是描述 **UI 展示层级**（树节点展开到一级子目录），
但写在了「扫描粒度」的位置，导致歧义。

### 1.2 定稿表述

> **扫描：对每个顶层目录完整递归统计三元组（`src`/`code`/`o`/`cmd`）。**
> **展示：树上展开到一级子目录，每个节点显示自己所属顶层目录的完整统计值。**
> **判定：L0~L3 规则作用在顶层目录的完整统计值上。**

### 1.3 为什么必须是完整子树

外网的理由成立，我再补一条：

推荐器的 L3 判据是 `o_ratio = src / o`。若只统计顶层目录**直接**包含的文件
（不含子目录），`kernel` 的 `src` 会接近 0（源码全在 `kernel/kernel_sdk/`），
`o` 也接近 0 → `o_ratio = 0/0` → 无意义。

**只有完整递归才能得到有意义的比值。**

### 1.4 一级子目录数据的用途（明确边界）

| 用途 | 是否使用一级子目录数据 |
|---|---|
| L0~L3 判定 | ❌ 用顶层的完整统计 |
| UI 树展示 | ✅ 展开显示 |
| 用户手动细化配置 | ✅ 显示以便用户改（如 `minisys/minisys_com`） |

**所以一级子目录需要统计**（否则 UI 展不开），但**不参与判定**。

### 1.5 实现要求

```python
def recommend_scope(root, progress=None):
    tops = listdir(root)                      # 12 个顶层
    result = {}
    for i, top in enumerate(tops):
        # 完整递归统计（含所有后代）
        src, code, o, cmd, timed_out = _count_dir_full(
            os.path.join(root, top), deadline=time.time() + 300)
        # 一级子目录统计（用于 UI 展示）
        sub_stats = {}
        for sub in listdir(os.path.join(root, top)):
            ss, sc, so, scm, _ = _count_dir_full(
                os.path.join(root, top, sub), deadline=time.time() + 120)
            sub_stats[sub] = (ss, sc, so, scm)
        result[top] = {...}
```

**注意**：一级子目录统计是**重复劳动**（顶层已含全部后代）。
优化：完整递归时顺手按「第一层子目录」分组累加。

```python
def _count_dir_full(path, deadline):
    """一次递归，同时得到顶层总计和一级子目录分组。"""
    total = [0, 0, 0, 0]          # src, code, o, cmd
    per_sub = {}                  # 一级子目录名 -> [src, code, o, cmd]
    stack = [(path, None)]        # (目录, 所属一级子目录名)
    while stack:
        if time.time() > deadline:
            return total, per_sub, True
        d, top_sub = stack.pop()
        try:
            with os.scandir(d) as it:
                ents = list(it)
        except OSError:
            continue
        for e in ents:
            try:
                if e.is_dir(follow_symlinks=False):
                    nm = e.name
                    if nm.startswith('.') or nm.lower() in _SKIP_TMP:
                        continue
                    # 记录一级子目录归属
                    child_sub = top_sub if top_sub is not None else nm
                    stack.append((e.path, child_sub))
                else:
                    low = e.name.lower()
                    ext = os.path.splitext(low)[1]
                    bucket = per_sub.setdefault(top_sub or '', [0,0,0,0])
                    if ext in _SRC_EXTS:
                        total[0] += 1; bucket[0] += 1
                    if ext in _CODE_EXTS:
                        total[1] += 1; bucket[1] += 1
                    if low.endswith('.o'):
                        total[2] += 1; bucket[2] += 1
                    elif low.endswith('.cmd'):
                        total[3] += 1; bucket[3] += 1
            except OSError:
                continue
    return total, per_sub, False
```

**一次递归，两种输出，无重复劳动。**

## N3【P1】点目录剪枝：恢复例外 ☑

### 3.1 三方说法

| 来源 | 说法 |
|---|---|
| 终版方案 §三 | 「目录名以 `.` 开头 → 剪枝」（一律） |
| 现有代码 `_keep_dir` | 「不跳通用点目录——`.libs`/`.pio` 里的 `.o`/`.cmd` 是合法产物」 |
| 我的 v2 评审 §4.3 | 「点目录在 `whitelist` 状态下作为产物输入保留」 |

**终版方案简化过度，删掉了例外。外网说得对。**

### 3.2 确认采用外网的调和方案

```python
def _keep_dir(name, rel):
    if name.lower() in _skip:                 # _SKIP_DIRS
        return False
    if name.lower() in _TMP_NAMES:            # tmp/temp/tmpdir/tempdir
        return False
    if name.startswith("."):
        # 点目录：whitelist 状态下保留（读 .cmd/.o 推产物），其余剪
        st = state_of(rel) if state_of else None
        return st == "whitelist" or _in_artifacts(rel)
    if state_of and state_of(rel) == "off" and not _in_artifacts(rel):
        return False
    return True
```

### 3.3 为什么这个方案正确

| 场景 | 行为 | 理由 |
|---|---|---|
| `.libs/` 在 `whitelist` 目录下 | **保留** | 读里面的 `.o`/`.cmd` 推产物 |
| `.libs/` 在 `full` 目录下 | **剪枝** | 不需要产物推导 |
| `.libs/` 在 `off` 目录下 | **剪枝** | 不收 |
| `.foo.o.cmd` 文件（点开头**文件**） | **保留** | 现有 `_dot_path` 只在 `files.txt` 写出端过滤 |

### 3.4 但有个关键点要说明

**点目录里的文件最终不进 `tags`**——现有代码在 `files.txt` 写出端有 `_dot_path` 过滤：

```python
def _dot_path(rel):
    return any(seg.startswith(".") for seg in rel.split("/"))

_list_pool = sorted(r for r in final_files if not _dot_path(r))
```

所以「保留点目录」的实际效果是：
- ✅ 目录被 walk，里面的 `.o`/`.cmd` 被计入 `compiled` 和符号表
- ❌ 里面的 `.c`/`.h` 不进 `tags`（`_dot_path` 过滤）

**这正好是「作为产物输入保留，文件不进 tags」的语义，无需额外实现。**

### 3.5 修正后的终版方案 §三

```
目录名以 "." 开头：
    在 whitelist 目录下       → 保留（作为产物输入，文件不进 tags）
    在 artifact_roots 下      → 保留
    其余                      → 剪枝

目录名 ∈ _SKIP_DIRS           → 剪枝
目录名 ∈ {tmp,temp,tmpdir,tempdir} → 剪枝
```

## N4【P1】`artifact_roots`：我改主意，建议采用 C

### 4.1 重新评估

外网指出我的建议（只取 `linux`/`uboot`）与用户定调「白名单要对编译物递归全面，**不要落东西**」冲突。

**外网说得对。**

用户的原始定调是完整性优先。而 `optee-head` 有 911 个 `.cmd`、
`busybox` 有 407 个——如果用户确实要跳转这些第三方库的源码（排查问题时很常见），
`off` 后就完全看不到符号。

### 4.2 三个方案的实测代价

| 方案 | artifact_roots | 扫描耗时 | 完整性 |
|---|---|---|---|
| A. linux+uboot | 2 个包 | ~2 秒 | 漏 optee/busybox 等 |
| B. 全部 62 包 | `output/build` | ~22 秒 | 完全 |
| **C. 全部包 + 自动丢弃无法映射的** | `output/build` | ~22 秒 | 完全，且不污染 `compiled` |

**C 的成本与 B 相同**（都要扫 62 个包），但结果更干净。

### 4.3 关键疑问：`_parse_cmd_file` 真的会过滤吗

外网说「`_parse_cmd_file` 的 `source_roots` 映射本来就会过滤掉无法映射的 `.cmd`」。

**我需要核实这一点，因为如果不过滤，C 就会引入 62 个包的 `compiled` 条目污染。**

实测数据（G10 `sbuilder/output/build` 的 `.cmd` 解析）：

| 包 | `.cmd` 总数 | 解析成功 | 解析失败 |
|---|---|---|---|
| linux | 3,246 | 2,300（包内相对）+ 1（绝对）= 2,301 | 945 |
| optee-head | 911 | 860 + 49 = 909 | 2 |
| uboot | 475 | 358 | 117 |
| busybox | 407 | 348 | 59 |
| hal_bsp-head | 1 | 0 | 1 |

**「解析成功」不等于「映射到收录集内」**。

比如 `busybox` 的 `applets/applets.c` 解析成功，但映射后是
`sbuilder/output/build/busybox-1.36.1/applets/applets.c`，**不在收录集内**（sbuilder 是 off）。

现有代码的处理（`build()` 的阶段 1）：

```python
srel = os.path.relpath(src, root).replace(os.sep, "/")
compiled.setdefault(srel, {"o": base, "src": "cmd"})
```

**它不检查 `srel` 是否在收录集内**——直接写进 `compiled`。

后续阶段用 `compiled` 时：
- `_units = {_rel_by_l[u.lower()] for u in compiled if u.lower() in _rel_by_l}`
  → **这里做了交集**，不在 `all_rels` 里的会被过滤掉

**所以只影响阶段 1 的 `compiled` 表大小，不影响最终 `final_files`。**

### 4.4 但 `manifest.compiled` 会膨胀

`compiled` 表会写进 `manifest.json`。G10 扫全部 62 包的话，`compiled` 会从
4,371 条涨到约 4,371 + 3,700（无法映射的条目）= 8,000 条。

**影响**：
- `manifest.json` 文件大小翻倍（当前 595KB → 约 1.2MB）
- 查询期 `mf.get("compiled")` 加载变慢（可忽略，一次性加载+缓存）

**可接受，但不是零成本。**

### 4.5 内网最终建议：采用 C，但加一个清理步骤

```python
# 阶段 1 结束后，清理无法映射的 compiled 条目
_compiled_pruned = {k: v for k, v in compiled.items()
                    if k.lower() in _rel_by_l}
if len(_compiled_pruned) < len(compiled):
    say("  产物源：%d 个 .cmd 指向收录集外的源码，已丢弃"
        % (len(compiled) - len(_compiled_pruned)))
    compiled = _compiled_pruned
```

**这样：**
- 扫描范围完整（62 个包都扫）
- `compiled` 表干净（只有能映射的）
- 用户能看到「丢弃了多少」

**代价**：22 秒扫描（vs A 方案的 2 秒）。

### 4.6 用户已定夺：采用 C

> 用户答复：**全部包（推荐）**

即：扫全部 62 个包（约 22 秒），无法映射到收录集的 `.cmd` 自动丢弃。

## N5【P2】`cmd_ratio > 100%`：正常现象

### 5.1 H11 modules 的数据

```
H11 modules: src=457, o=430, cmd=607, cmd_ratio=132.82%
```

### 5.2 原因分析

`.cmd` 数 > 源文件数的可能原因：

| 原因 | 是否可能 |
|---|---|
| 同一源被多次编译（多配置/多目标） | ✅ 最可能 |
| 增量构建残留旧 `.cmd` | ✅ 可能 |
| `.cmd` 指向外部源 | ✅ 可能 |

**H11 的 modules 编译率极高（`o_ratio = 1.06`，几乎一对一）**，说明是正常编译。
`cmd` 多出来是「同一源被多次编译」或旧残留。

### 5.3 对判定的影响

**无影响。** L3③ 判据是 `cmd_ratio >= 3%`，132% 显然成立。

### 5.4 UI 显示建议（采纳外网的）

```python
display_ratio = min(cmd_ratio, 1.0)
label = "%.0f%%" % (display_ratio * 100)
if cmd_ratio > 1.0:
    label += "+"          # 显示 "100%+"
    tooltip = "含同一源的多次编译或残留 .cmd"
```

**采纳外网的 §5.4 建议。** UI 上封顶显示 `100%+` 并加提示。

## N6【P2】`tmp` 无条件跳过：接受风险，写明边界

### 6.1 确认接受

用户定调明确：「`tmp` 目录无条件跳过，不检查里面有没有 `.cmd`」。

### 6.2 实测依据

G10 `boot-regbin/tmp/poifiles`：35,532 个文件，**0 个 `.cmd`**。

### 6.3 已知边界（写进文档）

> **`tmp` 目录跳过的已知风险**：若某个 `tmp/` 下确实有增量构建的 `.cmd`，
> 该源的编译单元不会被推导。此类源在最终 `final_files` 中可能缺失。
>
> 缓解：
> 1. 建库日志会显示「白名单单元数」，若用户发现明显偏少可检查
> 2. 用户可手动把 `tmp` 加入 `always_include`（若将来有此功能）或改名重建
>
> **当前视为可接受风险**（用户定调）。

### 6.4 建议加一个可选的诊断

建库时统计「被 `tmp` 剪枝的目录数」，显示在日志：

```
ℹ 跳过 tmp/temp 类目录 47 个（不检查内容）
```

这样用户至少知道有多少目录被无条件跳过。

## N8【P2】`off` 目录的三元组统计口径

### 8.1 外网的疑问

> 内网 W4 §4.2 写 `sbuilder` 的 `src = 783`——这个 783 是从哪来的？
> `sbuilder` 目录本身（不含 `output/`）的源码数吗？

### 8.2 核实

`783` 来自我 W2 的数据表：

```
G10 sbuilder: src = 783（我 W2 表格里的数）
```

但那个数是**用 `files.txt` 算的**（白名单档只含已收录文件），**不可信**。

### 8.3 正确的统计口径

**`off` 目录的三元组是否需要统计？**

| 场景 | 需要吗 |
|---|---|
| L0/L1 已命中，判定完成 | ❌ 不需要（N7 的短路） |
| 用户点「查看详情」 | ✅ 需要（但那时代价用户已知） |
| UI 显示「按规则推荐（未扫描）」 | ❌ 不需要 |

**结论：默认不统计，按需统计。**

### 8.4 统计范围的定义（供「查看详情」使用）

```
sbuilder 的统计范围 = sbuilder/ 下全部，但排除：
  - output/  （buildroot 产物树，不是源码）
  - 已在 _SKIP_DIRS 里的目录
  - tmp/temp 类目录
```

**理由**：`output/` 是产物，不是源码。统计它会把 62 个包的源文件算进来，
失去「这个目录有多少真实源码」的意义。

### 8.5 实现

```python
def _count_for_display(path, exclude_subs=("output",)):

                        continue          # 排除 output/
                    stack.append((e.path, sub or nm))
                else:
                    ...
```
