## 二、`nm_lock` 的真实缺陷（与 `full` 无关）

### 2.1 缺陷机制

`definition()` 的 `rank()`（`nav_index.py`，a414 标记段）：

```python
return (
    0 if c["nm_lock"] else 1,          # 第 0 位：nm 符号级锁定
    0 if c["file_local"] else 1,       # 第 1 位：当前文件 static
    1 if _vendor else 0,
    0 if c["in_build"] is True else 1,
    0 if ("/include/" in c["rel"] and c["kind"] == "macro") else 1,
    -c["dist"],
    c["rel"],
)
```

`nm_lock` 的定义（`definition()` 内）：

```python
nm_lock = None
nm_srcs = syms.get(symbol)                 # symbols.json：符号 → 源文件列表
if nm_srcs and len(nm_srcs) == 1:
    nm_lock = nm_srcs[0]                   # 全局唯一，则锁定到它
```

**问题**：`nm_lock` 是**全局**概念（「这个符号在全工程只有一个 `.o` 定义了它」），
而 `file_local` 是**上下文**概念（「当前文件里就有定义」）。

`nm_lock` 排第 0 位 = 只要 `symbols.json` 认为某符号唯一源是 A，
那么**从任何文件**点这个符号，都会被拽到 A —— **包括当前文件自己就是定义处的情况**。

### 2.2 实证（H8 真实工程，库 `669e892c4b7e240c`）

**规模统计**（`symbols.json` 唯一锁定 ∩ `tags` 多处定义）：

```
唯一锁定且符号在别处也有定义的条目：4084 个
```

**按「误伤文件数」排序**：

| 符号 | 其他定义处 | 被拽到 |
|---|---|---|
| `flags` | 598 处 | `rootfs/eroot/packages/zip/zip30/trees.c` |
| `mode` | 290 处 | `kernel/kernel_sdk/init/initramfs.c` |
| `state` | 216 处 | `kernel/kernel_sdk/init/initramfs.c` |
| `offset` | 211 处 | `rootfs/.../mke2fs.c` |
| `key` | 142 处 | `rootfs/.../zip30/globals.c` |
| `start` | 109 处 | `kernel/.../arch/arm/boot/compressed/head.S` |
| `ops` | 106 处 | `kernel/.../phy-hik-usb2.c` |

**符号名长度分布**（越短越危险，用户高频点击）：

```
1 字符:   2 个
2 字符:  23 个
3 字符:  33 个
4 字符:  34 个
5 字符:  56 个
...
```

### 2.3 实际跳转验证（不是推演）

从以下文件发起 F12，实测首候选：

| 发起文件 | 符号 | 首候选 | `nm_lock` | 本文件候选 | `file_local` |
|---|---|---|---|---|---|
| `rootfs/.../tcrypt_prng.h` | `start` | `kernel/.../head.S` | True | 同文件 | False |
| `kernel/.../include/linux/sctp.h` | `start` | `kernel/.../head.S` | True | 同文件 | False |
| `kernel/.../lib/xz/xz_dec_lzma2.c` | `start` | `kernel/.../head.S` | True | 同文件 | False |
| `kernel/.../include/linux/kexec.h` | `start` | `kernel/.../head.S` | True | 同文件 | False |
| `minisys/.../fstrim.c` | `start` | `kernel/.../head.S` | True | 同文件 | False |

**结论**：用户在**自己的文件里**点「`start`」（这个文件就定义了它），跳转却把他送到了
未编译的 `head.S`。这是明确的错误行为，与目录状态、与 `full` 档、与本次重构**全部无关**——
它是现存的 bug。

### 2.4 为什么 `full` 目录会加剧它

本次重构引入三态树后，`full` 目录的源码**全部进索引**（不受 `.o` 推导约束）。
这意味着 `tags` 里的同名定义会**变多**，而 `symbols.json` 的唯一锁定不会变——
误伤面随全量目录数量线性扩大。

换句话说：即使外网对 §7.4 的论证成立（「唯一源确实是证据」），
**它的正确性前提是「全工程只有一处定义」，而 `tags` 有多处说明这个前提不成立**。

`symbols.json` 的 `len(v) == 1` 判据只看**有没有 `.o` 映射**，
不看「源码里有没有其他定义」。命名冲突的短符号（`start`/`flags`/`mode`）
大量命中这个盲区。

## 三、建议的修法（请三方审议）

### 3.1 方案甲：`file_local` 提到 `nm_lock` 之前

```python
return (
    0 if c["file_local"] else 1,       # 第 0 位：当前文件优先（上下文最可信）
    0 if c["nm_lock"] else 1,          # 第 1 位：nm 锁定
    ...
)
```

- **优点**：符合「就近原则」直觉；改动 2 行。
- **缺点**：会破坏原有设计意图——`nm_lock` 原本就是为了解决
  「`pr_warn` 被 uboot 工具的 `fprintf` 局部宏抢走」这类场景（a414 注释有记录）。
  若把 `file_local` 提到前面，那个修复会失效。

### 3.2 方案乙：`nm_lock` 只在「tags 无其他定义」时生效（推荐）

```python
# 计算 nm_lock 时增加约束：只有当该符号在 tags 里确实只有一处定义才对全体生效
nm_lock = None
nm_srcs = syms.get(symbol)
if nm_srcs and len(nm_srcs) == 1:
    # a5xx：唯一 .o 源 ≠ 唯一源码定义。若 tags 里该符号有多处定义，
    # 说明 nm 的「唯一」只是「唯一被编译的」，不能作为全局锁定
    if len(cands) <= 1:
        nm_lock = nm_srcs[0]
```

即：**`nm_lock` 只在 `tags` 全局唯一时启用**。

- **优点**：保留 `nm_lock` 的原始价值（解决闭源 SDK 场景，那里 tags 确实只有一处）；
  不影响 a414 的 `pr_warn` 修复（那场景 tags 有多处，`nm_lock` 本就不该生效）。
- **缺点**：需要 `cands` 已算完才能决定 `nm_lock`，而现有代码是先算 `nm_lock` 再建 `cands`。
  需要调整顺序（约 15 行）。

### 3.3 方案丙：`nm_lock` 与 `file_local` 同级，由 `dist` 决定

```python
return (
    0 if (c["nm_lock"] or c["file_local"]) else 1,
    ...
)
```

- **优点**：最小改动（1 行），两种「证据」并列。
- **缺点**：仍然没有解决「当前文件 vs 别处的 nm 源」的歧义——
  二者同分后看 `dist`，`dist` 是「路径公共祖先深度」，在跨子树场景下没有判别力。

### 3.4 内网推荐：**方案乙**

理由：

1. 它纠正的是 `nm_lock` 的**语义**，而不是调整优先级。
   `len(syms[symbol]) == 1` 表达的是「只有一个 `.o` 编译了该符号」，
   **不等于**「源码里只定义了一次」。方案乙把这个不等号补上了。
2. 对已有修复零影响（a414 的 `pr_warn` 场景下 tags 有多处，`nm_lock` 本就不会触发）。
3. 方案甲虽然简单，但会回退 a414 的修复，引入已知回归。

### 3.5 请外网确认

若外网认为方案乙的「`nm_lock` 只在 tags 唯一时生效」会削弱其价值，请说明
**什么场景下**「tags 有多处定义但 `nm_lock` 仍应优先」——
这是判定方案乙是否可行的唯一关键。

我这边能想到的唯一反例是：**同名不同 scope 的 static 函数**。
但那种情况下 `tags` 的 `file:` 标记会让 `file_scope` 非零，
被 `definition()` 的 a414 修复 A 剔除（`if file_scope and ...: continue`），
不会进入排序。因此不影响结论。

## 五、对 v3 §7.4 的最终立场

外网的论证链条是：

> `nm_lock` 是「被编译进产物」的证据 → 让它赢符合证据

这个链条**在「只有一个定义」时成立**。但实测 4084 个符号违反这个前提。

所以内网的立场调整为：

> **保留 `nm_lock` 作为排序因子**（同意外网），
> **但必须修正它的触发条件**（方案乙），
> 而不是降权或不降权的问题。

这样两边的核心诉求都满足：

- 外网：「`nm_lock` 是证据，不该降权」→ 保留，且仍排第 0/1 位。
- 内网：「当前文件被拽走」→ 通过收窄触发条件解决。
