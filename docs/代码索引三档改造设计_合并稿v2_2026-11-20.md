## 二、冲突解决结果

### 冲突 1：`ask_tier` 中途询问 → 保留，但收窄到「首次」

- 外网：用户定调保留
- 内网 §8②：建议删除，改事后汇总

**结论 `[新]`**：保留，但触发条件收窄——只有「该工程从未有过有效配置」时才暂停询问。
理由：用户的「首次询问，后续自动」正好把两边的顾虑都解掉——
首次给用户决策权（外网的诉求），后续不重复打扰（内网的诉求）。

内网引用的 a432 卡死风险已在 `nav_api.py:278` 修掉（0.2s 分片轮询 + `should_cancel`
检查 + 10 分钟超时兜底），不再构成删除理由。

### 冲突 2：白名单目录零单元 → 分情况

- 内网 §4.2：自动降全量，不阻塞
- 外网：暂停问用户

**结论 `[新]`**：按 #4 + #5 组合：

| 情形 | 处理 |
|---|---|
| 完全零单元 + **首次**建库 | 暂停询问（全量 / 严格白名单 / 重新配置 / 取消） |
| 完全零单元 + **已有配置** | 自动降全量，结束汇总里提示 + 「严格白名单重建」按钮 |
| 有单元但覆盖率 < 2% | 自动降全量，结束汇总告警（不询问） |

### 冲突 3：白名单严格度（用户对内网/对外网措辞相反）

- 对外网：「白名单要严格」「不要落东西」
- 对内网：「也不用太严格……至少不要漏文件」

**结论 `[新]`**：按 #4 拆成两层——
- **推导阶段严格**：能推的一个不漏（扩展链完整：单元 → 同目录头 → `-I` + BFS `#include` → 邻近 inc 池）
- **判档阶段务实**：推不出时降级而非报错

即内网 §一 的「可解释闭包」表述成立，但**降级必须让用户可见**（汇总告警，不静默）。

### 冲突 4：`off` 目录扫不扫产物

- 内网 §4.1：scandir 层剪枝，不进入
- 外网：仍扫

**结论 `[新]`**：采用用户的「可标记为仅产物源」。这意味着**内网 §3.3 计划废弃的
`artifact_roots` 不能删**，语义改为：

> `artifact_roots` = 用户显式标记的「仅产物源」目录列表。默认空。
> 推荐器会自动填充（如 `sbuilder/output/build`），用户可在树上增删。

这一条同时解释了一个真实场景：海思 out-of-tree 工程里 `.o` 在 `out/obj`、
`.c` 在 `source`，若 `out/obj` 被 `off` 剪枝则产物推导归零（a415R2 的 bmap 兜底正为此存在）。

## 三、数据模型 v2

```jsonc
{
  "version": 2,
  "name": "G10 推荐配置",
  "mode": "whitelist | manual | full",
  "arch": "auto",
  "dirs": {
    "kernel":            "whitelist",
    "kernel/tools":      "full",
    "kernel/tools/test": "off",
    "rootfs/buildroot":  "off"
  },
  "artifact_roots": ["sbuilder/output/build"],   // 仅产物源（见冲突 4）
  "exclude_names": []
}
```

### 3.1 `dirs` 继承语义 `[内]`

- 只存**显式覆盖节点**，不展开全树
- 键不存在 = 继承最近的显式祖先；上溯到根仍无值 → 取 `mode` 语义
- 取值 `whitelist` / `full` / `off`

```python
def _resolve_dir_state(rel, dirs, default):
    """rel='' 表示根。返回 whitelist|full|off。O(目录深度)。"""
    cur = rel.strip("/")
    while True:
        v = dirs.get(cur)
        if v in ("whitelist", "full", "off"):
            return v
        if not cur:
            return default
        cur = cur.rpartition("/")[0]
```

采用内网的 `dict` 形态而非外网的 `[{path,state}]` 数组：查表 O(1)、JSON 更小。

### 3.2 mode 与 dirs 的关系 `[合]`

| mode | dirs | 根 default |
|---|---|---|
| `whitelist` | 忽略 | — |
| `full` | 忽略 | — |
| `manual` | 生效 | `whitelist`（内网 §8① 理由：新目录不静默丢失） |

### 3.3 v1 处理 `[新]`

按用户定调**不兼容**。读到 v1（缺 `version: 2`）时：

1. 记日志：`旧格式配置已废弃，本次按推荐器重新生成`
2. 当无配置处理，走推荐器
3. 建库成功后把最终生效的 v2 写回原路径（工程根 `.fcpk-scope.json`）

内网 §3.4 的 `_migrate_v1()` 不实施。

## 四、执行语义

### 4.1 目录状态 `[合]`

| 状态 | walk 阶段 | 产物扫描 | 收录清单 |
|---|---|---|---|
| `off` | 剪枝（scandir 层） | **不扫** | 无 |
| `full` | 全量 walk | 不区分（全收） | 该子树全部 `CODE_EXTS` |
| `whitelist` | 全量 walk | 扫 `.cmd/.o` | 单元 + 同目录头 + 递归 include 触达 + 头文件区 |

`artifact_roots` 中的目录：**扫产物但不收录源码**（等价于「只读 `off`」）。

### 4.2 剪枝规则三档共用 `[合]`

```
目录名以 "." 开头            → 排除（例外见 4.3）
目录名 ∈ _SKIP_DIRS          → 排除
__pycache__ / node_modules   → 排除（已在 _SKIP_DIRS）
```

`_SKIP_DIRS` 现状（`nav_index.py:51`）：`.git` `.svn` `.hg` `.history` `.cache`
`.ua` `.codegraph` `.agents` `.codex` `.vscode` `.tmp_versions` `.buildroot-ccache`
`__pycache__` `node_modules`。

### 4.3 点目录例外 `[合]`

现状 `nav_index.py:372` 的 `_keep_dir` 特意保留 `.libs` / `.pio` —— 里面的 `.o`
是合法产物。v2 明确为：

- 点目录**在 `whitelist` 状态下**作为产物输入保留（读 `.cmd/.o`，文件不进 tags）
- 其余情况一律剪枝
- 用户若需要某点目录参与，可显式标记为 `artifact_roots`

**注意**：这属于「执行侧先验」，与「执行不许有先验」的铁律有张力。
合理解释：`.libs`/`.pio` 不是**目录名先验**，而是**产物扫描的物理必要**——
任何名称的点目录在 `whitelist` 下都同样处理，不针对特定名字。

### 4.4 `off` 剪枝的实现位置 `[内]`

`_walk_tree` 已有 `excl_names`/`excl_paths`，增加 `state_of` 回调：

```python
def _keep_dir(name, rel):
    if name.lower() in _skip:
        return False
    if state_of and state_of(rel) == "off" and rel not in _artifact_roots:
        stats["pruned_off"] = stats.get("pruned_off", 0) + 1
        return False
    return True
```

剪枝发生在 **scandir 层**——SMB 上跳过 `rootfs/`（数万文件）可省数十秒至数分钟。
这是本次重构最大的性能红利。

## 五、推荐器 `[内]`

`detect_scope()` → `recommend_scope()`，返回 `mode=manual` 的 v2 配置 + 每项理由。

### 5.1 扫描深度 `[内]`

只 listdir **2~3 层**（顶层 + 一级 + 必要时二级），不读文件内容、不遍历全树。
目标耗时：SMB 2~3 秒。

### 5.2 规则表 `[合，扩充]`

规则集中在模块常量 `_SCOPE_RULES`，便于单测。

| 特征（目录名 + 浅层标记文件） | 推荐状态 | UI 理由 |
|---|---|---|
| `kernel/` 下有 `arch/` 或 `.config` | `whitelist` | 标准 Kbuild 内核树，可按 `.cmd` 精确推导 |
| `uboot/` `u-boot*/` `seeboot/` `bootloader/` | `whitelist` | 引导程序源码，有构建产物可推导 |
| `sbuilder/output/build` 存在 | `off` + `artifact_roots` | buildroot 构建产物树，只读不索引 |
| `sbuilder/.buildroot-ccache` | `off` | ccache 缓存 |
| `rootfs/` 下有 `buildroot`/`errot`/`*_build` 且带 `output/` | `off`（子层无产物则 `full`） | 根文件系统构建树 |
| `libs/hal_bsp/` | 同层有 `.o` → `whitelist`，否则 `full` | HAL 源码与接口头 |
| 顶层同时有 `src/` 与 `inc/`（或 `include/`）且全树零 `.cmd` | `full` | MCU/IDE 工程，白名单不可推导 |
| `tools/` | `full` | 工具脚本，无编译产物 |
| 顶层 `.cmd` > 0 且有 `kernel/` | 各子树按上表，其余 → `whitelist` | 混合工程 |
| 无任何特征命中 | `full` | 未识别出构建系统，建议全量 |

### 5.3 外网补充：CMake / `compile_commands.json` `[外]`

内网 §十.4 自己问「CMake+ninja 是否遗漏」——**答案是实质功能缺口，不是形态问题**：

- 现有白名单只认 Kbuild `.cmd`（`_UNIT_EXTS` + `_parse_cmd_file`）
- CMake 工程的标准产物是 `compile_commands.json`（内容为 `{"file": "...", "command": "..."}` 数组）
- 现在 CMake 工程的产物推导恒为零，会被 §4.2 降成全量

**建议**：在推荐器规则表新增一行——

| 工程根或 `build/` 下有 `compile_commands.json` | `whitelist` | CMake 工程，可按 compile_commands 推导 |

并在产物扫描阶段支持该格式（约 60 行解析）。

**范围建议**：作为 **P5 独立项**，不阻塞本次重构（本次先保证现有 Kbuild 路径不出错）。

## 七、排序层适配 `[内 + 外]`

内网 §7.1 发现了一个真实 bug，外网方案漏了：

`nav_index.py:3267` 的候选排序：

```python
out.sort(key=lambda c: (0 if c["in_build"] else 1, -c["dist"]))
```

混合档下 `full` 目录的源没有 `.o` 记录，`in_build=False` 被降权，
真定义可能输给白名单目录中的同名符号。

**修法**（内网提出）：`manifest.json` 增加 `full_dirs`，判定改为

```python
in_build = (rel in compiled) or _under_any(rel, full_dirs)
```

**外网补充 `[新]`**：内网 §十.3 问「白名单是否应优先于全量」——**不建议**。
用户显式选了 `full` 的目录，其源码是「确定的源码」，不应比白名单目录低一等。
两者同级，让 `dist`（路径公共祖先深度）决定胜负。
