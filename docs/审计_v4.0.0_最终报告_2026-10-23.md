### 5.2 第六至八轮（迟到事件投递方案的连续推翻）

第五轮的「严重6」修法 `_late_dirty` 是个粘滞标记——一旦发生迟到就永久逼整窗快照。
外层审计由此发起连续三轮对抗，每一轮都推翻了上一轮的方案：

| 轮次 | 方案 | 被推翻的原因 |
|---|---|---|
| 六 | 拒续传（`_late_dirty` 粘滞） | 永不复位，迟到一次后每次重连都整窗快照（MAJOR-1→10） |
| 七 | 区间水位 + 全局快照清位 | 多标签页互相擦除——A 页的自愈把 B 页的强制重对齐清掉了（MAJOR-8） |
| 七 | 补投原 seq | 补投帧 `toSeq == 客户端游标`，被前端 `if (!(f.toSeq > this.seq)) return` 整帧丢弃；服务端每 5s 无限重发、idle 永不归零导致心跳停摆（FATAL-7） |
| 八 | 重新分配 seq（排到末尾） | 劫持未来真实 seq → 并发 600 条实测丢 170（FATAL-8） |
| 八 | 保留原 seq + 哨兵水位 + per-conn resnap | **第九轮实锤致命**：哨兵 `W+1` 与下一笔真实 seq 撞号（store 连续分配 `_last_seq += 1`）→ 该事件必被判迟到 → 此后 16/17 轮全是整窗快照；且 `_late_lo` 永久钉死 → 断线重连永远被拒续传 |
| 九 | **投递序号与真实 seq 分离** | ✅ 采用 |

**最终采用（投递序号与真实 seq 分离）**——第九轮审计推翻了哨兵方案：

```python
# _commit：wseq 单调追加，真实 seq 只判重
self._wseq += 1
w = self._wseq
self._log.append((w, ds))
self._seqs.append(w)
self.snap["seq"] = w          # 客户端游标 = wseq

# _claim_seq：只回答「这个真实 seq 摄入过吗」
if seq in self._seq_set: return False
self._seq_set.add(seq); self._seq_fifo.append(seq)   # 8192 有界 FIFO
return True
```

- **真实 seq**（store 的事件身份）只进判重集，与游标解耦；
- **wseq**（投递序号）单调递增，迟到事件追加到末尾 → 天然落在任何游标
  之后，`frames_after`/`poll` 常规路径即可投递；
- 整套 `late/resnap/哨兵/per-connection rsnap` 机制**全部删除**。

**为什么前面的方案全错**：它们都假设「一个数既当事件身份又当游标」。
九次全审实测该前提必然产生两件事——(1) 哨兵 `W+1` 恰好等于下一笔真实
seq（store 连续分配），该事件必被判迟到，此后 **16/17 轮全是整窗快照**；
(2) `_late_lo` 永久钉死，断线重连的游标永远落在区间内 → 每次重连整窗快照
（a92/MAJOR-10 已否掉的行为）。分离后两者在结构上不可能发生。

### 5.4 第十轮复审：分离方案自身的四个缺陷

第九轮根修「投递序号与真实 seq 分离」方向正确，但第十轮审计发现新方案自身
有四个问题（前两条必须修）：

| # | 缺陷 | 根因 | 处置 |
|---|---|---|---|
| **F1（致命）** | 进程重启 / feed 重建后**静默丢一段历史** | `_wseq` 每实例从 0 重编，而 epoch 跨重建不变（lifecycle 沿用账本 epoch）→ 客户端持久游标 3 在新 wseq 空间 map 成「第 3 个事件」→ `resume_probe` 返回 ok → 只发增量 → 旧游标之前的行永久缺失且永不回退快照（实测丢 3/15） | `V4Feed(wseq_base=...)` 注入**跨实例单调**起点：主 feed = `账本 last_seq + LOG_RETAIN`，子 feed = `毫秒时间戳 ×1e6`；`snap["seq"]` 与空 log 的 `_floor_seq` 一律从起点起步（原为 0，会让旧游标合法落进新空间） |

超出 8192 的真实 seq 判重窗口后重放会多画一行（账本 retention=2000 < 8192，
实际不触发）。

### 5.5 第十一轮复审：F1 未闭合（等号边界）

第十轮给 `wseq_base` 的公式 `账本 last_seq + LOG_RETAIN` **有洞**：

```
旧实例 max_wseq = L1 + 600 + k     （k = 期间产 delta 的事件数）
新实例 base     = L2 + 600 = L1 + m + 600
k == m（1 delta/事件，即纯对话、无后台代理的最常见形态）⇒ 两者相等
```

而判据当时是闭区间 `base_seq >= _floor_seq` → 旧游标恰等于新 floor 时被放行
→ 整段历史当增量重画、早段永久缺失（审计实测丢 E1..E4、重复 E500..E503）。

**修法（双防线，互不依赖）**：

1. **判据改严格**：`can_resume` / `resume_probe` / `frames_after` / `poll`
   一律要求「游标 **严格大于** floor」才可续传；等号走整窗快照。
   （`floor == 0` 的首个实例保持旧语义放行 0，负游标恒判越窗。）
2. **起点改进程级高水位**：删掉推算公式，新增 `V4Feed._hwm` + `_hwm_lock`；
   `__init__` 经 `_claim_base()` 取 `max(提示, hwm+1)`，`_commit` 每次落账
   `_bump_hwm(w)`。`wseq_base` 降级为「下界提示」，实际起点恒严格大于本
   进程发过的任何 wseq。
3. **子 feed 弃用墙钟**：原 `int(time.time()*1e6)` 在时钟回拨或同毫秒两次
   重建时会拿到 ≤ 旧 max 的起点 → 改由类级 HWM 分配。

**验证**：HWM 归零 + 强制 `wseq_base == 旧游标` 时，`can_resume` 与
`resume_probe` 仍返回 False（两防线各自独立有效）；1500 条高速正常消费
零次误伤（`can_resume` 恒 True）。

**新增测试**：`test_wseq_base_equal_boundary_goes_snapshot`（等号边界）、
`_HWMTestCase` 每例重置进程级水位（否则用例互相污染）。48 → **53**。

**已知副作用（可接受）**：类级 HWM 跨 sid 共享，活跃会话会把新会话的起点
推高。新会话首个客户端本来就走整窗快照（`base_seq=0`），不受影响；已存在
的客户端游标属于本会话自己的 wseq 空间，同样不受影响。

### 5.6 第十二至十五轮复审：严格判据的连锁反噬与投递序号持久化

第十一轮的「严格大于」判据修好了等号边界，却引出新的连锁缺陷；到第十四轮
确认**固定偏移方案在信息论上不可闭合**，第十五轮改由持久化解决。

**第十二轮（N1，严重）**：严格判据把空 feed 的 floor 也拒了。会话刚建、
还没任何 delta 时 `_log == []`、`_floor_seq == _wseq_base`，客户端游标恰等于
base → 每 5s 一次整窗快照（审计实测 11 秒内 SNAPSHOT×3、keepalive×0）。
**修**：`_in_window` 对空 log 短路放行。

**第十三轮（致命）**：`_floor_seq` 的更新写在 `if len(_log) > LOG_RETAIN:`
块内 → log 长期 ≤600 时 floor 永远停在初始值 → 第十轮已修的 F1（跨重建丢历史）
原地复发（实测丢 E1..E4、重复 E500..E503）。
**修**：floor 同步移出 `if`，无条件执行。

**第十四轮（致命，设计层推翻）**：`+1` / `+2` 固定偏移都追不上代数累积——
```
旧 cursor = 上代账本 + 偏移 + m（期间发 m 条）
本代 base = 本代账本 + 偏移 = 上代账本 + m + 偏移
⇒ 恒等，与代数无关，偏移多大都撞
```
**修（换路线）**：不再靠公式推算。**wseq 高水位持久化**——`store.wseq_hwm`
→ `session.to_meta()["wseq"]` → `lifecycle.restore(epoch, seq, wseq)` →
新 feed 的 `wseq_base`。起点来自「上一代真实发到哪」，与代数解耦。

**第十五轮（三致命 + 三严重）**：

**当前 `_in_window` 终态**：

### 5.7 第十六轮复审：异步落盘路线被推翻，改同步根修

第十五轮的 debounce/看门狗方案被审计证明**不可能闭合**——不是实现问题，
是路线问题：

| 编号 | 缺陷 | 证据 |
|---|---|---|
| F3-1（致命） | 冷建补放走 `_replay_from → feed.ingest → _commit`，**不经** `v4_ingest_main`，异步落盘器根本不知道有变更 | 实测冷建补放 40 条，`_persist_dirty` 全程 `<none>`，重启后 40 条新消息一条也拿不到 |
| F3-2（严重） | debounce 窗口内崩溃，重启 `base = persisted + 2` 可能 ≤ 客户端游标 → 首批新事件拿到**已被消费**的 wseq | 实测 lag=3 丢 1 条、lag=4 丢 2 条 |
| F3-R2（严重） | `_persist_dead` 检查与 `sync_meta()` 之间无锁（TOCTOU），定时器已进入执行时 drop 仍会写盘 | 实测账本 `[] → ['S1']`，**删除的会话被复活** |
| drop 兜底（一般） | `routes.py` 先 `_sessions.pop` 再 `v4_drop_session` → drop 里 `_sessions.get(sid)` 恒 None | 实测 `sync_meta` 调用 0 次，整段是死代码 |

**修法（换路线，不加密）**：把持久化下沉到**数据结构的 setter**。

```python
# src/eventlog/store.py
@property
def wseq_hwm(self):
    return self._wseq_hwm

@wseq_hwm.setter
def wseq_hwm(self, v):
    self._wseq_hwm = max(self._wseq_hwm, int(v or 0))
    self._save_wseq(self._wseq_hwm)      # 同步：tmp + os.replace 原子写
```

- 独立小文件 `~/.serialconsole_pro/v4wseq/<sid>.wseq`（几十字节），
  不进 meta——meta 是全量读盘+合并+原子写，每条事件都同步会变成磁盘风暴。
- `_commit` 无论来自 live 还是冷建补放，都要推进 `log_store.wseq_hwm`
  → **所有写入路径共用同一入口**，「某条路径忘了持久化」在结构上不可能。
- 滞后恒为 0，F3-1/F3-2 同时消失。

**连带删除**：`_arm_persist` / `_persist_dirty` / `_persist_timer` /
`_persist_dead` / `_persisted_hwm` / drop 兜底落盘（v4hub 净减约 80 行）。
定时器不存在了，TOCTOU 窗口也随之消失。

**文件生命周期**：`/delete` 路由在 `_meta_save()` 后调 `drop_wseq_file(sid)`
清理，防止长期累积孤儿小文件。

**测试**：`TestPersistWatchdog`（针对已删看门狗）→ `TestSyncWseqPersist`
（6 例），含「冷建 40 条后重启旧游标必须拒」「lag=0 不吞消息」。
模块级 `_use_temp_wseq_dir()` 保证用例不写用户真实 HOME_DIR。
68 → **70 项**。

**降级路径（十六次全审修正：原论证是错的）**。原文档写「写盘失败时最坏
走一次整窗快照，不丢数据」——**审计实测推翻**：写盘失败 → 读回 0 →
`base=0` → 旧游标 40 被判合法 → 新事件重新从 1 编号 → **40 条消息全部
静默消失，无快照、无重连、无日志**。快照只在 `can_resume=False` 时触发，
而这里恰被判 True。

**十七次全审再次推翻**：条件式（`hwm>0 才用兜底`）假设「失效 = 读回 0」，
但真实失效形态是**陈旧非零**——先成功写过几个值、之后写失败，盘上是旧值，
分支根本不触发。实测陈旧值与真实水位差 ≥3 时首批新事件拿到 ≤ 旧游标的
wseq，静默吞 13~33 条。

最终修法（**双防线**）：

```python
# 防线一：无条件 max（判据侧，不靠落盘可信）
_hint = max(int(getattr(s.log, "wseq_hwm", 0) or 0),
            int(s.log.last_seq or 0))

# 防线二：本代首条（V4Feed._in_window）
if self._log and self._wseq_base > 0 and seq < self._first_issued:
    return False
```

防线一的代价经实测**可接受**：只让换代那一次走整窗快照（换代本就该重
对齐），快照 ack 的 toSeq 进入新空间后后续重连全部安静续传
（`resume(100)=False → 快照 502 → resume(502)=True`）。

防线二闭合「`base` 与旧游标撞等号」的结构性风险。

**十八次全审再次推翻**：`max(持久化值, last_seq) + 2` 的偏移**逐代累积**
（持久化失效后退化为 `last_seq`，恒比上代水位小 offset，每代 +2 且不回退）
→ 几代后旧游标同时越过 `_wseq_base` 与 `_first_issued`，实测 16~20 条丢。

**最终修法：换空间** —— 起点改用**墙钟微秒**（与任何状态无关的单调源）：
```python
_wall = int(time.time() * 1000000)
base = max(guess, hi, cls._hwm_floor, _wall) + 2
```
- 跨进程/跨崩溃/跨 epoch 天然单调，不依赖任何文件是否可写；
- `1.79e15 < 2^53`，JS Number 精确表示无虞（前端 `Number.isSafeInteger` 已验）；
- `max(...)` 仅兜住系统时钟回拨，保证本进程内不倒退。

**十九次全审（致命）**：初版还留了 `if not (guess or hi or floor): return 0`
早退，理由是「本进程第一代 ⇒ 无旧游标」。**这条不成立**——旧游标的真源
不止后端文件，前端 `localStorage['hg_v4snap:<sid>:main']` 与后端完全独立。
后端全丢 + 前端仍持游标时，`base=0` 会让新事件从 1 起编、与旧游标空间
重叠（实测主窗 5 条全丢；子 feed `epoch` 恒 `"sub"`，跨重启 300 行内容错位）。
**早退已删除**，墙钟源无条件生效。`base=0` 的唯一用途是「客户端本地无内容」，
而 routes 层 `base_seq > 0` 门（`routes.py:700`）已保证游标 0 不进
`resume_probe`，该语义多余。

**测试可读性**：起点变墙钟量级后，写死 `snap["seq"]==5` 的断言全部失效。
新增测试辅助 `_mkfeed()`——构造后把各游标字段统一切到 0 起编（**仅供断言
可读性**，相对语义不变）；验证起点单调/跨代拒绝的用例不走它，仍用真实
墙钟起点。

**二十次全审（严重）：守护测试本身假绿**。`test_base_survives_total_persistence_loss`
原本只断言 `can_resume(旧游标)==False`——而 `return 0` 缺陷形态下 base=0、
water=0，任何正游标都会被 `seq > water` 拒掉，断言「通过」但与被测逻辑
无关。审计把 `return 0` 注入后跑全套 **75 例全绿**，证明该缺陷可无声回归。

修法：**直接断言 `_wseq_base` 本身**，并在补事件（此时 water 已越过旧游标、
不再有 `seq > water` 遮挡）后再断言一次：

```python
self.assertGreater(f2._wseq_base, cur, "起点未越过旧游标（return 0 早退回归）")
self.assertFalse(f2.can_resume(cur))
for i in range(5): f2._commit(...)
self.assertGreater(f2.snap["seq"], cur)
self.assertFalse(f2.can_resume(cur), "水位越过旧游标后仍放行 → 静默丢行")
```

并用**变异测试**验证守护有效：注入 `return 0` → 75 例中 1 例失败；还原 → 全绿。

> 教训（已写入〈六、遗留风险〉）：守护用例必须能**区分修好与没修**。
> 只断言「某个返回值为 False」时，要确认拒的理由正是被测判据，
> 而不是被另一条更早的判据顺手挡掉。
持久化读回 0（不可信）时回落到账本 `last_seq`——每个 `store.append`
对应一次 ingest/补放，上一代发过的 wseq 数不超过它。

**为什么是条件式而非 `max`**：`last_seq` 常态大于已发 wseq 数（订阅前的
V3 零开销事件不经 `_commit`；判重丢弃的事件也已 `append`）。无条件取
max 会把 base 抬到远高于真实水位，让本来有效的客户端游标白白走整窗
快照（每次重连全量重渲）。实测：`last_seq=500, wseq=100` 时 base 应为
102，取 max 会变 502。

三情形实测：
| 场景 | 输入 | base | 旧游标 40 |
|---|---|---|---|
| 常态 | `last_seq=500, wseq=100` | 102 | —（未抬高） |
| 降级 | `last_seq=40, wseq=0` | 42 | `can_resume=False` ✓ |
| 空 feed | — | — | `can_resume(自身水位)=True` ✓ |

另补：`_save_wseq` 首次失败打 `log.warning`（`_wseq_warned` 只打一次），
`os.write` 返回值校验短写。

**性能（同步写必须廉价，否则等于用卡顿换正确性）**。首版用
`open+write+os.replace`，实测 **15.3 ms/次（65 条/秒）**——流式 token
每秒数十条事件，直接拖垮对话。改为**常开 fd + 定长覆盖写**：

```python
blob = ("%020d" % v).encode("ascii")   # 20 位零填充，长度恒定
os.lseek(self._wseq_fd, 0, os.SEEK_SET)
os.write(self._wseq_fd, blob)
```

实测 **0.0003 ms/次（约 290 万条/秒）**。定长是必须的：变长写入时
1000 覆盖 999 会残留成 `10009`；零填充保证 `lseek(0)+write` 完整覆盖。

**并发**：`_commit` 持 feed._lock、`restore` 持 store._lock——两把不同的
锁，会并发进 `_save_wseq`。`lseek`+`write` 是两步 syscall，必须用模块级
`_WSEQ_FD_LOCK` 串行化（临界区仅两次 syscall）。压测：8 线程 × 2000 次
并发写，0.038s，内存/磁盘/重读三方一致。

**句柄生命周期**：新增 `close_wseq()`；`/delete` 路由在 `s.close()` 之后、
`drop_wseq_file(sid)` 之前调用（Windows 下打开的文件删不掉）。

### 5.8 第二十一轮：墙钟被回拨攻破，换持久化启动序号

第二十轮把起点换成墙钟微秒，主路径闭合。但独立复审（干净上下文）证明
**墙钟可被回拨攻破**：

```
危险窗口：R ∈ (E − m·1µs, E]      E = 两代 feed 创建间隔，m = 本代 wseq 数
实测（子 feed，epoch 恒 "sub"、无 log_store、纯靠墙钟）：
  gen1 cursor = ...623893
  gen2 回拨 R=0.0254s → base = ...623588 < cursor
  can_resume(旧游标) = True → 服务端重放 480 条，rowId 321..800 与客户端完全重叠
```
NTP 校时/手动改钟的回拨量级（秒~分钟）与 IDE 热重载重启耗时（秒级）重叠，
**不是不可达的构造场景**。这是本修复唯一承重源，风险不该只写进注释。

**修法：给序号空间加持久化的启动序号作高位**（与时钟完全无关）：
```python
_BOOT_STRIDE = 10 ** 9
base = boot * _BOOT_STRIDE + (time.time()*1e6 % _BOOT_STRIDE) + 2
```
- `boot` 是持久化计数器（`~/.serialconsole_pro/v4wseq/BOOT`），进程启动时
  读+1 写回，跨进程严格递增；
- 跨重启：boot 递增 ⇒ base 至少跳 `_BOOT_STRIDE`（10 亿），远超上代水位；
- 同一启动内：低位按墙钟微秒递增，仍单调；
- 回拨：只影响低位（≤1e9 µs = 1000 秒），**不可能跨过 boot 高位**。

**连带修复（同轮）**：

| # | 缺陷 | 修法 |
|---|---|---|
| 2（一般） | 多实例同 sid 时盘上高水位可回退（`_wseq_written` 是每对象私有，GC 重建窗口内两 store 并存） | `_save_wseq` 守卫增加「读当前盘值再比较」（`_read_disk_wseq`），实测 `a=100,b=500,a=300` 后盘上保持 500 |

### 5.9 第二十二轮：boot 序号的三个次生缺陷

### 5.10 第二十三轮：放弃「数值单调」，改为**实例身份匹配**

第二十二轮复审判定：5.8/5.9 路线仍不成立。理由是**结构性**的——

- wseq 起点要「严格大于上一代发过的任何值」，但该值只存在于内存与
  一个可丢失的小文件里；持久化一旦完全丢失（换机/清目录/进程被杀在
  `os.replace` 之前），新一代只能从下界（账本 seq）重新起算，
  **必然**可能 ≤ 旧客户端游标；
- 任何用「时间」补位（墙钟微秒、boot 序号）都要额外对抗回拨、并发撞号、
  JS 安全整数越界；每补一个洞就长出两个新洞（5.6–5.9 五轮全在填）;
- 数值单调性在「持久化可丢 + 时钟可回拨 + 多进程并发」的世界里**不可达**。

**改换判据：不再问「这个 seq 是否安全」，改问「这个游标是不是我的」。**

```python
# v4feed._reset()
self.incarnation = uuid.uuid4().hex[:16]
```

```python
# routes.py /v4/stream
if (base_inc and base_inc == feed.incarnation
        and base_epoch and base_epoch == feed.epoch and base_seq > 0):
    _ok, _fr, _last = feed.resume_probe(base_seq)   # 才允许续传
# 否则：整窗快照
```

ack 两处（resume / snapshot）都回带 `inc`；前端 `v4store.js` 持
`this.inc`，随请求携带、随 ack 更新、随本地垫片持久化——冷连接垫显
旧快照时 `inc` 一并恢复，重连请求因此能命中同一实例。

**为什么这是终结条件**：旧游标要落进新实例的序号空间，前提是「新实例
认它是自己人」；实例身份是随机 64 位，换实例必不匹配 → 无条件快照。
与时钟、持久化、并发**全部解耦**，不再需要任何单调性假设。

**代价**：进程重启后第一次连接必出一次整窗快照（旧行为里如果 wseq
文件还在、还恰好能续传，可以省这一次）。这是可接受的：快照是既有且
被充分测试的路径（冷建 hydration 本就走它），一次性成本换掉整条
隐患链。

**测试**（87 项，+5）：
- `TestIncarnation`：实例身份唯一、实例内稳定；
- `test_same_epoch_seq_but_different_inc_must_snapshot`：同 epoch + 同
  seq + 不同 inc → 身份判据必须拒（这是本设计的唯一承重判据）；
- `test_inc_not_leaked_across_instances`：20 次重建身份全不同；
- boot 系列测试全部保留——它们守护的「数值单调」已降级为**次要属性**
  （影响的是「能否省一次快照」，不再是「会不会丢消息」）。

**变异验证 5 组全部被杀死**：去 boot 高位 / 去 wseq 高位兜底 / 去 guess /
`incarnation` 固定常量 / `_BOOT_MAX` 不预留低位域。

**承重判据的守护测试**（复审实测：该判据当时**零覆盖**，变异掉它 86 项
全绿）。新增 `tests/test_v4_inc.py`（4 项，直接打 `/v4/stream` 取首帧 ack）：

| 用例 | 断言 |
|---|---|
| `test_matching_inc_resumes` | inc 相同 + epoch 相同 + seq 在窗内 → `mode=resume` |
| `test_different_inc_forces_snapshot` | **同 epoch、同 seq、inc 不同 → `snapshot`**（承重判据本体） |
| `test_missing_inc_forces_snapshot` | 不传 inc（老客户端/垫片丢失）→ 一律 `snapshot`，不得因「没带」放行 |
| `test_ack_always_carries_inc` | ack 必须回带 inc（前端续传的唯一依据） |

**变异实测**：删掉 `routes.py` 里 `base_inc == feed.incarnation` 这一条
→ 后两项立刻 FAIL；还原后 4 项全绿。

**同轮自查补出的真实缺陷**（身份匹配的次生问题）：`/v4/stream` 生成器
循环内有**三处**换 feed 后补发整窗快照（越窗补快照、子 feed 孤儿替换、
main 的 epoch/对象换代），原来**只发 frame 不发 ack**。身份匹配落地后，
前端只从 ack 取 inc —— 换 feed 后前端拿着旧实例的 inc 配新实例的 seq，
之后每次重连都被判「身份不匹配」，把「同实例可续传」永久退化成
「一断线就整窗快照」。修法：抽出 `_ack_text(f, mode, to)`，起始两处与
循环内三处**全部**改走它，保证「先 ack（带新 inc）后 frame」的顺序与
起始路径一致。

**测试隔离补漏**：`test_route_smoke` 会真打 `/v4/stream`，实测跑一轮就在

之前重定向 `_WSEQ_DIR` 与 `_boot_path`（与 `test_v4feed` 同法）。现全部
9 个套件逐一套跑均**不污染 HOME**。

#### 5.10.1 复审打回的严重项：ack/frame 撕裂态使身份判据失效

复审实测（未改任何代码，真打 `/v4/stream`）：ack 与 snapshot frame 是
**两次独立 `yield`**，落进**两个 TCP chunk**（实测 99 / 208 字节）：

```
chunk[0]  event:ack   {"mode":"snapshot", ..., "inc":"代2"}   ← 新身份
chunk[1]  event:frame {"kind":"snapshot", "toSeq":..., ...}   ← 新游标
```

客户端若在两者之间断线（SSE 本就是长连接，写超时/切标签/抖动都可能），
本地状态变成 **(inc=代2, seq=代1 旧游标)**。下次重连 `base_inc ==
feed.incarnation` **成立** → 身份判据放行 → `resume_probe(旧游标)` 若在
数值窗口内则判可续传 → 只发增量 → **旧投影吃新实例增量**。

实测撕裂后客户端与服务端 20 行里 10 行不一致（rowId 1–5 全是旧代内容、
6 以后客户端为 None），且 `fromSeq == 客户端 seq` 使前端「规则 2 断档
不猜」**不触发**——花屏直接入账、永不回退快照。这正是原始 P0 的最终形态：
静默丢行 + rowId 撞号。

**可达性**：需「代2 数值窗口覆盖旧游标」+「ack/frame 撕裂」两条件叠加。
前者来自 boot 撞号（实测 6 进程并发启动撞 3 个，read-modify-write 非原子），
后者是网络常态。

**修法（双保险）**：

1. **服务端同批写出**：新增 `_snap_pair(f)` 返回 `(ack_text, frame_text)`，
   调用处一律 `yield _a + _t` —— 一次 yield = 一个 chunk，SSE 客户端同一
   read 拿到两帧。四处（起始 snapshot + 循环内三处）全部改为同批。
2. **前端作废游标**：`v4store.js` 的 ack handler 在 `mode === 'snapshot'`
   时置 `self.seq = 0` + `self._forceSnapshot = true`，直到 snapshot frame
   落账才恢复。即使 chunk 仍被拆开，撕裂态也只会表现为「再快照一次」，
   而不是「旧投影吃新增量」。`mode === 'resume'` 时清掉该标志（否则安静
   feed 只 ack 不发帧会把标志一直挂着）。

守护测试（`tests/test_v4_inc.py` 增至 6 项）：
- `test_ack_and_snapshot_in_same_chunk`：首 chunk 必须同时含 ack 与 frame
  且 ack 在前；
- `test_ack_carries_same_inc_as_frame_seq`：ack.seq 必须等于同批 frame 的
  toSeq（配对原子）。

**变异实测**：把 `yield _a + _t` 拆回两次 yield → 首项立刻 FAIL。

#### 5.10.2 复审打回的一般项：`guess`/`hi` 路径不受钳制

`base = max(guess, hi, floor, boot量) + 2` —— 钳制此前只作用于 boot 那一路。
升级自旧版（boot 曾用时间戳）遗留的 wseq 文件里可能存 ~1.79e18，经
`v4hub` 的 `_hint` 注入 guess → base 越过 JS 安全整数（实测
`1792758829942572290 > 2^53-1`）。且 `_save_wseq` 的 `v <= _wseq_written`
守卫会让该大值**永远留在盘上**（不会被新小值覆盖），故不是一次性问题。

修法：新增 `_BASE_MAX = (2**53) - 1 - 10**6`（留 100 万条余量，避免顶格
钳制后第一条事件立刻再越界），在 `_claim_base` 末尾对**最终 base** 统一
兜底 + 一次告警。守护测试 `test_base_clamped_when_guess_is_polluted`
（注入 1.79e18 起点 → 断言钳制在安全范围内 → 再补一条事件断言仍安全）。
**变异实测**：删掉该钳制 → 用例立刻 FAIL。

#### 5.10.4 复审打回的第二个严重项：`_snap_pair` 吞掉 `sent` 游标

5.10.1 抽 `_snap_pair` 时把原来**解包到 `_gen` 外层**的 `sent` 写成了函数
内局部变量：

```python
# 改坏了：sent 只活在 _snap_pair 里
def _snap_pair(f):
    t, sent = _snap_text(f)
    return _ack_text(f, "snapshot", sent), t
...
_a, _t = _snap_pair(feed)        # _gen 的 sent 仍是 0
```

后果：`_gen` 里 `poll(sent)` 用 `sent=0` → `_in_window(0)` 恒 False →
`poll` 恒 None → 命中 `elif not can_resume(sent)` 的「越窗补快照」分支 →
再发整窗 → 无限循环。实测：空闲每 5 秒一次整窗快照；有 live 事件时
**每来一条消息就整窗重渲一次**（6 秒 22 条事件 = 22 次 snapshot、
**deltas = 0**）。这会直接压垮大会话（649 卡会被全量重建），并废掉
a92/MAJOR-10 整批「安静 feed 不重渲」的修复。

修法：`_snap_pair` 返回三元组，四处调用点全部三元解包：

```python
def _snap_pair(f):
    t, sent = _snap_text(f)
    return _ack_text(f, "snapshot", sent), t, sent

_a, _t, sent = _snap_pair(feed)
```

**守护测试**：`test_snapshot_then_deltas_converges` —— 起始快照后落一条
事件，必须收到 deltas；断言 `snaps == 1 and deltas > 0`。含 8 秒硬截止
（回归态下循环永不退出，没有截止测试会**挂死**而不是失败）。
**变异实测**：把三元返回改回二元 → 用例 15 秒内 FAIL
（`AssertionError: 0 not greater than 0 : 增量路径失效`）。

#### 5.10.3 关于「数值单调」的定位修正

复审不同意把它降级为「次要属性」，理由是撕裂态下它仍是**唯一的偶然
兜底**：若代2 的数值窗口不覆盖旧游标，`resume_probe` 会因 `seq > water`
或 `seq < base` 拒掉，恰好自愈。故注释口径改为：

> **身份匹配是主链；数值单调是撕裂态的第二道兜底，不可删。**

`v4hub.py` 建 feed 处的注释已按此改写，避免后续维护者依据「次要属性」
的说法删掉那批测试。

**边界修正**：`_BOOT_MAX = ((2**53) - 1 - _BOOT_STRIDE) // _BOOT_STRIDE`
（初版只除一次，未预留低位域 → 74.5% 的低位取值越界，实测
`base = 9007199400000002 > 2^53-1`）。修正后最坏 base =
9007199000000001，仍留 25 万安全余量。

## 六、遗留风险（诚实登记）

1. **守护用例必须能「区分修好与没修」**（二十次全审的教训，已固化为纪律）。
   只断言「某函数返回 False」是不够的：要确认拒绝的理由正是被测判据，
   而不是被另一条更早的判据顺手挡掉。本轮 `test_base_survives_total_persistence_loss`
   曾因此假绿——`return 0` 缺陷下 `base=0/water=0`，任何正游标都被
   `seq > water` 拒掉，断言「通过」却与被测逻辑无关。修法是**直接断言
   内部量**（`_wseq_base`）+ 补事件让 water 越过旧游标后再断言一次，
   并用**变异测试**（注入缺陷 → 全套必须挂）证明守护有效。

2. **worker 子系统零自动化测试**。本轮修了 6 条 worker 缺陷，但没有引入测试；下次改动无回归网。
3. **a98 性能批的正确性依赖本轮的 SSE 循环改写**。若后续有人「优化」回 `if _v2 != _v` 的写法，丢帧会立刻复发——已在 `routes.py` 加注释锚定。
4. **需求 1/3 未达成是结构性的**，修 bug 不会改变净增 6360 行、零退役的事实。
5. **图片附件**：`transcript.py` 只修了 images 的类型契约（int → 空数组 + imageN），
   转写里没有本地路径，**重启后照片缩略图仍不可恢复**——本轮不冒充修好。
6. **重启后首连必出一次整窗快照**（5.10 身份匹配的代价）。若某会话快照
   极大（21 回合窗 + 大工具输出），该次连接有可感知的加载延迟。这是用
   一次可预测的成本，换掉「静默丢消息」这类不可恢复的故障——方向不调整。
7. **真实 seq 判重集是 8192 条有界 FIFO**：极老的重复事件（越 8192 条之后
   重放）会多画一行。这是「内存有界」与「绝对不重画」的取舍，选择前者：
   重复画一行可被用户忽略/删除，丢数据不可恢复。正常单线程 emit 不产生
   重复，实际触发率接近零。
